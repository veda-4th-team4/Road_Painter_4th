# RTSP 4채널 패스스루 중계

> **카메라 영상 중계는?** 에 답하는 문서.
> 관련: [../README.md](../README.md) · [docs/PROTOCOL](../docs/PROTOCOL.md) (`LOGIN_OK.stream`)


카메라(PNM-C16083RVQ, 4채널 멀티디렉셔널) → **이 서버** → Qt 클라이언트로 영상을
넘기는 중계. MediaMTX 를 써서 **디코드·재인코딩 없이 그대로 재발행**한다.

```
카메라 4채널 ──RTSP(TCP)──▶ 서버:8554 ──RTSP(TCP)──▶ Qt (2x2)
                            /ch1 /ch2 /ch3 /ch4
```

## ⚠️ 기존 구조는 그대로 둔다

PNM-C16083RVQ 는 **아직 시도 단계**다. 기존 PNO-A9081R 단일 채널 직결 경로
(Qt → 카메라, `LOGIN_OK.cam_ip` 로 URL 조립)는 손대지 않는다 — 언제든 되돌아갈 수
있어야 한다.

그래서 이 중계는 **완전히 선택적**이다:

- 별도 프로세스다. `Server/start.sh` 나 `Makefile` 어디에서도 자동 기동하지 않는다.
  이 디렉터리의 `start.sh` 를 손으로 띄울 때만 존재한다.
- 포트가 안 겹친다 (중계 8554 / 127.0.0.1:9997, 기존 9000 · 6100 · 8083 · 6101).
- 중계를 안 띄우면 서버·카메라·Qt 어느 쪽에도 영향이 없다.
- 되돌리려면 프로세스만 죽이면 된다: `pkill -f relay/bin/mediamtx`

Qt 쪽도 같은 원칙이어야 한다 — 중계 주소는 **추가 설정으로만** 들어가고, 설정이
없으면 지금처럼 카메라에 직결한다.

## 왜 재인코딩을 안 하나

이 서버는 라즈베리파이(aarch64 4코어)다. 4채널 4MP H.265 를 디코드해서 다시
인코딩하는 것은 성능상 불가능하다. MediaMTX 는 받은 패킷을 그대로 넘기므로
(`ffmpeg -c copy` 와 같은 의미) **화질 손실이 0** 이고 CPU 도 거의 안 쓴다.
대신 중계 단을 하나 더 타는 만큼 지연은 직결보다 늘어난다 — 이건 구조상 피할 수 없다.

## ⚠️ 알아둘 제약 두 가지

1. **카메라 트래픽은 반드시 유선(eth0)으로 나가야 한다. 무선으로는 4채널이
   깨진다 — 추측이 아니라 실측이다.**

   4채널 동시 수신 40초, 같은 장면으로 비교한 결과 (2026-08-03):

   | | wlan0 (무선) | eth0 (유선) |
   |---|---|---|
   | 합계 수신 | 6.38 Mbps | **9.90 Mbps** |
   | 중계 경고 | RTP 유실·FU-A 오류 다수 | **0** |
   | 소스 재접속 | 발생 (ch2 끊김) | 없음 |

   ⚠️ 무선 쪽 수신량이 **더 낮은** 것이 핵심이다. 대역폭이 남는데도(상한 20.5Mbps)
   카메라가 프레임을 버리고 있었다는 뜻이다 — 받는 쪽이 못 빼가니 카메라가 자기
   송신 버퍼를 포기한다. TCP 로 당겨오는데도 `RTSP source ... RTP packets lost`
   가 찍히면 이 상황이다.

   ### 📌 2026-08-10 정정 — 주소 배치가 예전 서술과 다르다

   이 절은 원래 "eth0 이 192.168.0.2, wlan0 이 192.168.0.8 이라 커널이 무선을
   고른다"고 적고 있었다. **지금은 그 상태가 아니다.**

   ```
   eth0    192.168.0.8/24  (고정)      ← 서버 주소. 인증서 SAN·클라이언트 기본값
           192.168.0.2/24  (공유기 수동할당)
   wlan0   IPv4 없음 — VEDA_TEAM4 에 붙어 있으나 주소를 안 받음
   ```

   즉 **.2 도 .8 도 둘 다 유선**이고, 무선으로는 이 서버에 붙을 수 없다. 카메라
   경로도 `dev eth0` 으로 나가므로 위 표의 문제는 현재 발생하지 않는다.

   확인:

   ```bash
   ip -brief addr show          # .8 이 eth0 에 있어야 정상
   ip route get 192.168.0.13    # dev eth0 이어야 정상
   ```

   🔴 **주소 배치를 netplan 으로 못박아 둘 것.** `/etc/netplan/60-wifi.yaml` 이
   `.8` 을 wlan0 의 고정 주소로 지정한 채로 두면, 재부팅했을 때 `.8` 이 무선으로
   이사한다. 서버 주소가 `.8` 이므로 (인증서 SAN, 로봇 `NetworkManager.h:13`,
   Qt `serverclient.h:132`) **모든 트래픽이 조용히 무선으로 넘어가고**, 위 표의
   화면 깨짐이 그대로 재현된다. 에러 없이 화질만 나빠지는 종류라 원인을 찾기 어렵다.

   `.8` 은 eth0 에 고정하고, wlan0 에서는 빼고 기본 경로도 주지 않는다 (무선은
   비상 접속 전용). 공유기의 `.8` 예약은 wlan0 MAC 에 걸린 채로 **두는 것이 맞다**
   — 그 예약이 다른 기기가 `.8` 을 받아가는 것을 막아준다. 대신 wlan0 이 DHCP 를
   하게 두면 안 된다 (예약대로 `.8` 을 받아 같은 IP 가 두 인터페이스에 생긴다).
2. **채널별 RTSP 경로를 짐작해서 넣지 말 것.** 틀린 URL 로 반복 접속하면 Hanwha
   카메라가 계정을 잠근다 (`RTSP/1.0 490 Account Blocked`). 반드시
   `probe_onvif.py` 로 카메라가 직접 알려주는 값을 받아 쓴다.

## 설치와 기동

```bash
cd Server/relay

# 1) MediaMTX 바이너리 받기 (bin/ 은 gitignore — 60MB)
./install.sh

# 2) 설정 파일 만들기
cp cameras.env.example cameras.env

# 3) 카메라에게 채널별 RTSP 주소 물어보기
python3 probe_onvif.py --host <카메라IP> --user admin --password '<비번>' --env

# 4) 출력된 MTX_PATHS_CH1..CH4_SOURCE 를 cameras.env 에 붙여넣기
#    (이름·해상도를 보고 채널 순서가 맞는지 확인할 것)

# 5) 기동
./start.sh        # 포그라운드 (로그 보며 확인)
./start.sh -d     # 백그라운드 + relay.log
```

기동하면 Qt 는 이 주소들을 본다:

```
rtsp://<서버IP>:8554/ch1
rtsp://<서버IP>:8554/ch2
rtsp://<서버IP>:8554/ch3
rtsp://<서버IP>:8554/ch4
```

## 파일

| 파일 | 역할 | 커밋 |
|---|---|---|
| `mediamtx.yml` | 중계 설정. 카메라 주소·계정 없음 | O |
| `cameras.env.example` | 카메라 접속 정보 템플릿 | O |
| `cameras.env` | 실제 주소·계정 | **X** (gitignore) |
| `probe_onvif.py` | ONVIF 로 채널별 RTSP 주소 조회 | O |
| `install.sh` | MediaMTX 바이너리 설치 | O |
| `start.sh` | 중계 기동 | O |
| `bin/` | MediaMTX 바이너리 | **X** (gitignore) |

카메라 주소와 계정은 `mediamtx.yml` 에 안 들어간다. `cameras.env` 의 값이
환경변수(`MTX_PATHS_CH1_SOURCE` …)로 주입되어 설정을 덮어쓴다. 그래서 설정 파일은
그대로 커밋해도 안전하다.

## 확인과 문제 해결

```bash
# 중계가 보는 경로 상태 (연결됨/대기 등)
curl -s http://127.0.0.1:9997/v3/paths/list | python3 -m json.tool

# 중계된 스트림을 직접 열어보기
ffplay -rtsp_transport tcp rtsp://<서버IP>:8554/ch1
```

| 증상 | 원인 | 조치 |
|---|---|---|
| `401 Unauthorized` (카메라 쪽) | `cameras.env` 의 계정·비번 | 비번에 `@ : / ? #` 있으면 URL 인코딩 (`@`→`%40`) |
| `404 Not Found` (카메라 쪽) | 채널 경로가 틀림 | `probe_onvif.py` 로 다시 받기. 계속 두드리면 계정 잠김 |
| `490 Account Blocked` | 이미 잠김 | 카메라 웹 UI 에서 잠금 해제 후 정확한 URL 로만 재시도 |
| Qt 에서만 끊김 | 무선 대역 포화 | `ip route get <카메라IP>` 로 wlan0 으로 나가는지 확인 → eth0 로 넘기기 |
| 어느 날 갑자기 연결 실패 | 카메라 IP 가 바뀜 | PNM 은 DHCP 라 IP 가 움직인다. 아래 "카메라 IP 고정" 참고 |
| `write queue is full` 로그 | 큐 부족 | `mediamtx.yml` 의 `writeQueueSize` 상향 (지연이 늘어남) |

## 채널 매핑과 실측 (2026-08-03, PNM-C16083RVQ @ 192.168.0.13)

ONVIF 로 조회한 결과 채널마다 프로파일이 3개씩, 총 12개다. 경로의 채널 인덱스는
**0-based** 이며 카메라 웹 UI 의 CH 1~4 에 대응한다.

| 프로파일 | 스펙 | 용도 |
|---|---|---|
| `profile1` | 2592x1520 MJPEG 5fps | 스냅샷 |
| `profile2` | 2592x1520 **H.264** 30fps | **메인스트림 — 중계가 쓰는 것** |
| `profile10` | 640x480 H.264 10fps | 모바일/서브 |

```
메인 (선택 채널을 크게 볼 때)
rtsp://<서버IP>:8554/ch1  <-  rtsp://<카메라>:554/0/onvif/profile2/media.smp  (웹UI CH1)
                    /ch2  <-                      /1/onvif/profile2/...        (CH2)
                    /ch3  <-                      /2/onvif/profile2/...        (CH3)
                    /ch4  <-                      /3/onvif/profile2/...        (CH4)

서브 (2x2 미리보기용)
rtsp://<서버IP>:8554/ch1s <-  rtsp://<카메라>:554/0/onvif/profile10/media.smp
                    /ch2s ...  /ch3s ...  /ch4s
```

카메라에 설정된 비트레이트 상한은 **채널당 5120kbps** (GOP 60, H.264 High) 이므로
4채널 최악이 **20.5Mbps** 다. 실측은 아래와 같다 — 대역폭 자체는 여유가 있고,
문제가 되는 건 위에 적은 **경로(무선/유선)** 다.

| 4채널 동시 | 합계 | 비고 |
|---|---|---|
| 메인 (`ch1`~`ch4`) | 9.9 Mbps | 2592x1520 30fps |
| 서브 (`ch1s`~`ch4s`) | 3.14 Mbps | 640x480 10fps, 메인의 약 1/3 |

서브스트림은 2x2 미리보기용이다. 4칸을 1920x1080 화면에 늘어놓으면 한 칸이
960x540 정도라, 2592x1520 을 받아봐야 줄여서 그리게 된다 — 눈에 안 보이는 화질을
위해 클라이언트 CPU 를 태울 이유가 없다. Qt 쪽 설계는
[`Client/PNM_4CH_QT_PLAN.md`](../../Client/PNM_4CH_QT_PLAN.md) 참고.

## 카메라 IP 고정 — 완료 (2026-08-10)

두 카메라 모두 **이중으로** 고정돼 있다. 카메라 웹 UI 에서 `IP 타입: 수동` 으로
박고, 공유기에도 같은 MAC 에 수동할당 예약을 걸어두었다.

| IP | MAC | 카메라 | 상태 |
|---|---|---|---|
| 192.168.0.12 | `e4:30:22:eb:d7:f9` | PNO-A9081R (LAN 2) | 카메라 수동 + 공유기 예약 |
| 192.168.0.13 | `e4:30:22:f2:d1:86` | PNM-C16083RVQ (LAN 3) | 카메라 수동 + 공유기 예약 |

**둘 다 필요하다.** 카메라 쪽만 고정하면 공유기는 그 주소가 쓰이는 줄 모르고,
나중에 붙는 기기에 같은 주소를 내줘서 IP 충돌이 난다 — 이 공유기의 DHCP 풀은
실제로 `.3 .5 .6 .11` 을 자동할당하고 있어 `.12/.13` 이 사정권 안이었다.
공유기 예약이 그 주소를 "찜" 해 두는 역할을 한다.

`.13` 이 움직이면 `cameras.env` 와 `config/camera.json` 이 조용히 깨지고 영상이
통째로 안 나온다. 장비를 찾을 때는 이름표 말고 MAC 으로 확인한다:

```bash
ping -c1 192.168.0.13 >/dev/null; ip neigh show 192.168.0.13
```

> 2026-08-03 기록: 당시 공유기 장치 목록이 PNM 을 `.12` 로 잘못 표시했다.
> PNO 가 `.12` 를 이미 고정으로 쓰고 있어 충돌이 났고 PNM 이 `.13` 으로 밀려난
> 흔적이다. 지금은 양쪽 예약이 정리돼 표와 실제가 일치한다.

## 안 볼 때는 안 당긴다

모든 경로가 `sourceOnDemand: true` 다. 보는 클라이언트가 없으면 카메라에서
아무것도 안 당겨오고, 마지막 시청자가 끊기고 10초 뒤 카메라 연결을 닫는다.
무선 대역과 카메라 세션을 아끼기 위한 설정이다.
