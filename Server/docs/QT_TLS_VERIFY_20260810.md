# Qt 요청 — TLS 서버 인증서 검증 활성화

**작성일**: 2026-08-10
**대상**: Qt팀
**Qt 기준**: `main` `5d17adf` (PR #41 병합분)
**분류**: 보안 — 기능에는 영향 없음, 지금 당장 깨지는 것 없음

---

## 1. 현재 상태

`Client/src/serverclient.cpp`에서 서버 인증서 검증이 **세 겹으로** 꺼져 있습니다.

```cpp
// :15  생성자
m_socket->setPeerVerifyMode(QSslSocket::VerifyNone);

// :40  connectToServer()
m_socket->ignoreSslErrors();

// :70  onErrors()
Q_UNUSED(errors);
m_socket->ignoreSslErrors();
```

주석에 의도가 적혀 있습니다 — "1차 연동이므로 생략, 권장 방식은 server.crt를 신뢰 CA로 추가"(`serverclient.h:25`). **그 1차 연동 단계는 지났다고 보고 요청드립니다.**

### 다른 두 클라이언트와의 비교

| 클라이언트 | 체인 검증 | 신원(IP) 검증 | 코드 |
|---|:---:|:---:|---|
| **CCTV** | ✅ | ✅ | `SSL_VERIFY_PEER` + `X509_VERIFY_PARAM_set1_ip_asc` |
| **로봇** | ✅ | ❌ | `SSL_VERIFY_PEER` (IP 확인 없음) |
| **Qt** | ❌ | ❌ | `VerifyNone` + `ignoreSslErrors()` ×2 |
| 서버 테스트 도구 | ✅ | ❌ | `SSL_VERIFY_PEER` + `server.crt`를 CA로 |

**Qt만 아무 검증도 하지 않습니다.** CCTV는 이미 IP 신원까지 확인하고 있으므로, 같은 수준을 맞추는 것이 목표입니다.

---

## 2. 왜 지금 문제인가

### TLS는 켜져 있지만 절반만 동작합니다

`VerifyNone`은 **도청은 막지만 중간자는 막지 못합니다.** 암호화 채널은 만들어지는데, 그 채널 반대편이 진짜 서버인지 확인하지 않습니다. 공격자가 자기 인증서를 내밀어도 Qt는 그대로 받아들입니다.

### 이 현장의 조건이 공격을 쉽게 만듭니다

- Qt는 **무선으로** 서버에 붙습니다
- WiFi 비밀번호가 `12345678`입니다
- 같은 WLAN에 붙은 누구나 ARP 스푸핑으로 Qt↔서버 사이에 낄 수 있습니다

### 중간자가 얻는 것

Qt 세션을 장악하면 **QT role이 보낼 수 있는 모든 것**을 보낼 수 있습니다.

| 얻는 것 | 결과 |
|---|---|
| `LOGIN` 평문 열람 | 계정 id/비밀번호 |
| `CMD START_DRAW` 주입 | **로봇이 실제로 출발합니다** |
| `CMD FORWARD/TURN` 주입 | 로봇 수동 조종 |
| `BLUEPRINT` 변조 | 엉뚱한 도형을 바닥에 도색 |
| `CMD ESTOP` 차단 | 조작자의 비상정지가 서버에 안 닿음 |

🔴 **마지막 항목이 핵심입니다.** 이건 데이터 유출이 아니라 **움직이고 페인트를 뿌리는 기계의 제어권** 문제입니다.

---

## 3. ⚠️ 같이 알아두실 것 — 서버도 클라이언트를 인증하지 않습니다

공정하게 말씀드리면, **이건 Qt만의 문제가 아닙니다.**

서버는 클라이언트 인증서를 요구하지 않습니다 (`Server/src/tls_server.cpp` 생성자에 `SSL_CTX_set_verify` 호출이 없습니다). 그래서 포트 9000에 닿을 수 있는 누구나 이렇게 할 수 있습니다:

```json
{"type":"HELLO","payload":{"role":"QT"}}
```

그리고 서버는 **같은 role의 기존 연결을 끊고 교체합니다** (`tls_server.cpp` 세션 등록부). 즉 중간자가 될 필요도 없이, 그냥 접속해서 진짜 Qt를 밀어내면 됩니다.

**그래서 Qt 쪽만 고치면 절반만 닫힙니다:**

| 조치 | 막히는 것 | 안 막히는 것 |
|---|---|---|
| Qt가 서버를 검증 (이 문서) | Qt가 가짜 서버에 붙는 것 | 남이 QT를 사칭해 서버에 붙는 것 |
| 서버가 클라이언트를 검증 (별건) | 사칭 접속 | — |

Qt 쪽이 더 싸고 (아래 §4 참고) 코드 변경이 작아서 먼저 요청드리는 것이고, **서버 쪽 mTLS는 서버팀 과제로 따로 잡겠습니다.** 두 개가 다 되어야 닫힙니다.

## 4. 고치는 법

서버 인증서는 자체 서명이므로, `server.crt`를 **신뢰 CA로 등록**하면 됩니다. 그러면 그 인증서(그리고 그 키를 가진 서버)만 통과합니다 — 사실상 인증서 피닝입니다.

```cpp
// ServerClient 생성자
m_socket = new QSslSocket(this);

QSslConfiguration cfg = m_socket->sslConfiguration();
cfg.setCaCertificates(QSslCertificate::fromPath(
    QStringLiteral(":/certs/server.crt")));   // qrc 리소스로 넣는 것을 권장
m_socket->setSslConfiguration(cfg);
m_socket->setPeerVerifyMode(QSslSocket::VerifyPeer);
```

그리고 **`ignoreSslErrors()` 두 곳을 제거**합니다. `onErrors()`는 무시가 아니라 사용자에게 알리도록 바꿔 주십시오:

```cpp
void ServerClient::onErrors(const QList<QSslError> &errors)
{
    QStringList msgs;
    for (const QSslError &e : errors) msgs << e.errorString();
    // 🔴 여기서 ignoreSslErrors()를 부르면 위 VerifyPeer 설정이 통째로 무의미해진다.
    emit socketError(QStringLiteral("서버 인증서 검증 실패 — %1").arg(msgs.join(", ")));
}
```

`connectToServer()`의 `ignoreSslErrors()`(:40)는 **접속 전에 미리 부르는 것이라 더 위험합니다** — 어떤 오류가 날지 보지도 않고 전부 무시하겠다고 선언하는 셈입니다.

### 현재 인증서 SAN

```
IP Address:127.0.0.1, IP Address:192.168.0.8, DNS:localhost
```

`m_host` 기본값이 `192.168.0.8`이므로 그대로 통과합니다. 다만:

⚠️ **`192.168.0.2`는 SAN에 없습니다.** 파이 eth0에 그 주소도 붙어 있어서, Qt 설정에서 `.2`로 바꾸면 검증이 실패합니다. 서버 주소는 `.8`로 통일된 상태이므로 정상 동작에는 문제가 없지만, 접속 오류를 만나면 이걸 먼저 의심해 주십시오.

---

## 5. 운영 비용 — 솔직히 말씀드리면

**인증서를 재발급하면 배포된 Qt를 전부 갱신해야 합니다.**

자체 서명 인증서를 CA로 쓴다는 건 그 인증서 자체에 묶인다는 뜻입니다. `gen_cert.sh`를 다시 돌리면 기존 Qt는 전부 접속이 끊깁니다.

이건 CCTV와 로봇이 **이미 지불하고 있는 비용**입니다. Qt만 면제받고 있었던 것이고요. 서버 IP나 인증서를 바꿀 일이 잦지 않다면 감당할 만합니다.

qrc 리소스로 넣으면 실행 파일 하나만 교체하면 되므로, 파일을 따로 배포하는 것보다 낫습니다.

## 6. 요청 정리

| # | 내용 | 규모 |
|---|---|---|
| 1 | `server.crt`를 신뢰 CA로 등록 + `VerifyPeer` | 5줄 |
| 2 | `ignoreSslErrors()` 2곳 제거 | 2줄 |
| 3 | `onErrors()`에서 사용자에게 오류 표시 | 5줄 |
| 4 | `serverclient.h:25` 주석 갱신 | 1줄 |

**기능 변경은 없습니다.** 정상 상황에서는 동작이 완전히 같고, 달라지는 건 "가짜 서버에 붙었을 때 접속이 실패한다"뿐입니다.

일정에 여유가 없으시면 **1·2번만이라도** 먼저 해주시면 위 §2의 위험은 닫힙니다. 3번은 그 뒤에 하셔도 됩니다.

## 7. 서버팀이 할 것

- **mTLS (클라이언트 인증서 검증)** — §3의 나머지 절반. 별도 과제로 잡겠습니다.
  Qt·로봇·CCTV 모두에 클라이언트 인증서를 발급해야 하므로 세 팀 합의가 필요합니다.
- **SAN에 `.2` 추가 여부** — 현재 불필요하다고 보지만, 유선 직결 시험 계획이 있으면 알려주십시오.

### 인증서 파일은 이미 저장소에 있습니다

`Server/certs/server.crt`가 커밋되어 있으므로 **따로 전달받으실 필요가 없습니다.**
그대로 복사해 qrc에 넣으시면 됩니다.

```
CN       : road-painter-server
유효기간 : 2026-07-15 ~ 2027-07-15
SAN      : IP 127.0.0.1, IP 192.168.0.8, DNS localhost
```

⚠️ **개인키(`server.key`)는 저장소에 없고 앞으로도 올리지 않습니다** (`.gitignore`로
차단, 전체 커밋 이력에도 흔적 없음 — 확인 완료). 인증서는 서버가 핸드셰이크마다
모든 접속자에게 보내는 공개 데이터라 저장소에 있어도 무방하지만, 개인키가 새면
누구나 서버를 사칭할 수 있어 이 문서의 조치가 통째로 무의미해집니다.

🔴 **인증서를 재발급하면 세 클라이언트(Qt·로봇·CCTV) 모두 갱신이 필요합니다.**
개인키가 서버 파이 한 대에만 있으므로, 파이를 교체하면 재발급이 강제됩니다.
