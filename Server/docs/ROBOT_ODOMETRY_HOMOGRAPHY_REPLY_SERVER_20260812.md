## 1. §2 확정 요청 — 회신

| | 항목 | 회신 |
|---|---|---|
| 2-1 | 픽셀 공간 | **제안대로 확정** (단서 1건) |
| 2-2 | 메시지 형식 | **확정** — §3-1 JSON + `CALIB_DONE`에 `m_mm`/`n_mm` |
| 2-3 | `request_id` | **`H_MATRIX` 송신부 수정 불필요** |
| 2-4 | 채널 규약 | **1-based 확정** (기존 규약과 동일) |
| 2-5 | `m`/`n` 전달 | **수용** |
| 2-6 | 세션 중복 | **서버 측 이미 구현됨** |

### 1-1. (§2-1) 픽셀 공간 — raw로 확정

POS가 raw 픽셀인 것 맞습니다. `src/calib.hpp` 헤더 규약에 명시돼 있습니다:

> CCTV는 마커 코너를 "원본 픽셀 좌표"로만 보낸다 (변환 금지).
> 서버가 undistort(왜곡 보정) → H_marker 적용으로 바닥 좌표를 계산한다.

따라서 `CALIB_CAPTURE_OK.pixel_uv` = **raw**, 왜곡보정·피팅은 카메라 내부, 번들은
`coord_mode:"undistort"` — 제안 그대로 갑니다.

**단서 하나**: 서버가 이 raw 픽셀로 찍는 폐합오차(계획서 §2-3)는 **mm 환산이
불가능합니다.** 그 시점에 새 캘리는 아직 없고, 옛 캘리는 있을 수도 없을 수도 있기
때문입니다. 그래서 서버 로그는 **픽셀 공간 지표로만** 남기고, **mm 환산본은 카메라
쪽 기록을 정본**으로 하겠습니다. 관리자창 표시도 카메라 값 기준으로 부탁드립니다.

### 1-2. (§2-2) 메시지 형식 확정

계획서 §3-1의 JSON을 그대로 쓰되 `CALIB_DONE`에 §2-5를 반영합니다.

```
Server → CCTV:  CALIB_CAPTURE     {ch, request_id, point_index, world_xy_mm:[x,y]}
CCTV → Server:  CALIB_CAPTURE_OK  {ch, request_id, point_index, pixel_uv:[u,v], spread_px}
Server → Robot: GO
                ...9점 반복...
Server → CCTV:  CALIB_DONE        {ch, request_id, m_mm, n_mm}
CCTV → Server:  H_MATRIX          {ch, calib:{...}}
```

`spread_px`(§1-1)를 ack에 실어주시는 것 찬성합니다. 서버 로그에도 같이 남기겠습니다.

### 1-3. (§2-3) `request_id` — `H_MATRIX` 쪽은 작업하지 않으셔도 됩니다

`src/router.cpp:939`에 이미 결론이 박혀 있습니다:

> 🔴 `request_id`는 서버가 직접 찍는다. CCTV가 되돌려주기를 기대하면 안 된다:
> 평면 번들 스키마에서는 `outMsg["payload"] = bundle`이 payload를 통째로
> 갈아치우므로 CCTV가 실어 보낸 필드가 여기서 사라진다.

즉 `H_MATRIX`에 `request_id`를 실어 보내셔도 **서버가 덮어씁니다.** 카메라 송신부
수정은 불필요합니다.

`CALIB_CAPTURE_OK`는 실어주시면 로그 대조에 유용하지만, **서버가 세션 매칭에 쓸 키는
`point_index` + `ch`** 입니다. 여기서 실제로 막아야 하는 것은 "이전 지점의 늦게 도착한
ack가 현재 대기를 푸는 것"이고, 그 방어는 `point_index` 일치 검사입니다.
`request_id`는 로그용으로만 씁니다.

### 1-4. (§2-4) 채널 1-based — 확정

`src/protocol.hpp:358`에 이미 규약이 있습니다: "채널 번호는 1부터 시작한다
(카메라 웹UI의 CH1~CH4와 같은 번호)". 인바운드 `CALIB_CAPTURE`/`CALIB_DONE`도
1-based로 보냅니다. 2026-08-11 POS 사고와 같은 규약입니다.

### 1-5. (§2-5) `CALIB_DONE`에 `m_mm`/`n_mm` — 수용

역산보다 명시가 낫다는 데 동의합니다. §1-2 형식에 반영했습니다.

### 1-6. (§2-6) 세션 중복 — 서버 측은 이미 구현됨

`src/router_calib.cpp:101`의 `calibActive_` 가드가 **method와 무관하게** 진행 중인
세션이 있으면 `busy`로 거절합니다. 추가로 도색 중(`planActive_` / `awaitingArrival_` /
`drawRequested_`)에도 거절합니다. 카메라 쪽 가드만 붙이시면 양방향이 닫힙니다.

## 2. §4 검증의 한계 — 동의, 계획서를 고칩니다

### 2-1. 균일 스케일이 통과하는 것 — 검산 확인

라벨이 참값의 `s`배(`W_label = s · W_true`)이면, 피팅 결과는
`H_fit = diag(s, s, 1) · H_true`가 되고 이것은 **유효한 호모그래피**입니다.
잔차가 정확히 0으로 나옵니다.

이 연산이 서버 코드에 그대로 있다는 게 오히려 좋은 방증입니다 —
`src/calib.hpp`의 `scaleMat3Rows01()`(mm↔m 변환에 쓰는 함수)이 정확히
"0·1행에 스칼라를 곱한다"입니다. **스케일은 호모그래피가 자유롭게 흡수한다**는 사실이
이미 코드로 드러나 있었습니다.

폐합오차가 0이 되는 것도 맞습니다. 네 변이 같은 비율로 짧아지면 실제 궤적도 닫힌
직사각형이라 출발점으로 정확히 복귀합니다.

### 2-2. 표에서 한 줄만 수정 제안 — "회전 88°"

`재투영 잔차 ❌ 흡수(전단)`은 과합니다. 네 번 다 88°면 헤딩이 8° 남아 경로가 닫히지
않고, **라벨(직사각형)의 아핀상은 반드시 평행사변형인데 실제 궤적은 평행사변형이
아니라서** 잔차가 남습니다. (m=900 / n=600 / 88°로 계산하면 폐합오차 약 77 mm,
잔차도 0이 아닙니다.)

잔차의 진짜 사각지대는 **닫히는** 아핀 왜곡입니다:

| 오도메트리 오차 | 재투영 잔차 | 폐합오차 |
|---|---|---|
| 균일 스케일 3% | ❌ 완전 흡수 | ❌ 0 |
| m·n 스케일 다름 | ❌ 흡수 | ❌ 0 |
| turn이 88°/92° 번갈아 (진짜 전단) | ❌ 흡수 | ❌ 0 |
| turn 전부 88° | ✅ 잡힘 | ✅ 잡힘 |
| 한 지점만 슬립 | ✅ | ✅ |

결론(스케일이 두 장치의 공통 사각지대)은 그대로입니다. 계획서 §2-1의 "유일한 자체
검증 수단", §2-3의 "유일한 직접 측정값" 표현을 이 표에 맞게 고치겠습니다.

### 2-3. §4-1 두 방식 비교 — 동의, CCTV 계산으로

닮음변환 정렬 후 `s`와 RMS를 보는 절차 동의합니다. 월드 원점이 다르므로 행렬 직접
비교가 안 된다는 것도 맞습니다.

### 2-4. §4-2 1 m 실측 — 수락

로봇팀에 요청하겠습니다. 이건 세션마다가 아니라 **로봇 상수 캘리 1회**이므로,
이 값을 확보한 뒤에도 오도메트리 방식의 이점은 그대로 남습니다:

- `H_marker`를 **직접 측정** — 카메라 높이/마커 높이를 거치는 시차 보정 체인이 없음
- 작은 보드가 아니라 **실제 작업 영역 전체**를 덮는 대응점
- 재캘리에 **물리 타깃 불필요** — 로봇만 있으면 됨

즉 "줄자가 결국 필요하면 이 방식은 왜 하나"에 대한 답을 계획서에도 적어두겠습니다.

## 3. 서버팀 추가 요청

### 3-1. 번들에 `method` 필드

§3-2에서 운영자가 파생/측정 슬롯을 고르면, **서버는 어느 방식으로 만든
`H_marker`인지 모른 채** 번들을 받습니다. 나중에 좌표가 이상할 때 "이 캘리가 어떻게
뜬 것인가"를 추적할 방법이 없습니다.

`marker_height_mm`처럼 번들에 한 필드만 추가해주시면 서버 저장·로그·Qt 중계 어디서든
구분됩니다.

```json
"method": "checkerboard" | "robot_motion"
```

### 3-2. `coord_mode`는 선언일 뿐 서버가 검증할 수 없습니다

`coord_mode:"undistort"`는 번들이 스스로 주장하는 값이고, 서버는 그것을 확인할
수단이 없습니다. 문제는 서버의 왜곡 보정이 **`K`/`D`의 존재 여부로만 켜진다**는
점입니다(`Calib::hasKD`). `K`/`D`가 빠진 번들이 오면 서버는 **왜곡 보정을 조용히
건너뛰고** H를 raw 픽셀에 그대로 적용합니다 — H는 보정된 픽셀을 기대하는데요.
에러 없이 좌표만 틀어집니다.

이 프로젝트에서 실제로 겪은 것으로 보입니다. `admin_console/cctv.py` 주석에
"`K`·`D`·`H_marker`를 버렸다 — 에러 없이 보정만 꺼졌다"가 남아 있습니다.

**요청**: 오도메트리 탭의 번들 조립기가 `K`/`D`를 **반드시** 싣도록(비면 전송 거부)
해주시면 좋겠습니다. §1-4에서 "조립 함수 하나"로 구조화하셨으니 그 지점에 게이트를
하나 두는 것으로 충분할 것 같습니다. 서버 쪽에서도 `coord_mode == "undistort"`인데
`K`/`D`가 없으면 WARN을 찍도록 넣겠습니다(거부는 하지 않습니다 — 레거시 번들 호환).

### 3-3. `K` 변경 시 측정 `H_marker`가 stale이 됩니다

§3-3에서 **마커 높이** 변경에 대해 stale 표시를 붙이겠다고 하셨는데, 같은 성격의
함정이 **`K`** 쪽에도 있습니다.

측정 `H_marker`는 §4-3대로 기존 `K`/`D`로 보정한 픽셀 위에서 피팅됩니다. 나중에
체커보드 내부 파라미터를 다시 잡아 `K`가 바뀌면, 그 `H_marker`는 **더 이상 유효하지
않은 왜곡 보정 결과 위에 얹힌 행렬**이 됩니다. 조용히 틀어집니다.

§1-4에 "H 피팅 후 `K`가 바뀌면 다시 확인하라고 표시하되 버리지는 않는" 장치가 이미
있다고 쓰셨는데, **그 가드가 신설 `H_marker`(측정) 슬롯에도 걸리는지** 확인
부탁드립니다. 마커 높이 stale과 같은 취급이면 됩니다.
