## 0. 로봇 코드 현황 (2026-07-28 `origin/feature/rpi-robot` @ `77afd1b` 기준)

로봇팀이 스텝 오도메트리 + IMU를 올리면서 이전에 비어 있던 것 중 상당수가 채워졌다.
**그래도 통합(단계 D)을 지금 돌리면 접근 단계에서 멈춘 채 끝난다.** 남은 것이 아래다.

### 채워진 것

| 항목 | 상태 | 근거 |
|---|---|---|
| 세그먼트 진행 | ✅ `AdvanceSegment()` 신설, MOVE/TURN 완료 시 호출 | `PathFollower.cpp:45`, `main.cpp:188,205` |
| 도달 판정 | ✅ **스텝 카운트 기반** (시간 기반 아님) — 15433.09 steps/m, 22.58044 steps/deg | `PathFollower.cpp:115,63` |
| `READY` 송신 | ✅ `SendReady(seg)` | `NetworkManager.cpp:205` |
| `ALIGN`/`GO`/`DRIFT` 수신 | ✅ 파싱·큐잉 구현 | `NetworkManager.cpp:349,356,360` |
| IMU Yaw 적분 | ✅ MPU6050 z축, 데드밴드·슬루·이상치 필터 포함 | `ImuManager.cpp:117` |

### 🔴 아직 막혀 있는 것 — 단계 D 진입 전 필수

| # | 문제 | 결과 | 위치 |
|---|---|---|---|
| 1 | **`PATH_DONE`을 어디서도 보내지 않는다** | 서버가 `awaitingArrival_`로 영원히 대기 → 접근에서 그리기로 못 넘어감 | 로봇 전체에 문자열 자체가 없음 |
| 2 | **`bypass_server_go = true`로 하드코딩** | READY는 보내지만 GO/ALIGN을 기다리지 않고 바로 출발 → **출발 전 정렬이 무효** | `main.cpp:132` |
| 3 | **DRIFT 부호 반대** | 각도 보정이 오차를 키우는 쪽으로 작동 (발산) | `PathFollower.cpp:158` |
| 4 | **IMU Yaw를 오차에 그대로 더함** | TURN을 한 번 지나면 Yaw가 절대각(예: 90°)이라, 직진 중 90°를 되돌리려 계속 회전 | `PathFollower.cpp:157` |
| 5 | **`NOZZLE` op 미지원** | 해당 세그먼트에서 어느 분기에도 안 걸려 `AdvanceSegment()`가 호출되지 않음 → **영구 정지** | `main.cpp:130,192` |
| 6 | **`dist_m` 음수 무시** | `fabs`로 크기만 쓰고 속도는 항상 `+0.05` → 후진 명령이 **전진**함 | `PathFollower.cpp:118,201` |
| 7 | `pivot` 필드 미파싱 | 꼭짓점 동작 구간을 로봇이 구분 못 함 | `RobotTypes.h:78` |
| 8 | `speed_mps`/`speed_dps` 미파싱 | 구간별 속도 지정이 무시됨 (속도 5cm/s·회전 400sps 고정) | 〃 |

**3·4번이 특히 위험하다.** 5·6번처럼 멈추거나 안 움직이는 게 아니라 **로봇이
그럴듯하게 움직이면서 틀린 방향으로 간다.** 단계 A에서 잡지 못하면 단계 D에서
"CCTV가 이상한가? 서버 계산이 이상한가?"로 원인이 흩어진다.

> 📌 **결론은 그대로: 사용자가 말한 2)번(로봇 단독)을 1)번보다 먼저 한다.**
> 아래 단계 A가 그것이고, 단계 A를 통과해야 단계 D(통합)가 의미를 가진다.

### 참고 — 정리 대상 (동작에는 지장 없음)

- `PathFollower::Update()` (`PathFollower.cpp:208`)는 이제 아무도 호출하지 않는 옛 경로. 스텝 기반 `UpdateMove`/`UpdateTurn`으로 대체됐다.
- `StartOffsetMove`/`UpdateOffsetMove` (`PathFollower.cpp:172,181`)는 펜 오프셋용으로 만들었으나 `main.cpp`에서 호출되지 않는다. 6번을 고칠 때 여기에 방향 부호를 넣으면 된다.
- MOVE 완료 시마다 `out_nozzle_on = 0` (`PathFollower.cpp:148`) — 연속 도색 구간 사이마다 노즐이 한 번 꺼져 **꼭짓점마다 끊긴 자국**이 생길 수 있다. 단계 A-3에서 확인.

## 단계 구성 — 앞 단계를 통과해야 다음으로

| 단계 | 내용 | 로봇 | CCTV | 서버 | 소요 |
|---|---|---|---|---|---|
| **A** | 로봇 단독 성능·정확도 (사용자 2번) | ✅ | ❌ | ❌ | 반나절 |
| **B** | 좌표계 정합성 (로봇은 가만히) | 정지 | ✅ | ✅ | 30분 |

## 단계 A — 로봇 단독 (사용자 2번)

서버 없이 로봇 RPi에서 직접 명령을 주입한다. 기존 도구가 일부 있다:
`src/motor_test.cpp`(모터 직결), `src/imu_test.cpp`, `driver/driver_test.cpp`.

### A-1. 먼저 고쳐야 할 것 (로봇팀) — 0절의 8개

우선순위 순. 1~4는 단계 D 진입 전 필수, 5~8은 program 중계를 쓰려면 필수.

1. **`PATH_DONE {phase}` 송신** — `IsPathFinished()`가 참이 되는 순간 1회.
   받은 PATH의 `phase`를 그대로 되돌려준다. 이게 없으면 서버가 접근→그리기로 못 넘어간다.
2. **`bypass_server_go`를 끈다** (`main.cpp:132`). 지금은 READY를 보내고도 GO를
   안 기다려서 출발 전 정렬이 통째로 무효다. 끄면 GO 대기 경로(`main.cpp:147~173`)가
   살아난다 — 이미 구현돼 있으니 플래그만 내리면 된다.
3. **DRIFT 부호를 뒤집는다** (`PathFollower.cpp:158`).
   서버의 `ALIGN`/`DRIFT`는 둘 다 `normDeg(목표heading − 현재theta)` = **"반시계로 이만큼
   더 돌아야 한다"**는 같은 규약이다. 로봇의 `velocity_to_sps`는 `w > 0`이 반시계이므로
   `target_w = +error * gain`이어야 하는데 지금은 `-`가 붙어 있다.
   ALIGN 쪽(`StartTurn`, 양수 = 좌회전)은 부호가 맞으므로 **로봇 코드 안에서도 서로 어긋나 있다.**
4. **IMU Yaw를 오차에 더하지 않는다** (`PathFollower.cpp:157`).
   `current_yaw`는 draw 진입 시 0으로 리셋한 뒤 계속 적분되는 **절대 방위**고,
   세그먼트마다 리셋되지 않는다. TURN을 한 번 지나면 정상 주행 중에도 Yaw ≈ 90이라
   `drift + 90`을 오차로 보고 계속 되돌리려 한다.
   → MOVE 시작 시점의 Yaw를 기준값으로 잡고 **그 차이만** 쓰거나, 서버 DRIFT가
   들어오는 동안엔 IMU를 보정이 아니라 **DRIFT 사이의 보간용**으로만 쓴다
   (서버 DRIFT는 5Hz, 제어 루프는 12.5Hz).
5. **`NOZZLE` op 처리** — 지금은 MOVE/TURN 어느 분기에도 안 걸려 `AdvanceSegment()`가
   호출되지 않고 **거기서 영구 정지**한다. 최소한 "모르는 op는 로그 남기고 건너뛴다"는
   기본 분기라도 넣어야 한다.
6. **`dist_m` 음수 = 후진** — `CalculateMoveSteps`가 `fabs`를 쓰는 건 맞지만
   (스텝 수는 크기), `UpdateMove`/`UpdateOffsetMove`의 `target_v`가 항상 `+0.05f`라
   **후진 명령이 전진한다.** 펜 오프셋 보정이 정반대로 작동하므로 6번 없이는 A-3을 못 한다.
7. `pivot` 필드 파싱 (`Segment_t`에 추가) — 이 구간엔 서버가 ALIGN/DRIFT를 안 보낸다.
8. `MOVE.speed_mps` / `TURN.speed_dps` 파싱 + `CMD SET_SPEED`.
   지금 MOVE는 `0.05f`, TURN은 `400 sps`로 하드코딩돼 있다.

> ✅ `current_waypoint_idx` 증가와 스텝 기반 도달 판정은 `77afd1b`에서 **이미 구현됐다.**
> 이전 계획서의 해당 항목은 해소됐다.

### A-2. 측정 항목 — ★ 4cm를 낼 수 있는지가 전체 설계의 전제

펜 오프셋 보정(꼭짓점에서 **후진 4cm → 회전 → 전진 4cm**)은 로봇이 4cm를 정확히
낼 수 있다는 가정 위에 서 있다. **4cm 명령에 6cm를 가는 로봇이면 보정이 오히려 해가
되므로**, 이 측정이 단계 A에서 제일 중요하다.

| # | 항목 | 명령 | 측정 방법 | 합격 기준 (제안) |
|---|---|---|---|---|
| A-a | 직진 거리 | `MOVE 1.0m` | 줄자, 5회 반복 | 오차 ≤ ±3 cm, 편차 ≤ ±2 cm |
| A-b | **미세 직진** | `MOVE 0.04m` | 줄자/버니어, 10회 | **오차 ≤ ±1 cm** ← 못 넘기면 펜 오프셋 설계 재검토 |
| A-c | **미세 후진** | `MOVE -0.04m` | 〃 | **오차 ≤ ±1 cm**, A-b와 대칭일 것 |
| A-d | 제자리 회전 | `TURN +90°` | 각도기/바닥 표식, 5회 | 오차 ≤ ±3° |
| A-e | 회전 중심 이동 | `TURN +90°` | 회전 전후 중심점 편차 | ≤ 2 cm (크면 "제자리 회전"이 아님) |
| A-f | 노즐 응답 | `NOZZLE down/up` | 스톱워치·영상 | 지연 ≤ 0.5 s, 반복 재현 |
| A-g | 속도 반영 | `speed_mps` 0.08 / 0.25 | 1 m 소요시간 | 명령 대비 오차 ≤ 20 % |
| A-h | 하트비트 | `STATUS` | 서버 로그 | 2 초 이내 간격 유지 |

> **A-b / A-c가 핵심이다.** 여기서 오차가 크면 Qt팀에 "펜 오프셋 보정을 로봇 동작으로
> 하는 방식이 성립하지 않는다"고 되돌려줘야 한다 (대안: 노즐을 회전중심에 가깝게
> 재배치하거나, 꼭짓점을 곡선으로 처리).

### A-3. 꼭짓점 동작 단독 시연

위가 다 되면 program 없이 손으로 이 시퀀스를 넣어 본다:

```
NOZZLE down → MOVE 0.5m → NOZZLE up → MOVE -0.04m
→ TURN +90° → MOVE +0.04m → NOZZLE down → MOVE 0.5m → NOZZLE up
```

**합격**: 바닥에 그려진 ㄱ자의 모서리가 뭉개지지 않고, 두 변의 교점이 실제 꼭짓점과
2 cm 이내로 일치.

## 단계 B — 좌표계 정합성 (로봇은 움직이지 않는다)

**가장 짧고, 가장 많이 건너뛰고, 틀리면 그 뒤 전부가 무의미한 단계다.**
theta 부호가 반대면 서버의 `ALIGN`이 반대 방향으로 나가 로봇이 계속 더 틀어지는
쪽으로 돈다 (발산).

### B-0. 준비

1. 카메라·보드 고정 (이후 절대 건드리지 말 것 — 캘리가 무효가 된다)
2. **관리자 창에서 `test` / `1234`로 먼저 로그인** → 그 다음 캘리브레이션 시작
   - 🔴 순서가 반대면 캘리 결과가 세션에만 남고 서버 재시작 시 사라진다
     (`[WARN] 캘리브레이션 수신 - 로그인 사용자 없음`). 나중에 로그인해도 소급 저장 안 됨
3. 계정이 없으면: `python3 tools/seed_user.py --id test --pw 1234`
4. 캘리 완료 후 확인:

```bash
python3 -c "import json;d=json.load(open('config/users.json'));print(d['test'].get('calib') and 'calib 저장됨' or 'calib 없음!')"
```

### B-1. 측정 (로봇을 손으로 옮겨가며 `admin_console` → `/logs`에서 `POSE` 읽기)

| # | 놓는 방법 | 읽는 값 | 합격 기준 |
|---|---|---|---|
| B-a | 보드 원점에 로봇 중심 | `POSE.x, y` | 실측과 ≤ 3 cm |
| B-b | 원점에서 **+x로 1 m** 이동 | `POSE.x` 증가량 | **1.0 ± 0.05** (1000이 나오면 mm/m 환산 버그) |
| B-c | 로봇 정면을 **+x 축**으로 정렬 | `POSE.theta_deg` | **0 ± 5°** |
| B-d | 그 자리에서 **반시계 90°** 회전 | `POSE.theta_deg` | **+90 ± 5°** (−90이 나오면 부호 반전) |
| B-e | 정면을 **−x 축**으로 | `POSE.theta_deg` | **180 또는 −180** (0이 나오면 마커 앞뒤가 뒤집힘) |
| B-f | 필드 네 귀퉁이에 놓기 | `POSE` | 전부 값이 나오는가 = **유효 시야 확인** |

### B-2. 틀렸을 때 어디를 고치나

| 증상 | 원인 | 조치 |
|---|---|---|
| 값이 1000배 | mm/m 환산 | CCTV가 H를 **mm 기준**으로 보내는지 확인 (서버가 ÷1000 함) |
| theta 부호 반대 | 마커 코너 순서 | CCTV `corners`를 **[전좌, 전우, 후우, 후좌]** 순으로 |
| theta가 180° 어긋남 | 마커 부착 방향 | 마커를 돌리거나 corners 순서를 2칸 회전 |
| x/y가 바뀜 | H 행/열 | CCTV 캘리 쪽 확인 |
| 특정 위치에서 POSE 없음 | 시야/검출 실패 | **B-f 결과가 실제 주행 가능 영역이다** |

### B-3. 🔴 이 단계에서 반드시 정하는 값 두 개

1. **유효 주행 영역** (B-f) — 사각형 경로는 이 안에 들어와야 한다. 밖으로 나가면
   pose가 끊겨 `START_DRAW`가 `no_pose`로 대기하거나 주행 중 피드백이 멈춘다.
2. **마커 중심 ↔ 로봇 회전중심 오프셋** — 서버 pose는 마커 4코너 평균이다.
   ArUco 판이 회전중심 바로 위에 없으면 펜 오프셋과 **별개인 오프셋이 하나 더** 생긴다.
   4 cm를 따지는 이상 이것도 재서 기록할 것 (줄자로 충분).

## 단계 C — 서버 알고리즘 드라이런 (로봇 없이)

로봇이 준비되기 전에 **서버가 만드는 PATH가 맞는지**만 따로 검증한다.
단계 A와 병렬로 진행 가능하고, 여기서 나온 PATH 출력이 곧 로봇팀에게 주는
"이렇게 동작해야 한다"는 레퍼런스가 된다.

### C-1. 필요한 도구 (서버팀이 만든다)

| 도구 | 역할 | 현재 |
|---|---|---|
| `robot_sim` | ROBOT 대역: STATUS 하트비트 자동 송신, PATH 수신 출력, READY 자동 송신, ALIGN 적용 시뮬, PATH_DONE 송신, **펜 자취 계산** | ❌ 신규 |
| `draw_test` | QT 대역: `test`/`1234` 로그인 → 사각형 BLUEPRINT(`points`+`paint`+`pen_offset_m`+`program`) → `START_DRAW` → 응답 관찰 | ❌ 신규 (`qt_sim`·`path_test` 재활용) |

> `path_test`는 **접근을 일부러 건너뛰도록** 만들어져 있어(시작점 = 현재 pose)
> 이번 테스트에는 그대로 못 쓴다. 접근을 포함하는 버전이 필요하다.

`robot_sim`이 펜 자취를 계산하면 **로봇 없이도** "펜이 도면 꼭짓점을 정확히 지나는가"를
검증할 수 있다 (Qt팀이 `mp_test`로 한 것과 같은 검증을 서버 쪽에서).

### C-2. 검증 항목

| # | 항목 | 합격 기준 |
|---|---|---|
| C-a | `BLUEPRINT_OK` 회신 | 보낸 개수와 일치 (`points`/`paint`/`program`/`pen_offset_m`) |
| C-b | 접근 PATH | `phase="approach"`, 전부 `paint=false`, 목표가 `points[0]` **그대로**(+d 아님) |
| C-c | 도색 PATH | `phase="draw"`, **Qt가 보낸 program과 바이트 단위로 동일** |
| C-d | 꼭짓점 동작 | 각 꼭짓점에 `NOZZLE up → MOVE -d → TURN → MOVE +d → NOZZLE down`, 전부 `pivot:true` |
| C-e | `pivot` 정렬 차단 | pivot 세그먼트의 READY에 **ALIGN 없이 즉시 GO**, DRIFT도 안 옴 |
| C-f | 펜 자취 | 시뮬된 펜이 도면 꼭짓점을 ≤ 1 mm로 통과, 도색 거리 = 도면 길이 |
| C-g | `paint` 배열 | 도형 사이 이동 구간이 `paint=false`로 나감 |
| C-h | 이탈 복귀 | pose를 옆줄 쪽으로 주입 → **원래 달리던 줄**로 복귀 (옆줄 아님) |
| C-i | 하위호환 | `program` 없이 보내면 서버가 직접 생성 (종전 동작) |

C-h는 이미 단위 검증으로 통과했다(옛 구현 0.10 m → 재계획 안 걸림 / 새 구현 0.40 m →
3번 줄로 복귀). 여기서는 실제 서버를 통해 재확인하는 것.

## 단계 D — 통합 주행 (사용자 1번)

**진입 조건: 단계 A·B·C 전부 통과.**

### D-0. 안전·실무

- 🧯 **ESTOP 즉시 누를 수 있는 위치에 사람 한 명** (관리자 창 `/robot` 또는 Qt)
- 🎨 첫 주행은 **실제 페인트 대신 마커펜/물**로. 노즐 동작만 확인되면 페인트로 전환
- 📏 **사각형 한 변은 최소 40~50 cm.** 펜 오프셋이 4 cm라 10 cm 사각형이면 한 변의 40 %가
  보정 동작이 되어 무엇이 오차인지 구분이 안 된다 (`path_test`의 기본값 10 cm는 부적합)
- 📐 사각형 전체가 **단계 B-f에서 확인한 유효 시야 안에** 들어와야 한다
- 🤖 로봇 시작 위치는 사각형 시작점에서 **일부러 떨어뜨려 놓는다** (접근 단계를 타야 하므로)

### D-1. 실행 순서

```
1. 서버 기동            ./start.sh
2. 관리자 창 로그인      http://<서버IP>:8083  →  test / 1234
3. CCTV 접속 확인        /logs 에서 PEERS {cctv:true}
4. 로봇 접속 확인        PEERS {robot:true} + STATUS 주기 수신
5. 로봇을 시작점 밖에 배치, POSE가 나오는지 확인
6. draw_test 실행       사각형 BLUEPRINT + START_DRAW
7. 관찰                 /logs (tap + 서버 내부 로그)
```

### D-2. 관찰 항목 — 각 단계가 실제로 일어나는가

| # | 무엇을 보나 | 어디서 | 합격 기준 |
|---|---|---|---|
| D-a | `BLUEPRINT_OK` | Qt 대역 로그 | 보낸 값과 일치 |
| D-b | 접근 PATH 전송 | `[srv] 1단계 접근 경로 전송` | 세그먼트 수가 상식적 |
| D-c | **출발 전 정렬** | `[srv] READY(seg=n) 각도오차 …도 - ALIGN 전송` | ALIGN **부호가 맞는가** (양수 = 좌회전) — 로봇이 실제로 오차가 **주는** 쪽으로 도는지 |
| D-d | 정렬 수렴 | 〃 | ALIGN 반복이 `kAlignMaxTries`(4회)에 매번 걸리면 부호 반전 의심 |
| D-e | 접근 도착 | `[srv] 로봇 접근 완료` | 로봇 중심이 `points[0]`에서 ≤ 5 cm |
| D-f | 도색 PATH | `[srv] Qt 동작 시퀀스 사용` | 접근 완료 직후 자동 전송 (Qt 개입 없음) |
| D-g | **각도 피드백** | `[tap] SRV->ROBOT DRIFT` | 로봇을 손으로 살짝 틀었을 때 **부호가 반대로 나오는가** (틀어진 방향의 반대로 보정) |
| D-h | pivot 차단 | `[srv] 꼭짓점 동작 구간 - 정렬 생략하고 GO` | 꼭짓점마다 뜨는가 |
| D-i | 꼭짓점 결과 | 바닥 자국 | 모서리가 호로 뭉개지지 않고 각이 살아있는가 |
| D-j | 이탈 복귀 | 로봇을 손으로 20~40 cm 밀어보기 | `[srv] 경로 이탈 …m (구간 n) - 복귀 PATH 전송` |
| D-k | 완료 | `DRAW_DONE` | Qt 대역에 1회 도착 |
| D-l | 최종 정확도 | 그려진 사각형 실측 | 한 변 오차 ≤ 3 cm, 직각 오차 ≤ 5° |

### D-3. 각도 피드백 정확성을 어떻게 판정하나 (사용자 관심사)

말로만 "맞는 것 같다"가 되지 않게, **부호 검증을 따로 떼서** 한다.

**정적 검증 (D-c 전에, 로봇 정지 상태)**

1. 로봇을 목표 방위에서 **일부러 반시계로 +10° 틀어** 놓는다
2. `READY`를 한 번 보내게 한다 (`robot_sim`이면 바로, 실로봇이면 그 세그먼트에서)
3. 서버 로그의 `ALIGN` 값을 본다 → **약 −10 이어야 한다** (우회전으로 되돌림)
4. 시계로 −10° 틀어놓으면 **약 +10**

**동적 검증 (직진 중)**

1. 직진 중 로봇을 손으로 살짝 반시계로 틀기
2. `DRIFT` 값이 **음수**로 나오는지 (= 우회전 보정 필요)
3. 로봇이 실제로 **오차가 줄어드는 쪽**으로 도는지

> ⚠️ 3번이 반대면 로봇 쪽 부호 해석이 반대다. 이때 **서버 부호를 뒤집어 맞추지 말 것** —
> 프로토콜 규약(양수 = 좌회전)은 `ALIGN`/`DRIFT`/`TURN`이 전부 공유하므로,
> 한 곳만 뒤집으면 다른 곳이 깨진다. 로봇 쪽에서 맞춘다.
>
> 🔴 `77afd1b` 기준으로 **동적 검증은 반드시 실패한다** — DRIFT 부호가 실제로 반대다
> (0절 3번). 단계 A-1 §3을 먼저 고치고 오면 이 절차는 "고쳤는지 확인"용이 된다.
> ALIGN(정적)은 부호가 맞으므로 통과할 것이고, **정적은 통과인데 동적만 실패하는
> 이 조합 자체가 진단 결과**다.
