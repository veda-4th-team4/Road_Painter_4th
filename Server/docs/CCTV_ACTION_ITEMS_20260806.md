## C-0. 🔴 선행 확인 — 4채널 카메라에서 앱이 어떻게 도는가

**이 문서에서 서버팀이 답할 수 없는 유일한 항목이고, 나머지 설계가 여기 달려 있다.**

현재 앱은 **Hanwha OpenSDK 5.00 `.cap` 앱**으로 **카메라 안에서** 돈다
(`CCTV/README.md`). 대상 기기는 **PNO-A9081RG — 단일 채널 카메라**다.
프레임도 RTSP를 당겨오는 게 아니라 SDK가 주는 **raw NV12 버퍼**를 직접 받는다.

```
PNO-A9081RG / cctv_app.cap
  ├─ raw NV12 1920×1080 프레임에서 ArUco 검출
  └─ TLS HELLO/POS ──────────────> 중앙 서버 :9000
```

새 카메라는 **PNM-C16083RVQ — 4채널(멀티센서) 카메라**다. 그래서 물어야 한다:

| 질문 | 왜 중요한가 |
|---|---|
| **(a) 앱 인스턴스가 몇 개 뜨는가?** 채널당 하나인가, 전체에 하나인가 | 하나면 앱이 채널을 골라야 하고(C-2 필요), 채널당 하나면 각 인스턴스가 자기 채널 번호만 알면 된다(C-2 불필요, C-1만) |
| **(b) 한 앱에서 4개 센서 프레임에 접근할 수 있는가?** SDK에 채널/센서 인덱스 인자가 있는가 | 없으면 "한 앱 = 한 채널"이 강제되고, `SELECT_CHANNEL`은 앱이 아니라 **서버가 어느 인스턴스와 말할지 고르는 문제**가 된다 |
| **(c) 4개 인스턴스가 각각 서버에 접속하면 서버가 구분할 수 있는가?** | 현재 서버는 role별 세션이 **하나**다. `HELLO{"role":"CCTV"}`가 4개 오면 마지막 것이 이전 것을 대체한다 — 이 경우 **서버 수정이 추가로 필요하다** |

> 참고: 현재 코드에서 SDK 호출에 채널 인자로 보이는 것은
> `opensdk_getPtzAttr(0, ...)`(`aruco_detector_cv.cpp:1447`)의 첫 인자 `0` 정도다.
> 이게 채널 인덱스인지 PTZ 프리셋 인덱스인지 저장소의 코드만으로는 알 수 없다
> (SDK 헤더가 저장소에 없다).

**답을 알려주시면 C-2 설계를 구체적으로 다시 드리겠습니다.** (c)가 "구분 못 한다"로
나오면 서버 쪽 세션 관리도 같이 바꿔야 하므로 특히 중요하다.

아래 C-1·C-3은 **어느 답이 나오든 필요한 작업**이라 먼저 진행해도 된다.

### 📌 2026-08-07 실측 추가 — 앱은 아직 PNM으로 안 넘어왔다

서버 로그에서 확인됐다:

```
[접속] CCTV 192.168.0.12:35890
```

`.12`는 **PNO-A9081R(단일채널)**이고 `.13`이 PNM-C16083RVQ(4채널)다
(`relay/README.md`의 MAC 실측표 참고 — 공유기 장치 목록은 PNM을 `.12`로

`.cap` 앱을 PNM에 올려본 적이 없다는 뜻이다 (= 아래 "확인 요청 사항" 2번의 답).

그래서 2026-08-07 현재 시스템은 **영상과 측위가 서로 다른 카메라를 보고 있다**:

| 계층 | 카메라 | 상태 |
|---|---|---|
| 영상 (RTSP, Qt 화면) | `.13` PNM 4채널 | 동작 중 |
| 마커 검출·캘리 (`role=CCTV`) | `.12` PNO 1채널 | 이 문서 미착수 |

🔴 **이대로면 채널 2·3·4에서는 로봇을 잡을 수 없다.** 화면은 4채널이 나오는데
POS는 PNO 한 대에서만 오기 때문이다. C-0의 (a)(b)(c)를 확인하는 것이
여전히 **가장 급한 항목**이다.

## C-1. `POS`에 `ch` 싣기 (P0)

```cpp
// central_tls_sender.cpp:74-78 — 현재. ch 가 없다.
int central_tls_sender_send_pos(const float c[4][2]) {
    if (!c) return -1; advance(); if (state!=ONLINE) return -1; char j[320];
    int n=snprintf(j,sizeof(j),
        "{\"type\":\"POS\",\"seq\":%lu,\"payload\":{\"corners\":[[%.2f,%.2f],...]}}",
        seq++, ...);
    return (n>0 && n<(int)sizeof(j)) ? write_line(j) : -1;
}
```

**서버는 `ch`가 없으면 채널 1로 읽는다.** 그래서 지금은 어느 채널에서 본
마커든 전부 채널 1의 캘리브레이션으로 좌표 변환된다 — **에러 없이 조용히
틀린 좌표가 나온다.**

### 요청

`ch` 인자를 받아 payload에 싣는다. 시그니처를 바꾸는 게 부담이면 별도 setter로
현재 채널을 들고 있어도 된다.

```cpp
// 예: 채널을 인자로 받는 형태
int central_tls_sender_send_pos(int ch, const float c[4][2]) {
    if (!c) return -1; advance(); if (state!=ONLINE) return -1; char j[352];
    int n=snprintf(j,sizeof(j),
        "{\"type\":\"POS\",\"seq\":%lu,\"payload\":{\"ch\":%d,"
        "\"corners\":[[%.2f,%.2f],[%.2f,%.2f],[%.2f,%.2f],[%.2f,%.2f]]}}",
        seq++, ch, c[0][0],c[0][1], c[1][0],c[1][1], c[2][0],c[2][1], c[3][0],c[3][1]);
    return (n>0 && n<(int)sizeof(j)) ? write_line(j) : -1;
}
```

- ⚠️ **버퍼를 같이 늘릴 것.** 현재 `char j[320]`은 여유가 크지 않다.
  `"ch":N,`가 붙으면 최악 8바이트가 늘고, `snprintf`가 잘리면 `n >= sizeof(j)`라
  **전송이 조용히 실패한다**(반환값 -1). 위 예시는 352로 잡았다.
- 호출부는 `aruco_detector_cv.cpp:380` 한 곳뿐이다.
- 🔴 **틀린 채널을 싣는 것은 안 싣는 것보다 나쁘다.** 서버는 활성 채널이 아닌
  `POS`를 **버리므로**, 채널을 잘못 실으면 로봇이 화면에서 사라진다. 확신이
  없으면 차라리 싣지 말 것(그러면 종전대로 채널 1로 동작한다).

### 서버가 어떻게 반응하는지

```
[WARN] POS 채널 3 무시 - 활성 채널은 1 다 (CCTV가 다른 채널을 보고 있거나 ch를 잘못 싣는 중)
```

이 로그가 반복되면 채널이 어긋난 것이다. `POS`는 15~30Hz라 로그가 덮이지 않도록
**채널이 바뀔 때만 한 줄** 남게 해뒀다.

## C-2. `SELECT_CHANNEL` 수신 처리 (P0, C-0 이후 설계 확정)

```cpp
// central_tls_sender.cpp:90 — 현재. 문자열 하나만 본다.
bool ok = strstr(read_buf,"\"type\":\"CMD\"") &&
          strstr(read_buf,"\"cmd\":\"CALIB_START\"");
if(!ok) return 0;
snprintf(out,(size_t)out_len,"CALIB_START"); return 1;
```

`CALIB_START` 이외의 모든 CMD는 **파싱 단계에서 버려진다.** 서버가
`SELECT_CHANNEL`을 중계해도 앱에 도달하지 못한다.

### 요청

명령 이름과 `ch` 값을 뽑아 호출부로 넘긴다. 인자 있는 명령을 파싱하는 패턴은
이미 앱 안에 있다 — `handle_camera_height()`(`aruco_detector_cv.cpp:529`)가
`sscanf`로 값을 읽는 방식이다. 같은 방식으로 맞추면 된다.

```cpp
// central_tls_sender.cpp — poll_command 안, 기존 CALIB_START 판정 자리
if (strstr(read_buf, "\"type\":\"CMD\"")) {
    if (strstr(read_buf, "\"cmd\":\"CALIB_START\"")) {
        snprintf(out, (size_t)out_len, "CALIB_START");
        // consume 처리 후 return 1;
    }
    const char* p = strstr(read_buf, "\"cmd\":\"SELECT_CHANNEL\"");
    if (p) {
        int ch = 0;
        const char* q = strstr(read_buf, "\"ch\":");
        if (q && sscanf(q + 5, "%d", &ch) == 1 && ch >= 1 && ch <= 8)
            snprintf(out, (size_t)out_len, "SELECT_CHANNEL %d", ch);
        else
            snprintf(out, (size_t)out_len, "SELECT_CHANNEL_BAD");
        // consume 처리 후 return 1;
    }
}
```

⚠️ **`used`/`memmove`로 줄을 소비하는 처리는 어느 분기로 빠지든 반드시 거칠 것.**
지금 코드는 `ok` 판정 뒤에 한 번만 소비하는데, 분기를 늘리면서 `return`이
소비 전으로 새면 **같은 줄을 무한히 다시 읽는다.**

호출부(`aruco_detector_cv.cpp:1828`)는 이렇게 늘어난다:

```cpp
while (central_tls_sender_poll_command(cmd, sizeof(cmd))) {
    if (strcmp(cmd, "CALIB_START") == 0) {
        cmd_calib_start();
    } else if (strncmp(cmd, "SELECT_CHANNEL ", 15) == 0) {
        int ch = atoi(cmd + 15);
        cmd_select_channel(ch);   // ← C-0 결과에 따라 내용이 결정된다
    }
}
```

`cmd_select_channel(ch)`가 실제로 무엇을 하는지는 **C-0의 답에 달려 있다**:

| C-0 결과 | `cmd_select_channel(ch)` 의 내용 |
|---|---|
| 한 앱이 4센서 접근 가능 | 검출 대상 프레임 소스를 그 센서로 전환 |
| 채널당 앱 인스턴스 | 자기 채널이면 무시(이미 그 채널), 아니면 무시. **사실상 할 일 없음** |
| 채널 하나만 가능 | 앱에서는 못 한다 — 서버/대시보드가 인스턴스를 고르는 구조로 가야 함 |

## C-3. `H_MATRIX`에 `ch` 싣기 (P0)

```cpp
// aruco_detector_cv.cpp:856
int rc = central_tls_sender_send_typed("H_MATRIX", p);
```

payload `p`에 `ch`가 없으면 **서버가 전부 채널 1 슬롯에 저장한다.**
4채널을 차례로 캘리브레이션해도 **마지막 하나만 남고 앞의 셋은 덮인다** —
이것도 에러 없이 조용히 일어난다.

### 요청

payload를 만들 때 최상위에 `"ch":N`을 추가한다. 서버는 세 가지 스키마를 모두
받으며(`중첩 calib` / `평면 번들` / `레거시 H`), **`ch`는 어느 스키마든 payload
최상위에서 읽는다.**

```
{"type":"H_MATRIX","seq":12,"payload":{"ch":2,"calib":{...}}}
```

- 평면 스키마(payload 자체가 번들)면 `ch`가 번들 안에 남는데, 서버는 이를
  `calib_id`처럼 **손대지 않는 메타데이터로 보존**한다 — 저장된 번들만 봐도
  어느 채널 것인지 알 수 있어 오히려 낫다.
- 서버 로그로 확인할 수 있다:
  ```
  [INFO] 캘리브레이션 수신 [채널 2] (평면 번들, mm->m 정규화, ...) - 사용자 'xxx' + 전역 슬롯에 영속 저장
  ```
  **`[채널 1]`만 계속 찍히면 `ch`가 안 실린 것이다.**

## C-4. 채널별 캘리브레이션 상태 유지 (P1)

`calib_view_store.*`가 현재 캘리브레이션 결과를 하나만 들고 있다. 채널을 바꿔가며
캘리브레이션하면 앱 쪽 상태가 계속 덮인다.

서버는 채널별로 따로 저장하므로 **데이터 유실은 없지만**, 앱/대시보드 화면에
"지금 몇 번 채널을 보정 중인지"가 안 나오면 조작자가 헷갈린다. 관리자 대시보드
쪽은 이미 채널 선택 UI가 들어가 있다(`Server/admin_console/cctv.py`의
`set_calib_channel()` → `SELECT_CHANNEL` 송신).

C-0/C-2가 정리된 뒤에 같이 보는 것이 낫다.

## 부록 A. 서버가 이미 하고 있는 일 (CCTV팀이 안 해도 되는 것)

| 항목 | 서버 동작 |
|---|---|

| 채널별 캘리 저장 | 계정(`users.json`) + 전역(`calib_latest.json`) 둘 다 채널별 맵. 조회는 계정 → 없으면 전역 |
| 옛 형식 마이그레이션 | 채널 맵이 아닌 예전 단일 번들은 **채널 1로 읽는다.** 현장 파일을 손댈 필요 없다 |
| 비활성 채널 POS 폐기 | 활성 채널이 아닌 `POS`는 게이트를 태우기 전에 버린다 |
| 이상치 게이트 | 각도 변화 `3° + 40°/s × 경과시간` 초과 프레임 폐기(연속 5회 초과 시 재동기) |
| POS 수신 요약 | 10초마다 `수신/채택(Hz)/파싱실패/이상치폐기` 한 줄 |

## 부록 B. 하위호환 — 지금 당장 안 고쳐도 깨지지 않는다

`ch`는 **전부 선택 필드**다. 안 실으면 서버가 1로 읽으므로,
**단일 채널 카메라(PNO)와 지금 코드는 v0.3과 100% 동일하게 동작한다.**

즉 이 문서의 작업은 "고장 난 것을 고치는 것"이 아니라 **"4채널을 쓰려면 필요한 것"**이다.
PNO로 계속 가는 동안에는 급하지 않다.

⚠️ 단, **PNM(4채널)으로 전환하는 순간 C-1·C-3이 없으면 4채널이 동작하지 않는다.**
채널 4개를 캘리브레이션해도 서버에는 채널 1 하나만 남기 때문이다.

## 부록 C. 검증 방법 (카메라 없이)

서버 쪽 도구로 확인할 수 있다.

```bash
cd Server
make calib_channel_test && ./tools/calib_channel_test   # 채널별 저장/폴백 회귀 테스트
```

실제 링크 확인은 서버를 띄우고 로그를 본다:

```
[INFO] 활성 채널 2 로 전환 -> CCTV 중계 (캘리브레이션 있음)
[INFO] 캘리브레이션 수신 [채널 2] (...)
[INFO] POS 10초 요약 - 수신 14, 채택 14 (1.3Hz), 파싱실패 0, 이상치폐기 0
```

- `SELECT_CHANNEL` 중계 후에도 `POS`가 옛 채널로 오면 → C-2 미반영
- `[채널 1]`만 찍히면 → C-3 미반영
- `POS 채널 N 무시` 가 반복되면 → 활성 채널과 CCTV가 보는 채널이 어긋남
