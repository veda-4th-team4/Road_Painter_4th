## 0. 요약

실기 시험에서 **Qt의 top-view가 바닥이 아니라 마커 평면으로 전환됐습니다.**
바닥에 마커를 대보며 눈으로 확인한 결과입니다.

Qt는 번들의 `H_floor`만 읽습니다(`H` → `H_floor` 순, `H_marker`는 읽지 않음 —
코드 확인). 그렇다면 **Qt가 받은 번들의 `H_floor` 칸에 마커 평면이 들어 있었다**는
뜻입니다.

서버 코드에는 두 필드를 바꾸거나 섞는 경로가 없습니다(아래 §3). 그래서 카메라
쪽 두 가지를 확인 부탁드립니다.

---

## 1. ✅ 확인 요청 1 — 앵커 floor H가 없는 렌즈에서 `HG_QUERY`는 무엇을 돌려줍니까?

문제의 렌즈(CH2)에 대해 카메라가 이렇게 답하고 있습니다:

```
MARKER_PLANE {"type":"MARKER_PLANE","ch":2,"ready":false,"height_mm":160.0,"reason":…}
```

**CH2에는 앵커 기반 floor H가 없습니다.** (CH1은 `ready:true`,
`camera_z_mm:1650`, `derived_z_mm:1631.1`)

그러면 CH2에서 카메라가 가진 유일한 실측 호모그래피는 **오도메트리가 구한
마커 평면**입니다.

여기가 문제가 되는 이유는 관리자 창(`cctv.py`)의 자동 전송 경로입니다:

```python
# HG 응답을 받으면
calib_cache_h(H, ch)
# → push_calib_to_server()
bundle = {"version": 1, "H_floor": H}     # ← HG의 H를 무조건 H_floor로 라벨링
```

**`HG`가 무엇을 돌려주든 `H_floor`라는 이름으로 서버에 올라가고, 서버는 그걸
그대로 Qt에 중계합니다.** CH2처럼 floor H가 없는 렌즈에서 `HG_QUERY`가 오도메트리
측정 H(=마커 평면)를 돌려준다면, 관측된 증상이 그대로 설명됩니다.

> **질문**: `HG_QUERY`/`HG`가 돌려주는 H는 항상 **바닥 평면**입니까?
> 앵커 floor H가 없는 렌즈에서는 무엇이 나옵니까 — 오도메트리 측정 H입니까,
> 아니면 `available:false`입니까?
>
> 만약 측정 H가 나온다면 관리자 창 쪽에서 막겠습니다(어느 평면인지 표시하는
> 필드를 `HG` 응답에 하나 넣어주시면 확실합니다).

## 2. ✅ 확인 요청 2 — 측정값이 들어가는 슬롯이 `H_marker`가 맞습니까?

wire §6과 [`ROBOT_ODOMETRY_HOMOGRAPHY.md`](ROBOT_ODOMETRY_HOMOGRAPHY.md) §6-2/§6-3의
규약은 이렇습니다:

```
H_marker : 이 방식이 **직접 측정**한 값
H_floor  : 카메라가 역산 (H_marker + K 분해 + 마커/카메라 높이)
           floor = nadir + (marker − nadir) / (1 − h/Zc)      (확대)
```

받은 번들(`calib_id: odom-1786610340124`)을 수치로 검산했습니다:

```
H_floor = nadir + 1.10296 · (H_marker − nadir)     닮음 이탈 0.00mm
→ 마커높이 160mm 기준 Zc = 1714mm
```

**관계식 자체는 규약과 정확히 일치합니다.** 다만 이 관계는 아래 두 경우가
**수치적으로 완전히 동일**해서, 번들만 봐서는 구분할 수 없습니다:

| | `H_marker` 칸 | `H_floor` 칸 |
|---|---|---|
| (A) 규약대로 | 측정 (마커면) | 확대 역산 (바닥) |
| (B) 뒤바뀜 | 축소 역산 | **측정 (마커면)** |

둘 다 `H_floor = nadir + 1.103·(H_marker − nadir)`을 만족합니다. 실기 관측은
(B)를 가리킵니다.

> **질문**: `SendCalibBundle()`에서 오도메트리 주행으로 **측정한** 행렬이
> 들어가는 필드가 `H_marker`가 맞습니까? 역산한 쪽이 `H_floor`입니까?

### 참고 — `cmp_scale: 0.0`

같은 번들에 `cmp_scale`이 `0.0`으로 실려 왔습니다. 회신 §6에서 "1.000에서
벗어나면 그게 유일한 신호"라고 하신 값인데, **계산이 안 된 상태**입니다.
이게 정상 동작했다면 이번 문제가 그 자리에서 드러났을 가능성이 큽니다.

CH2에 앵커 floor H가 없어서(§1) 비교 대상이 없었던 것으로 짐작하는데,
맞습니까? 그렇다면 `cmp_scale`을 못 구하는 상황 자체를 번들에 표시해주시면
(예: `cmp_scale: null` + `cmp_scale_reason`) 서버가 경고로 남기겠습니다.

## 3. 서버·관리자창 쪽에서 확인한 것 (참고)

의심 범위를 좁히려고 저희 쪽 경로를 먼저 다 뒤졌습니다. **필드를 바꾸거나
섞는 코드는 없었습니다**:

| 지점 | 동작 |
|---|---|
| Qt `configureTopViewCalib` | `H` → 없으면 `H_floor`. **`H_marker`는 읽지 않음** |
| 서버 `aliasFloorKey` | `H` → `H_floor` 한 방향 별칭뿐 |
| 서버 `bundleToMm` | `H`/`H_floor`/`H_marker`를 같은 배율로 곱함 |
| 서버 `handleHMatrix` | 번들을 값 변경 없이 저장·중계 |
| 관리자창 `ODOM_DONE` | 화면 표시만 — 서버로 아무것도 안 보냄 |

다만 **서버가 라벨을 검증하지 않는다**는 점은 저희 취약점이 맞습니다.
`H_floor`라고 오면 그대로 믿습니다.

저희 쪽에서 같이 고친 것도 있습니다 — 관리자 창이 `CALIB_K_QUERY`(단순 조회)
응답만으로도 캐시된 번들을 서버에 밀어 넣던 문제입니다. 화면을 새로 열
때마다 서버의 캘리 슬롯이 덮이고 Qt까지 중계됐습니다. 조회가 전송을 유발하지
않도록 수정했습니다.
