## 0. 요약

개정판의 8점·폐합·`H_marker` 구분·정지 판정 이관까지 전부 동의합니다. 그대로 갑니다.

**한 가지 구조를 확정했습니다: 캡처한 대응점은 카메라가 보관하고, `CALIB_DONE` 을
받으면 카메라가 직접 피팅해 `H_MATRIX` 를 서버로 보냅니다.** 개정판 §4 는 "CCTV가
`findHomography` 를 돌리고 관리자창에 띄운다"까지만 적혀 있어 8쌍의 보관 주체와
관리자창까지의 경로가 비어 있었는데, 이 방식이면 그 구간이 닫힙니다. 이유는 §3.

**반드시 같이 읽어야 할 것은 §4 입니다** — 재투영 잔차와 폐합오차 둘 다
**균일 스케일 오차를 구조적으로 못 잡습니다.** SRS 금지조항이 지목한 1~5% 오픈루프
오차가 정확히 그 유형이라, 개정판이 마련한 두 검증 장치로는 그걸 검출할 수 없습니다.

## 1. §6 질문에 대한 답변

### 1-1. "로봇이 멈췄다"를 어떤 기준으로 판정할지

```
CALIB_CAPTURE 도착 시각 T 를 기록
 → t_capture 가 T 이후인 프레임만 사용 (그 전 프레임은 전부 폐기)
 → 연속 5프레임의 마커 중심 표준편차 ≤ 2 px 이면 정지로 판정
 → 그 N프레임의 평균을 pixel_uv 로 채택
 → T + 10 s 까지 판정 못 하면 실패 (CALIB_FAIL)
```

- **`t_capture` 필터가 핵심**입니다. `CAM_POSE` 에 촬영 시각이 실려 있어서, 요청이
  도착하기 전에 촬영된(=이동 중일 수 있는) 프레임을 정확히 걸러낼 수 있습니다.
  이게 없으면 이동 중 프레임이 평균에 섞여도 아무도 모릅니다.
- 임계값 2 px 은 현재 렌즈·거리 기준 잠정값입니다. 실측 후 조정하겠습니다.
- 소요 시간은 **검출 주기에 따라 2~20초**로 변합니다. 지금 CH2 단독이면 duty 60% 라
  빠르지만, 다른 채널을 켜면 거버너가 duty 를 나눠 4배까지 느려집니다. 서버가 고정
  대기를 세지 않기로 한 개정판 §3-1 의 판단이 이 때문에 맞습니다.
- `spread_px` 를 ack 에 같이 싣겠습니다. 나중에 잔차 표에서 튀는 점이 나왔을 때
  "그 점은 원래 흔들렸다"를 대조할 수 있습니다.

### 1-2. 실패 사유 정의

| reason | 뜻 | 서버 쪽 처리 제안 |
|---|---|---|
| `marker_not_found` | 그 지점에서 대상 마커가 안 보임 | 재시도 또는 중단 |
| `not_settled` | 제한 시간 안에 정지 판정 실패(계속 흔들림) | 재시도 |
| `unmappable` | **검출은 됐는데 왜곡보정이 수렴하지 않음** | 그 지점 배치를 바꿔야 함 |
| `no_intrinsics` | 그 렌즈에 K/dist 없음 | 세션 시작 자체를 거부 |
| `session_conflict` | 다른 캘리 세션(정적 앵커/K)이 열려 있음 | 세션 시작 거부 |
| `fit_failed` | `findHomography` 실패(점들이 일직선이거나 뭉침) | 실패 종료 |
| `too_few_points` | 유효 대응점 4개 미만 | 실패 종료 |

**`unmappable` 은 개정판에 없던 케이스라 따로 짚습니다.** 이 렌즈는 왜곡이 커서
(`k3 = -7.98`) 화면 바깥 약 15% 에서 왜곡보정이 발산합니다. 마커가 **보이는데도 쓸 수
없는** 상태가 존재하고, 운영자가 할 일이 "가린 것 치우기"가 아니라 "사각형을 화면
안쪽으로 옮기기"라 구분이 필요합니다. 카메라에는 이미 같은 개념(`unusable_ids`)이
정적 앵커 쪽에 있습니다.

> 실무 영향: 900×600 사각형의 꼭짓점이 이 영역에 걸릴 수 있습니다. 첫 주행 전에
> 사각형이 화면 중앙 85% 안에 들어오는지 확인하시길 권합니다.

### 1-3. 관리자창 UI

호모그래피 탭을 서브탭으로 나눴습니다(2026-08-12 배포 완료).

```
호모그래피 탭
├ [ floor ]     기존 체커보드/앵커 방식 — H_floor 측정
│               1. 상태 · 2. 앵커/마커평면 · 3. 저장 · 4. 서버 송신
└ [ Odometry ]  로봇 주행 방식 — H_marker 측정 (지금은 자리만)
                설명 · 서버 송신
```

- 기존 "계산" 탭을 **`floor`** 로 개명했습니다 — 두 탭의 산출물이 다르다는 걸
  이름에서 드러내기 위해서입니다(`H_floor` vs `H_marker`).
- 잔차(§2-1)·폐합오차(§2-3)·두 방식 비교(§4-2) 표시는 주행 캘리 구현과 함께 붙입니다.
- §4-2 의 조작자 입력(마커 높이, 카메라 높이)은 기존 `MARKER_HEIGHT` /
  `camera_z_measured_mm` 필드를 그대로 재활용합니다.

### 1-4. 두 탭의 `H_MATRIX` 번들 형식 동일성

**사람이 지키는 규칙이 아니라 구조로 막았습니다.** 두 서브탭의 [서버로 전송]이
**같은 조립 함수 하나**를 호출하고 출력 위치만 다릅니다. 형식이 갈라질 수 없습니다.

배경: 이 파일에는 조립 함수가 이미 둘(평면 스키마 / 레거시 중첩 스키마) 있었고,
2026-08-12 에 `coord_mode` 버그를 **양쪽에 똑같이 두 번** 고쳐야 했습니다. 서브탭마다
복사했으면 네 벌이 됐을 겁니다.

향후(주행 캘리 구현 시)에는 **조립 자체를 카메라로 옮길 예정**입니다 — 카메라가
`H_MATRIX` 를 직접 보내는 구조(§3)라 어차피 카메라에 조립기가 생깁니다. 그때
관리자창은 미리보기 + 전송 트리거로 내려갑니다.

## 2. 인터페이스 — 서버팀 확정/작업 요청

### 2-1. `pixel_uv` 가 raw 인지 왜곡보정 후인지 명시 필요

개정판 §3 은 *"평소 POS 로 올리는 마커 중심 픽셀과 같은 정의"* 라고 했는데, **POS 가
보내는 건 raw 픽셀**입니다(서버가 자체 undistort). 반면 번들의 `coord_mode` 는
`undistort` 라 **피팅 입력은 보정된 픽셀**이어야 합니다.

**제안**: ack 의 `pixel_uv` 는 **raw** 로 싣고(POS 와 정의 통일, 서버의 폐합오차
로깅도 raw 기준), 왜곡보정과 피팅은 카메라가 내부에서 수행. 번들은 그대로
`coord_mode:"undistort"`. 이견 없으시면 이대로 진행하겠습니다.

### 2-2. 카메라 중앙링크가 `CALIB_CAPTURE` / `CALIB_DONE` 을 아직 모릅니다

현재 카메라가 TLS 9000 에서 인식하는 명령은 **두 개뿐**입니다.

```
CALIB_START
SELECT_CHANNEL <n>
```

파싱 추가는 CCTV 쪽 작업입니다(§3 에 포함). 서버팀에는 **메시지 형식 확정**만
요청드립니다 — 개정판 §3-1 의 JSON 그대로면 됩니다.

### 2-3. `request_id` 왕복 경로가 없습니다

카메라가 서버로 보내는 기존 메시지(`POS`, `H_MATRIX`)에 `request_id` 를 되돌리는
필드가 없습니다. `CALIB_CAPTURE_OK` 와 최종 `H_MATRIX` 에 실으려면 카메라 쪽 송신부에
추가해야 합니다. 하겠습니다 — 서버가 그 값을 **세션 매칭에 실제로 쓰는지**만
확인 부탁드립니다(로그용이면 형식만 맞추면 됩니다).

### 2-4. 채널 번호 규약

개정판 예시가 `"ch":2` 입니다. 와이어는 1-based, 카메라 내부는 0-based 이고 카메라가
변환합니다. **인바운드(`CALIB_CAPTURE`)도 1-based 로 보내주시면** 기존 `SELECT_CHANNEL`
과 같은 규약이 되어 깔끔합니다.

> 이 프로젝트에서 이미 한 번 사고가 났던 지점입니다 — POS 의 ch 를 0-based 로
> 내보내다가 서버의 active-channel 게이트에서 CH1 이 통째로 버려졌습니다(2026-08-11).

### 2-5. 카메라는 `m` / `n` 을 모릅니다

`CALIB_START{m_cm, n_cm}` 는 서버가 받고, 카메라에는 지점별 `world_xy_mm` 만 옵니다.
번들의 `origin_mm` / `canvas_mm` 을 채우려면 받은 9점의 바운딩 박스로 역산해야 합니다.

**제안**: `CALIB_DONE` 에 `m_mm` / `n_mm` 를 실어주세요. 역산도 가능하지만
(min/max → `(0,0)~(900,600)`), 명시하는 쪽이 확실합니다.

### 2-6. 동시 세션 금지

같은 렌즈에서 주행 캘리와 정적 앵커 캘리(`CALIB_START` 기존 방식) 또는 K/dist 세션이
동시에 열리면 **한 렌즈의 프레임을 두 수집기가 나눠 가져 양쪽 다 굶습니다.** 카메라가
거부하도록 하겠습니다(기존 `StartFit()` 이 K 세션을 거부하는 것과 같은 가드).
서버 쪽에서도 세션 중복 요청을 막아주시면 좋습니다.

## 3. CCTV가 만들 것

### 3-1. 캡처 보관 + 피팅 (카메라)

```
CALIB_CAPTURE  → 정지 판정(§1-1) → 픽셀 평균 → {point_index, world_xy_mm, pixel_uv} 내부 저장
CALIB_DONE     → 유효 8점으로 findHomography + LOO → H_marker 산출 → H_MATRIX 전송
```

기존 코드를 거의 그대로 씁니다.

| 필요한 것 | 재사용 |
|---|---|
| 최소제곱 피팅 | `FitSubset()` — RANSAC 아님(잔차 재현성 때문) |
| **LOO 잔차 표** | `FinishFit()` — 점마다 in-sample / leave-one-out 두 값 |
| 비유한·특이 행렬 거부 | `Set()` 게이트 |
| 왜곡보정 | `PreparePixel()` |
| 결과 보고 | `HG` / `HG_FIT` / `HG_FIT_PT` (관리자창이 이미 받는 메시지) |

**새로 만드는 건 수집 버퍼 하나**입니다. 기존 앵커 테이블은 중복 id 를 거부하는데
(정적 앵커에선 정당한 방어) 주행 방식은 같은 마커 id 가 9번 나오므로 별도 버퍼를 둡니다.

> 참고 — 8점이면 카메라의 LOO 기준(`유효 5점 이상`, `8점 미만은 advisory`)을 만족해
> **advisory 없는 정식 LOO 잔차**가 나옵니다. 개정판 §2-1 이 기대한 "품질 지표"가
> 재투영 잔차보다 한 단계 강한 형태로 이미 구현돼 있습니다.

### 3-2. 저장 구조 — `H_marker` 슬롯 신설

```
H_floor           앵커 실측 (floor 탭)           — 저장
H_marker (파생)    H_floor 를 K 로 분해            — 필요할 때 계산
H_marker (측정)    오도메트리 주행                  — 저장 (신설)
```

측정값을 그대로 보관합니다. 개정판 §4-1 대로 **시차 보정을 또 걸면 안 되기** 때문에,
기존 슬롯에 넣으면 카메라가 그걸 바닥으로 보고 이중 보정을 겁니다.

번들의 `H_floor` 는 §4-2 의 역산으로 채웁니다. 필요한 값(마커 높이, 카메라 높이,
나디르)은 카메라가 이미 다 갖고 있습니다.

**로봇 측위에 어느 쪽을 쓸지는 운영자가 명시적으로 고릅니다. 기본값은 파생(체커보드)
쪽입니다** — 주행 방식은 아직 스케일 오차를 검증할 수단이 없어서(§4), 검증된 쪽을
기본으로 두고 의도적으로 전환하게 하는 편이 안전합니다. 전환 상태는 `/status` 에
남깁니다.

### 3-3. 마커 높이 변경 감지

측정 `H_marker` 는 **잴 당시의 마커 높이가 이미 녹아 있습니다.** 마커를 다시 달거나
로봇을 바꾸면 조용히 틀려지고, 카메라는 그걸 알 방법이 없습니다.

카메라에 이미 같은 성격의 장치가 있습니다(H 피팅 후 K 가 바뀌면 "다시 확인하라"고
표시하되 버리지는 않음). 마커 높이가 바뀌면 측정 `H_marker` 에 동일한 stale 표시를
하겠습니다. 안 그러면 이 방식의 장점("높이를 정확히 몰라도 된다")이 그대로 함정이
됩니다.

## 4. ⚠ 검증의 한계 — 잔차도 폐합오차도 스케일 오차를 못 잡습니다

개정판 §2-1 은 재투영 잔차를 *"이 방식의 유일한 자체 검증 수단"*, §2-3 은 폐합오차를
*"얼마나 믿을 만한지 재는 유일한 직접 측정값"* 이라고 합니다. **둘 다 중요한 맹점이
있습니다.**

**호모그래피는 아핀 변환을 완전히 포함합니다.** 그래서 오도메트리가 아래처럼 틀리면
잔차가 **정확히 0** 으로 나오면서 좌표는 틀립니다.

| 오도메트리 오차 | 재투영 잔차 | 폐합오차 |
|---|---|---|
| **균일 스케일 3%** (m·n 둘 다) | ❌ 완전 흡수 | ❌ 0 — 네 변 모두 똑같이 짧으면 제자리로 정확히 복귀 |
| m 과 n 의 스케일이 다름 | ❌ 흡수(아핀 신축) | ❌ |
| 회전이 90° 가 아니라 88° | ❌ 흡수(전단) | ✅ 잡힘 |
| 한 지점만 슬립 | ✅ 잡힘 | ✅ |

**SRS 부록 B 가 경고한 "오픈루프 오차 1~5%" 가 정확히 첫 줄입니다.** 900 mm 에서 3% 면
27 mm 인데, 두 검증 장치 모두 0 을 보고합니다.

### 4-1. 유일한 독립 검증 — 체커보드 결과와 비교

줄자와 엔코더는 **완전히 독립적인 길이 기준**입니다. 두 방식의 결과를 비교하면
스케일 불일치가 그대로 드러납니다.

행렬을 직접 비교하면 안 됩니다 — 월드 원점이 다릅니다(체커보드는 폼보드 좌하단,
주행은 로봇 출발 위치라 세션마다 이동). 절차는:

```
1. 같은 평면으로 맞춘다:  A = H_marker(파생, 체커보드) ,  B = H_marker(측정, 주행)
2. 테스트 픽셀 N개를 두 행렬로 각각 월드로 보낸다
3. 두 점집합 사이 닮음변환을 최소제곱으로 맞춘다:  world_B ≈ s·R·world_A + t
4. 회전 R 과 평행이동 t 는 프레임 차이일 뿐이라 버린다
```

남는 두 숫자가 답입니다.

| 지표 | 정상 | 벗어나면 |
|---|---|---|
| **스케일 `s`** | 1.000 | **길이 기준 불일치** — 이게 그동안 못 잡던 값 |
| **정렬 후 RMS 잔차** | ~0 mm | 형상 자체가 다름(전단·원근·왜곡 미보정) |

로봇이 900 mm 갔다고 보고했는데 실제 873 mm 였다면 `s = 1.031` 로 나옵니다.

이 비교는 CCTV(카메라)에서 계산해 관리자창 Odometry 탭에 표시하겠습니다. 두 H 와 K 를
모두 카메라가 갖고 있어 가능합니다.

### 4-2. 비교로도 "어느 쪽이 틀렸는지"는 모릅니다

`s = 1.031` 이 나와도 오도메트리가 3% 짧게 잰 것인지 줄자가 3% 늘어난 것인지는
구분되지 않습니다. **불일치의 크기**만 나옵니다.

확정하려면 제3의 기준이 필요합니다. **로봇을 정확히 1 m 직진시키고 실제 이동거리를
줄자로 재는 것 한 번이면 충분**합니다. 이건 서버/로봇팀 쪽에서 한 번만 해주시면
이후 계속 쓸 수 있는 값입니다(엔코더 스케일 보정계수).
