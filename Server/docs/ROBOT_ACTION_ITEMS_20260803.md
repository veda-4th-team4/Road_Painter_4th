### 새로 관측된 것 (2026-08-04)

- **[P0/CCTV] 도색 중 `POS` 완전 두절** — 도색 `MOVE` 구간에서 서버 수신이
  `0 (0.0Hz)`였다. 0.38m 획을 **전부 오픈루프로** 그었다는 뜻이다. 그 구간
  로봇 로그에도 `Received DRIFT feedback` 줄이 하나도 없다.
- **[P0/CCTV] `POS` 수신율 1.2~1.5Hz** — 설계 전제(15~30Hz)와 한 자릿수 차이다.
  정렬 파라미터 전반이 이 값에 묶여 있다.
- **[P1/로봇] stale `ALIGN` 래치 의심** — `GetAlignCommand()`가 `waiting_for_go`
  일 때만 호출되므로, 그 창 밖에서 도착한 `ALIGN`이 소비되지 않고 남는다.
  **새 `PATH` 수신 시 `has_align_cmd`/`go_signal_received`를 비울 것.**
- **[P1/서버] 정렬 핸드셰이크 중 `DRIFT` 중복 발행** — `READY`~`GO` 사이에도
  `DRIFT`가 나가 `ALIGN`과 같은 오차를 두 채널로 보낸다. 이 구간은 서버가
  로봇 정지를 확신할 수 있으므로 서버 단독 억제 가능. (후속 과제)

## A. 서버가 이미 바꾼 것 — 로봇 코드 수정은 불필요

메시지 형식·순서(프로토콜)는 **변경 없음**. 다만 타이밍이 달라졌으니 알아둘 것.

| 변경 | 내용 | 로봇 영향 |
|---|---|---|
| ALIGN 이후 READY 유예 | ALIGN을 보낸 뒤 온 READY는 즉답하지 않고, 그 READY 수신 시점부터 **2초 고정** 대기 후 판정 (2026-08-04 개정: 당초 "새 `POS` 3장 or 1초"였으나 현장 `POS`가 1~2Hz라 거의 항상 타임아웃에 먼저 걸려 폐기) | ALIGN/GO 응답이 **최악 2.5초** 늦어짐 |
| 정렬 판정에 POS 평균 사용 | 유예 중 모인 N장의 theta 평균(sin/cos)으로 판정 | 없음 |
| 정렬 허용 오차 2° → **4°** | 아래 B-5 근거 참고 | ALIGN 횟수가 줄어듦 |
| POS 이상치 게이트 | 각도 변화가 `3° + 40°/s × 경과시간`을 넘는 프레임 폐기 | 없음 |

> ### ⚠️ 로봇팀 필수 준수사항
> **`READY`에 자체 타임아웃을 걸어 임의로 출발하지 말 것.** 서버는 어떤 경로로든
> 반드시 `ALIGN` 또는 `GO`를 하나 돌려준다(판정 불가 상황에서도 `GO`를 보낸다).
> 응답이 1초 넘게 걸리는 건 정상 동작이다.
>
> **`STATUS` 주기 전송을 멈추지 말 것.** `POS`가 끊긴 상황에서 유예된 `READY`를
> 회수하는 heartbeat로 `STATUS`를 쓴다. 멈추면 로봇이 대기 상태로 남는다.

자세한 근거는 [server_PROTOCOL.md](../server_PROTOCOL.md) —
"ALIGN 이후 READY는 서버가 늦게 답한다", "POS 이상치 게이트" 절.

## B. 로봇이 고쳐야 할 것

### B-1. [P0] 정렬 핸드셰이크가 통째로 꺼져 있다

**위치**: `RaspberryPi/src/main.cpp:146`

```cpp
bool bypass_server_go = true; // Set to true to bypass server GO/ALIGN wait
```

로그의 `[BYPASS GO] Starting MOVE segment 1 directly.`가 이것이다. 로봇이 `READY`는
보내지만 응답을 기다리지 않고 바로 출발하므로, 뒤늦게 도착한 `ALIGN -5.2`는 그냥
버려졌다.

**중요**: 이 플래그가 `true`인 한 **A절의 서버 수정은 전부 무효**다. 다른 항목보다
먼저 `false`로 돌려야 나머지 검증이 가능하다.

**수정**: `bypass_server_go = false`. (연속 주행이 필요해 일부러 켜둔 것이라면,
왜 필요한지 알려주면 서버 쪽에서 다른 방법을 찾겠다.)

### B-2. [P0] DRIFT 부호가 반대로 적용된다 — 발산의 직접 원인

**위치**: `RaspberryPi/src/PathFollower.cpp:157-158`

```cpp
float total_heading_error = drift_offset_deg + imu_yaw_deg;
float target_w = -total_heading_error * 0.05f;   // ← 이 마이너스
```

**근거 3가지**

1. `velocity_to_sps()`(:243)는 `v_left = v − wb/2`, `v_right = v + wb/2` — 즉
   **w > 0 = 좌회전(CCW)** 표준 규약이다.
2. 서버가 보내는 `DRIFT.angle_deg`는 `normDeg(목표heading − 현재theta)`, 즉
   **양수 = "CCW(좌)로 이만큼 돌려라"** 는 *보정 지령*이다. 지령에 `−`를 붙이면
   정확히 반대로 간다.
3. **로그 교차검증**:
   - `TURN angle_deg=-37.1` → L +781 / R −781 = 시계방향. **음수 = CW** ✓ 서버 규약과 일치
   - `DRIFT +2.1°` → L 906 / R 637 = 시계방향. **양수 = CW** ✗ 정반대
   - 같은 로봇 안에서 TURN과 DRIFT가 반대 규약을 쓰고 있다. `PathFollower.cpp:230`의
     주석("positive angle_deg = left turn, 양의 w")이 로봇팀의 의도이고, TURN은
     그대로 구현돼 있는데 DRIFT만 어긋났다.

발산 궤적이 이걸 증명한다 — `1.1 → 2.1 → 4.6 → 12.1 → 35.6 → 49.4°` 단조 증가는
양의 피드백의 전형이다.

**수정**: `drift`는 이미 *보정 지령*이고 `imu_yaw`는 *측정값*이라 **필요한 부호가
서로 반대**다. 둘을 더한 뒤 `−` 하나를 씌운 게 진짜 결함이다.

```cpp
// IMU yaw가 CCW+ 기준일 때. IMU 부호 규약은 로봇팀이 확인 요망 (B-4 참고)
float target_w = (drift_offset_deg - imu_yaw_deg) * kSteerGain;
```

### B-3. [P0] 조향 게인에 포화 클램프가 없다 — 부호와 무관한 별개 버그

**위치**: 같은 줄 (`PathFollower.cpp:158`)

로그에서 역산한 실측 특성:

| 항목 | 값 |
|---|---|
| 기저 속도 | 0.05 m/s = **771 SPS** |
| 조향 게인 | 0.05 rad/s/도 = **약 64 SPS/도** |
| 한쪽 바퀴 정지 | **드리프트 12°** (L 1546 / R −3) |
| 한쪽 바퀴 역회전 | 12° 초과 (35.6°에서 L 3051 / R −1508 = 제자리 스핀) |

**부호를 고쳐도** 정당한 12° 이탈 한 번이면 제자리 스핀이 나온다. 직진 보정이
스핀으로 변하는 건 어떤 상황에서도 정상이 아니다.

**수정**: 다음 중 하나 이상.
- `target_w`를 ±0.3 rad/s로 클램프 (양쪽 바퀴가 계속 전진하는 범위)
- 또는 출력단에서 **어느 바퀴도 기저 SPS의 30% 아래로 내려가지 않게** 클램프
  (구현 무관하게 안전한 형태 — 축간거리 값에 의존하지 않음)
- 게인 자체도 하향 검토 (64 SPS/도는 0.25m짜리 짧은 세그먼트엔 과함)

### B-4. [P1] IMU Yaw가 전 구간 `0 deg`

**증상**: 로봇이 물리적으로 50° 넘게 돌아간 뒤에도 로그의 모든 줄이
`IMU Yaw: 0 deg`. `total_heading_error = drift + 0`이 되어 **융합의 절반이 죽어
있었다.**

IMU가 살아 있었다면 서버 DRIFT와 반대로 밀어 발산 전에 잡혔을 가능성이 있다. 즉
**B-2의 안전망이 없었던 것**이므로 별도 이슈로 다뤄야 한다.

**확인 항목**
- `imu_manager.GetYaw()`가 실제 값을 반환하는가 (I2C 초기화 실패 시 0 반환?)
- 세그먼트 전환 시 yaw를 0으로 리셋하는 설계인가 — 그렇다면 리셋 이후 누적이
  되고는 있는가
- **부호 규약**: CCW가 양수인가 음수인가 (B-2 수정식이 여기 의존한다)

### B-5. [P1] 미세회전이 매번 약 1.4° 오버슛한다 — 정렬 미수렴의 절반

**위치**: `RaspberryPi/src/main.cpp:328` — `usleep(80000)`

```
루프 1틱(80ms): 스텝 카운트 읽기 → UpdateTurn → 미달이면 ±400 SPS 명령 → 80ms 잠
                                                        ↑ 이 80ms 동안 모터는 계속 돈다
```

로봇은 초당 12.5번만 "다 돌았나"를 확인한다. 그 사이는 눈 감고 회전한다.

> **1틱당 회전량 = 400 SPS × 0.08s = 32스텝 ÷ 22.58스텝/도 = 1.42°**

**로그 검증** — 전혀 다른 속도의 두 사건이 같은 값을 가리킨다:

| 사건 | 초과분 | 그때 진행률 | 환산 |
|---|---|---|---|
| `Turn completed! 863/838` | 25스텝 | 400 스텝/s | 62ms |
| `Move completed! 4104/3858` | 246스텝 | (3935+2392)/2 = 3163 스텝/s | 78ms |

**왜 문제인가**: 종전 정렬 임계값이 2.0°인데 로봇의 회전 분해능이 1.42°였다.
2.0° ALIGN은 45스텝 = 113ms = 1.4틱이라 로봇은 **1.42° 아니면 2.84°** 를 실행한다 —
2°는 애초에 실행 불가능한 명령이었다. 게다가 오버슛은 **항상 목표를 지나치는 한쪽
방향**이라 평균으로 상쇄되지 않는 계통 편향이다.

서버는 임시로 임계값을 4°로 올렸다(A절). **이 항목이 고쳐지면 다시 내릴 수 있다.**

**수정**: 다음 중 하나.
- **감속 접근 (권장)**: 남은 스텝이 2틱분(64스텝) 미만이면 400 → 100 SPS.
  양자가 1.42° → 0.35°로 준다.
- **예측 정지**: `progress + 16 >= target`이면 정지 (반 틱 앞서 멈춰 편향 중심화).
  한 줄이면 되고 계통 편향이 사라진다.
- 루프 주기 단축(80ms → 20ms)은 UART 예산 전체를 건드려야 해서 부담이 크다.

### B-6. [P2] ALIGN 중 진행 중인 회전을 무조건 덮어쓴다

**위치**: `RaspberryPi/src/main.cpp:164`

```cpp
if (net_manager.GetAlignCommand(align_deg)) {
    path_follower.StartTurn(align_deg, ...);   // IsTurning() 검사 없음
}
```

`StartTurn`은 `turn_start_left_steps` 기준점을 새로 잡으므로(`PathFollower.cpp:75`),
회전 중에 ALIGN이 하나 더 도착하면 **부분 완료된 회전량이 통째로 증발**하고 처음부터
다시 센다.

서버 수정(A절 유예)으로 겹칠 확률은 크게 줄었지만, 방어적으로 막아두는 게 맞다.

**수정**:
```cpp
if (!path_follower.IsTurning() && net_manager.GetAlignCommand(align_deg)) { ... }
```

## C. 검증 절차 제안

B-1 ~ B-3을 고친 뒤, **발산 위험이 없는 순서로** 확인하는 걸 권장한다.

1. **정지 상태 부호 확인 (바퀴 들고)**
   서버 콘솔에서 임의 DRIFT를 주입하거나, 로봇을 목표 heading에서 좌/우로 5°씩
   틀어 세워둔다. `DRIFT` 양수일 때 **좌회전 방향**으로 바퀴가 도는지 눈으로 확인.
   → 이것만 통과하면 발산은 원천 차단된다.

2. **짧은 세그먼트 주행 (0.5m)**
   목표 heading에서 5° 틀어놓고 출발. 서버 로그의 `DRIFT` 값이 **단조 감소**하면
   정상. 증가하면 부호가 아직 반대다.

3. **클램프 확인**
   의도적으로 15° 이상 틀어놓고 출발. 어느 바퀴도 역회전하지 않는지 확인.

4. **정렬 수렴 확인** (B-1을 `false`로 되돌린 뒤)
   서버 로그에서 `READY(seg=N) 각도오차 X도 (POS N장 평균) - ALIGN 전송 (n/4회)`를
   본다. **n이 1~2에서 GO로 끝나면 정상.** 매번 4/4까지 가면 B-5가 아직 남은 것.

5. **IMU 확인**: 로봇 로그의 `IMU Yaw`가 0이 아닌 값을 내는지.

## D. 서버가 추가로 할 일 (참고 — 로봇팀 액션 아님)

- 정지 상태 theta 노이즈 실측 → 임계값 4°와 게이트 상수 3°를 근거 있는 값으로 재조정
- 주행 중 DRIFT용 sin/cos EMA 필터
- `POS`에 타임스탬프 추가 (CCTV팀 협의 필요) — ALIGN 유예의 근본 해결책
- DRIFT를 직진 구간에서만 송출 (현재는 TURN 중에도 나가서 로봇이 필터링 중)
