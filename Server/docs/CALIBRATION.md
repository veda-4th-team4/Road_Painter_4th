## 0. 무엇을 구하는 것인가

카메라가 본 **픽셀**을 바닥의 **밀리미터**로 바꾸는 3×3 행렬을 구하는 일이다.
채널마다 렌즈 방향이 달라 `K`·`D`·`H` 가 전부 다르므로 **채널별로 따로** 잡는다.

평면이 둘이라는 것이 이 시스템의 핵심이다.

| 행렬 | 대상 평면 | 쓰는 곳 |
|---|---|---|
| `H_floor` | 바닥 평면 (`z = 0`) | 사람 발끝 → 월드 좌표 (구역 침입 판정) |
| `H_marker` | 로봇 마커가 떠 있는 평면 (`z = 마커 높이`) | **로봇 pose** — 서버가 실제로 쓰는 것 |

사람 발끝은 바닥에 있고 로봇 마커는 바닥에서 높이를 갖는다.
하나의 호모그래피를 공통으로 쓰면 마커 높이만큼 **시차**가 생겨 로봇 위치가 어긋난다.

번들에는 `K`, `D`, `H_floor`, `H_marker`, `unit`, `coord_mode`, `image_size`, `canvas_mm` 이 함께 담긴다.
단위는 **mm 로 보존**하고, 미터 변환은 서버 내부 사본에서만 한다.

## 2. 공통 계약 — 세션은 반드시 응답 하나로 닫힌다

🔴 **이 문서에서 가장 중요한 규칙이다.**

> 시작한 세션은 **반드시 종결 응답 하나**로 끝나야 한다.
> `H_MATRIX` | `CALIB_FAIL` | `CALIB_CANCELLED` — 셋 중 정확히 하나.

Qt 는 `CALIB_START` 를 보낸 뒤 전체 화면 대기로 들어가서
채널 전환·새 작업·수동 주행·로그아웃을 전부 막아둔다.
**종결 응답을 빠뜨리면 조작자는 몇 분 동안 아무것도 못 한다.**

그래서 모든 이탈 경로가 전송으로 끝난다 — 사전 검증 실패, 피어 이탈, 타임아웃, 취소 ACK 불발.

### 소유권

개시자가 둘(QT / ADMIN)이고 로봇은 한 대뿐이라, 한쪽이 도는 동안 다른 쪽은 busy 로 거절된다.
동시에 두 세션이 돌면 서로의 주행을 자기 관측으로 착각하기 때문이다.

**취소는 소유자만 할 수 있다.** 단 관리자 창의 강제 회수(`CALIB_CANCEL{force:true}`)는 예외다 —
로봇이 실제로 바닥을 굴러다니는 중인데 Qt 단말 앞에 사람이 없을 수 있고,
그때 관리자가 로봇을 못 세우면 안 되기 때문이다.

### 타임아웃

| 값 | 기본 | 의미 |
|---|---|---|
| `calib_timeout_ms` | 3분 | 정적 앵커 세션 전체 |
| `calib_odo_timeout_ms` | 5분 | 오도메트리 **주행** 데드라인 |
| `calib_odo_result_wait_ms` | 1분 | 주행 후 카메라 계산 대기 |
| `calib_capture_timeout_ms` | 15초 | 캡처 한 번의 ack 대기 |
| `calib_cancel_ack_ms` | 5초 | 취소 후 정지 확인 대기 |

🔴 서버 타임아웃은 **Qt 자체 타임아웃보다 반드시 짧아야 한다.**
서버가 먼저 접어야 Qt 가 이유를 모른 채 기다리지 않는다.
Qt 대기 한도는 방식마다 다르다 — 정적 앵커 **5분**, 오도메트리 **10분**.
QT 가 개시한 오도메트리 세션은 서버가 예산을 알아서 깎는다(`Router::odoDriveBudgetMs`).

## 3. 정적 앵커 방식

바닥에 위치를 아는 ArUco 앵커를 깔고, 카메라가 그것들을 보고 `H_floor` 를 맞춘다.

```
QT/ADMIN → Server   CALIB_START{ch, request_id}
Server   → CCTV     (채널 전환 + 세션 개시를 한 덩어리로)
CCTV                앵커가 전부 보이는 프레임을 모아 findHomography
CCTV     → Server   H_MATRIX{ch, calib:{...}}   또는   CALIB_FAIL
Server              영속 저장 + Qt 중계
```

- 서버는 **경로도 알고리즘도 관여하지 않는다.** 요청을 받아도 되는 상태인지 검증하고,
  채널 전환과 세션 개시를 원자적으로 처리하고, 종결 응답을 보장하는 것이 전부다.
- 앵커 배치·검출·피팅은 카메라 담당이다.
- 잔차 평가는 별도 검증 세트를 두지 않고 **LOO(leave-one-out)** 로 낸다 —
  앵커가 적을 때 held-out 을 떼면 피팅과 평가가 둘 다 나빠지기 때문이다.

### `H_marker` 는 어떻게 나오나 — 시차 보정

앵커는 바닥에 있으므로 이 방식이 직접 주는 것은 `H_floor` 뿐이다.
`H_marker` 는 거기서 **유도**한다.

```
1. K⁻¹ 로 H_floor 를 분해해 회전 두 축 r1, r2 와 평행이동 t 를 얻는다
2. 셋째 축을 복원한다:  r3 = r1 × r2
3. 마커 높이 h 만큼 평면을 띄운다:  H_marker = K [ r1  r2  (h·r3 + t) ]
```

🔴 이 유도는 **`K` 로 왜곡을 보정한 좌표계에서 맞춘 `H_floor`** 에만 쓸 수 있다.
원본 픽셀에 그냥 맞춘 `H` 로는 분해가 성립하지 않아 카메라가 거부한다.

## 4. 오도메트리 주행 방식

### 4.1 원리

로봇이 **알려진 크기의 직사각형을 개루프로 한 바퀴 돌고**, 9개 정지점마다 카메라가 마커를 찍는다.
"물리좌표(서버 계산) × 픽셀좌표(카메라 관측)" 쌍 8개로 `H_marker` 를 직접 구한다.

| | 앵커 방식 | 오도메트리 주행 |
|---|---|---|
| 직접 얻는 행렬 | `H_floor` | **`H_marker`** |
| 시차 보정 | 필요 | **불필요** (마커를 직접 찍으므로) |
| 대응점 분포 | 앵커를 깐 만큼 | **작업 영역 전체** |
| 물리 타깃 | 앵커 필요 | **로봇만 있으면 됨** |

### 4.2 전체 흐름

```
[1] 개시    → Server   CALIB_START{method:"robot_motion", ch, m_cm, n_cm, start_corner}
[2] Server  → Robot    PATH{phase:"calib", ops:[11개]}
[3] Robot   → Server   READY(k)                        ← 정지점마다
    Server  → CCTV     CALIB_CAPTURE{point_index, world_xy_mm}
    CCTV    → Server   CALIB_CAPTURE_OK{pixel_uv}      ← 카메라가 정지 판정 후
    Server  → Robot    GO(k)                            ← 9회 반복
[4] Robot   → Server   PATH_DONE(calib)                ← 마지막 점은 READY 가 없다
    Server  → CCTV     CALIB_CAPTURE{point_index:8} → ack
    Server  → CCTV     CALIB_DONE{m_mm, n_mm}
[5] CCTV               8점으로 findHomography + LOO → H_marker
                       H_floor 역산, K/D 재활용, 번들 조립
    CCTV    → Server   H_MATRIX{ch, calib:{...}}
[6] Server             영속 저장 + Qt 즉시 중계
```

### 4.3 로봇 경로 — 11 op, 펌웨어 변경 없음

서버가 사각형 op 시퀀스를 만들어 기존 `PATH{phase:"calib"}` 로 보낸다.
전용 `CALIB_*` 명령을 로봇에 중계하지 않는다 — 로봇 펌웨어에는 그런 핸들러가 없고 만들 필요도 없다.
로봇은 `PATH`/`READY`/`GO`/`PATH_DONE` 기존 핸드셰이크를 그대로 탄다.

```
ops = [ MOVE(m/2), MOVE(m/2), TURN(±90°),
        MOVE(n/2), MOVE(n/2), TURN(±90°),
        MOVE(m/2), MOVE(m/2), TURN(±90°),
        MOVE(n/2), MOVE(n/2) ]                      (11 ops)
```

**사각형을 닫는 이유**: 3구간만 달리면 꼭짓점 4 + 중점 3 = 7점뿐이다.
4구간을 다 돌면 **8점**이 되고 로봇이 출발점으로 돌아온다 — 그 복귀가 폐합오차 측정이 된다.

### 4.4 정지점 9개

`m`/`n` 은 mm. 아래는 기본값 `m=900, n=600` 기준.

| `point_index` | 캡처 트리거 | `bottom_left` | `top_left` |
|---:|---|---|---|
| 0 | `READY(0)` | `(0, 0)` | `(0, 600)` |
| 1 | `READY(1)` | `(450, 0)` | `(450, 600)` |
| 2 | `READY(2)` | `(900, 0)` | `(900, 600)` |
| — | `READY(3)` | *(직전 op 이 TURN — 스킵, 즉시 GO)* | |
| 3 | `READY(4)` | `(900, 300)` | `(900, 300)` |
| 4 | `READY(5)` | `(900, 600)` | `(900, 0)` |
| — | `READY(6)` | *(스킵)* | |
| 5 | `READY(7)` | `(450, 600)` | `(450, 0)` |
| 6 | `READY(8)` | `(0, 600)` | `(0, 0)` |
| — | `READY(9)` | *(스킵)* | |
| 7 | `READY(10)` | `(0, 300)` | `(0, 300)` |
| 8 | **`PATH_DONE`** | `(0, 0)` | `(0, 600)` |

- **캡처 트리거 규칙**: 직전 op 이 `TURN` 이면 스킵한다. 회전 앞뒤 `READY` 는 같은 물리 위치다.
- **마지막 점(idx 8)은 `PATH_DONE` 으로 잡는다** — 로봇은 마지막 op 뒤에 `READY` 를 보내지 않는다.
- **idx 8 은 피팅 입력에서 제외한다.** 라벨이 idx 0 과 겹쳐 같은 물리좌표에 다른 픽셀을 주면
  모순된 대응점이 된다. 대신 **idx 0 과 idx 8 의 픽셀 차이 = 한 바퀴 누적 오차**로만 쓴다.

### 4.5 좌표계와 운영 제약

**월드 원점은 로봇의 출발 위치다.** 그래서 원점이 **세션마다 바뀐다**(수용된 결정).

**로봇은 작업 영역 왼쪽 변에서 시작한다.**

| `start_corner` | 시작점 | 1구간 방향 | 회전 |
|---|---|---|---|
| `bottom_left` | `(0, 0)` | +x | 왼쪽(CCW) |
| `top_left` | `(0, n)` | +x | 오른쪽(CW) |

회전 방향은 조작자가 고르는 값이 아니라 **시작 위치가 결정**한다.
코드로 강제하지 않는다 — 버튼을 누르기 전 조작자가 지켜야 하는 절차다.

**`world_xy_mm` 은 마커 중심 좌표다.** 로봇 회전 중심이 아니다.
카메라가 짝짓는 픽셀이 마커이기 때문이다. 마커가 회전 중심에서 벗어나 있으면
서버가 내부에서 보정한다 — 카메라는 무관하다.

```
world = center + marker_offset_mm × (cos(heading), sin(heading))
```

`marker_offset_m` 이 `0` 이면 위 좌표표가 그대로 나간다.
값이 나중에 밝혀져도 `params.json` 만 고치면 되고 코드도 wire 형식도 안 바뀐다.

> 측정 방법: 로봇을 제자리에서 360° 회전시켜 마커가 한 점에 머무는지 원을 그리는지 본다.
> 원이 그려지면 그 반지름이 오프셋이다.

### 4.6 피드백은 완전히 꺼진다

캘리 주행은 **온전한 개루프**여야 한다.
그 채널에 옛 캘리브레이션이 남아 있으면 pose 계산이 되면서
`MORE`/`ALIGN` 이 **옛 캘리 기준으로 이번 주행을 보정해버려** 순수 오도메트리가 아니게 된다.

이중으로 막는다.

1. **op 자체** — 11개 op 전부 `hasTarget=false`, `headingDeg=kNoHeading`, `isPath=false`.
   `MORE`/`ALIGN`/`DRIFT` 조건에 전부 걸려 자연히 차단된다.
2. **phase 가드** — `onReady()` 가 `phase=="calib"` 이면 판정 로직 전체를 건너뛰고
   캡처 핸드셰이크로 위임한다.

### 4.7 ⚠ 검증과 한계 — 반드시 읽을 것

#### 잔차도 폐합오차도 "스케일 오차"를 못 잡는다

**호모그래피는 아핀 변환을 완전히 포함한다.**
오도메트리 라벨이 참값의 `s` 배면 피팅 결과는 `diag(s,s,1)·H_true` 가 되고,
이것도 **유효한 호모그래피**다. 잔차가 **정확히 0** 으로 나오면서 좌표는 틀린다.

| 오도메트리 오차 | 재투영 잔차 | 폐합오차 | 현실성 |
|---|---|---|---|
| **균일 스케일** | ❌ 완전 흡수 | ❌ 0 — 네 변이 똑같이 짧으면 정확히 복귀 | **높음** (바퀴 지름·틱 환산) |
| **m·n 스케일이 다름** | ❌ 흡수(아핀 신축) | ❌ 0 | **있음** (방향별 슬립 차이) |
| 회전 88°/92° 교대 | ❌ 흡수 | ❌ 0 | 낮음 |
| 회전 전부 88° (계통 편향) | ✅ 잡힘 | ✅ 잡힘 | — |
| 한 지점만 슬립 | ✅ | ✅ | — |

900 mm 에서 3% 면 27 mm 인데 두 지표 모두 0 을 보고한다.

다행히 이 경로는 회전이 **전부 같은 방향**이라 계통적 회전 편향은
"전부 88°" 쪽으로 나타나고 그건 잡힌다. 실질적 사각지대는 **스케일 계열 두 개**로 좁혀진다.

#### 유일한 독립 검증 — 앵커 방식과 비교

줄자와 엔코더는 **완전히 독립적인 길이 기준**이다. 두 결과를 비교하면 스케일 불일치가 드러난다.
행렬을 직접 비교하면 안 된다 — 월드 원점이 다르다.

```
1. 같은 평면으로 맞춘다:  A = H_marker(앵커에서 유도),  B = H_marker(주행에서 측정)
2. 테스트 픽셀 N개를 두 행렬로 각각 월드로 보낸다
3. 두 점집합 사이 닮음변환을 최소제곱으로 맞춘다:  world_B ≈ s·R·world_A + t
4. 회전 R, 평행이동 t 는 프레임 차이일 뿐이라 버린다
```

| 지표 | 정상 | 벗어나면 |
|---|---|---|
| **스케일 `s`** | `1.000` | **길이 기준 불일치** — 다른 어떤 장치로도 못 잡던 값 |
| 정렬 후 RMS 잔차 | ~0 mm | 형상 자체가 다름 (전단·원근·왜곡 미보정) |

로봇이 900 mm 갔다고 보고했는데 실제 873 mm 였다면 `s = 1.031` 로 나온다.

#### 비교로도 "어느 쪽이 틀렸는지"는 모른다

`s = 1.031` 이 나와도 오도메트리가 3% 짧게 잰 것인지 줄자가 3% 어긋난 것인지는 구분되지 않는다.
**불일치의 크기**만 나온다.

확정하려면 제3의 기준이 필요하다 —
**로봇을 정확히 1 m 직진시키고 실제 이동거리를 줄자로 재는 것 한 번**이면 충분하다.
세션마다가 아니라 **로봇 물리 상수 1회 확인**이다.

#### 사각형 크기

키우면 원근항이 잘 잡히지만(대응점이 가장자리로 퍼져 조건수 개선)
**오도메트리 누적 오차도 같이 는다.**
스케일 사각지대는 키워도 나아지지 않고 드리프트만 커지므로,
**첫 주행은 900×600 으로 하고 폐합오차를 본 뒤** 결정하는 순서가 맞다.

`calib_odo_max_side_m`(기본 10 m)이 상한을 막는다. 🔴 이 값이 그대로 실제 주행 거리가 된다 —
`90` 을 `900` 으로 잘못 치면 로봇이 9 m 사각형을 그린다.

## 5. 채널 간 정합 (registration)

두 채널의 월드 좌표계를 잇는 **닮음변환**을 구한다. ADMIN 전용이다.

오도메트리 방식과 가장 큰 차이는 **로봇 경로가 없다**는 것이다.
FOV 겹침 구역이 아직 실측되지 않아 자동 경로를 짤 근거가 없다.
그래서 조작자가 **조이스틱으로 로봇을 겹침 구역에 직접 몬다.**

```
ADMIN  → Server   REGISTER_COLLECT_START{ch_a, ch_b, request_id}
Server → CCTV     REGISTER_CAPTURE          ← reg_capture_interval_ms 주기로 반복
CCTV   → Server   REGISTER_CAPTURE_OK / FAIL(not_both_seen)
ADMIN  → Server   REGISTER_COLLECT_STOP
Server → CCTV     REGISTER_DONE
CCTV   → Server   H_MATRIX{... reg_* 필드 포함}   또는  REGISTER_FAIL
```

- 로봇이 실제로 두 채널 시야 안에 있을 때만 카메라가 OK 로 답한다.
  아닐 때는 그냥 실패라 조용히 다음 주기로 넘어간다 —
  오도메트리의 `READY`/`GO` 와 달리 **한 번 실패해도 세션을 접지 않는다.**
- 계산(닮음변환 피팅)도 저장도 전부 카메라가 한다.
  서버는 캡처를 트리거하고 세션 하나를 관리할 뿐이다.
- 결과는 기존 `H_MATRIX` 번들에 실려 오므로 서버는 `reg_*` 필드를 손대지 않고 그대로 흘려보낸다.
- ADMIN 전용이라 QT 소유권·대기 예산 개념이 없다.
  거절이나 진행 상황은 회신 메시지 없이 **로그로만** 남긴다(관리자 창은 로그를 TAP 으로 이미 받는다).

## 6. 현장 절차 요약

1. 채널을 고른다. 캘리브레이션은 **채널별**이다.
2. 렌즈 내부 파라미터(`K`, `D`)를 먼저 잡는다 — ChArUco 보드, 카메라에서 수행.
   `coord_mode:"undistort"` 번들은 `K` 가 없으면 반쪽만 적용되므로 순서가 중요하다.
3. 방법을 고른다.
   - 바닥에 앵커를 깔 수 있으면 → **정적 앵커**
   - 아니면 → **오도메트리 주행** (로봇 주변에 사람·장애물이 없는지 먼저 확인)
4. 결과를 확인한다. 잔차(LOO)와 폐합오차를 본다.
5. 🔴 오도메트리 방식을 처음 쓰는 현장이라면 **앵커 방식과 비교해 스케일 `s` 를 확인한다.**
   `1.000` 에서 벗어나면 §4.7 을 읽는다.
6. 두 채널을 이어 쓸 것이면 마지막으로 **채널 간 정합**을 돌린다.

## 7. 검증

로봇·카메라 없이 돌아가는 오프라인 테스트가 있다.

```bash
cd Server
make calib_unit_test odo_calib_test calib_channel_test
./tools/calib_unit_test      # 번들 파싱·좌표계·mm↔m 변환
./tools/odo_calib_test       # 11-op 시퀀스, 9점 좌표표, 마커 오프셋 보정
./tools/calib_channel_test   # 채널별 번들 저장, 구형식 호환
```

TLS 세션 흐름까지 보려면 `calib_session_test`(정적 앵커) / `odo_session_test`(오도메트리)를 쓴다.
자세한 것은 [tools/README](../tools/README.md) 참고.
