## 1. 서버팀 추가 요청 3건 — 전부 수용

### 1-1. (§3-1) 번들에 `method` 필드

수용합니다. 값은 제안대로:

```json
"method": "checkerboard" | "robot_motion"
```

**한 가지 명확히 해둘 것**: 이 값은 "어느 탭에서 눌렀는가"가 아니라 **번들에 실제로
실린 `H_marker` 가 어느 슬롯에서 왔는가**로 채웁니다. 운영자가 측정/파생 슬롯을 바꿔
가며 쓸 수 있으므로, 탭 기준으로 채우면 실제와 어긋납니다.

### 1-2. (§3-2) `K`/`D` 필수화 — 수용, 근거도 확인했습니다

인용하신 `admin_console/cctv.py` 주석을 실물 확인했습니다(2317행):

> 그 전에는 평면 형식을 보내면 서버가 레거시로 오인해 `H` 만 남기고
> `K`·`D`·`H_marker` 를 버렸다 — **에러 없이 보정만 꺼졌다.**

서버의 왜곡 보정이 `Calib::hasKD` 로만 켜진다는 지적도 맞습니다. 조립 함수가 하나이므로
**그 한 곳에 게이트**를 둡니다 — `K` 또는 `D` 가 비면 전송 거부하고 사유를 표시합니다.
floor 탭과 Odometry 탭 양쪽에 동시에 적용됩니다.

> 한계 하나는 남습니다: 게이트는 **존재 여부**만 봅니다. 품질이 나쁜 `K`(뷰 수 부족,
> rms 큼, 품질 게이트 off)는 통과합니다. 그건 캘리 단계에서 걸러야 하는 문제라
> 번들 게이트로는 못 막습니다.

### 1-3. (§3-3) `K` 변경 시 측정 `H_marker` stale — 지적이 맞습니다

확인 결과 현재 stale 표시는 **기존 슬롯 전용**입니다.
`homography_mapper.cc:1006`:

```c
if (available_[ch] && fitted_undistorted_[ch]) k_stale_[ch] = true;
```

신설되는 측정 `H_marker` 슬롯에는 **같은 줄을 따로 넣어야** 합니다. 마커 높이 stale과
동일하게 취급하겠습니다 — 표시만 하고 버리지는 않습니다.

## 2. §2-2 표 정정 — 저희 오류였습니다, 검산 결과

"회전 88° → 잔차 흡수"라고 쓴 것은 **틀렸습니다.** 서버팀 지적대로 계산했습니다
(`m=900`, `n=600`).

### 전부 88° — 두 장치 모두 잡습니다

```
seg1  (0,0)   → (900.0,   0.0)      heading 0°
seg2  heading 88°  → (920.9, 599.6)
seg3  heading 176° → ( 23.1, 662.4)
seg4  heading 264° → (-39.6,  65.7)
```

- **폐합오차 = 76.7 mm** (서버팀 계산 "약 77 mm" 와 일치)
- 앞 3점으로 아핀변환을 맞추면 4번째 점의 예측은 `(20.9, 599.6)` 인데 실제는
  `(23.1, 662.4)` — **약 63 mm 어긋납니다.** 즉 **잔차도 남습니다.**

### 88°/92° 교대 — 둘 다 통과합니다

```
seg1  → (900.0,   0.0)     seg2  heading 88°  → (920.9, 599.6)
seg3  heading 180° → (20.9, 599.6)    seg4  heading 268° → (0.0, 0.0)
```

- **폐합오차 ≈ 0** (정확히 복귀)
- 궤적 `(0,0)-(900,0)-(920.9,599.6)-(20.9,599.6)` 는 **정확한 평행사변형** =
  직사각형의 아핀상 → **잔차 0**

### 실무적 함의 — 오히려 좋은 소식입니다

이 경로는 **회전이 전부 같은 방향(CCW)** 입니다. 자이로·엔코더의 계통적 회전 편향은
"전부 88°" 쪽으로 나타나고, 그건 **두 장치가 다 잡습니다.** 교대 전단은 물리적으로
덜 그럴듯합니다.

**공통 사각지대로 남는 실질적인 것은 두 개**입니다:

| | 현실성 |
|---|---|
| 균일 스케일 오차 | 높음 — 바퀴 지름·틱 환산 |
| `m`·`n` 스케일이 서로 다름 | 있음 — 방향별 슬립 차이 |

둘 다 §4-1 의 체커보드 비교로만 잡힙니다. 결론은 그대로입니다.

## 3. 프로토콜 확정 요청 — 5건

이 다섯만 정해지면 카메라 구현을 전부 착수합니다.

### 3-1. `world_xy_mm` 의 의미를 "마커 중심"으로 명시

**가장 중요한 항목입니다.** 현재 계획서 §3 은 이 값을 **로봇의 물리좌표**로 정의하고
좌표 표도 로봇 경로입니다. 그런데 카메라가 짝짓는 픽셀은 **마커**입니다.

마커가 로봇 회전축에서 벗어나 있으면 두 점이 다르고, 캡처 지점마다 헤딩이 달라
(0° · 0° · 90° · 180°) **어긋나는 방향까지 달라집니다.**

계획서에 *"마커 중심과 로봇 회전 중심은 일치한다(2026-08-12 확인)"* 이라고 되어
있는데, **확인 방법이 적혀 있지 않아** 저희가 그 전제에 기대기 어렵습니다.

**요청**: 필드 정의를 한 줄 바꿔주세요.

```
world_xy_mm = 그 순간 "마커 중심"의 월드 좌표   (로봇 기준점이 아님)
```

이렇게 두면 오프셋 보정이 **서버 내부 계산**이 되고 카메라는 무관해집니다.
오프셋이 0 이면 지금 좌표 표 그대로이고, 0 이 아니면 서버가 헤딩으로 보정해 보냅니다.
**어느 쪽이든 프로토콜은 지금 확정되고, 물리 측정 결과를 기다릴 필요가 없습니다.**

> 오프셋 확인 방법(참고): 로봇을 제자리에서 360° 회전시켜 마커가 점에 머무는지 원을
> 그리는지 봅니다. 원이 그려지면 **그 반지름이 곧 오프셋**입니다. 몇 분이면 됩니다.

### 3-2. 세션 매칭 키에 `request_id` 포함

§1-3 에서 매칭 키를 `point_index` + `ch`, `request_id` 는 로그용으로 하셨는데
**구멍이 있습니다.**

세션을 재시작하면 `point_index` 가 다시 0 부터입니다. **이전 세션의 늦은 ack 가 새
세션의 같은 `point_index` 대기 중에 도착하면 키가 일치해서 통과합니다.** 막으려던
시나리오("이전 지점의 늦은 ack 가 현재 대기를 푸는 것")가 세션 경계에서 재현됩니다.

이미 주고받는 값이라 추가 비용이 없습니다. **매칭 키에 포함**을 요청드립니다.

### 3-3. 부분 실패 시 동작

9점 중 일부가 `unmappable` / `marker_not_found` / `not_settled` 로 실패했을 때:

- (a) 세션 즉시 중단 → `CALIB_FAIL`
- (b) 실패한 점만 빼고 남은 점으로 진행

**(b)를 제안합니다.** 한 점 때문에 3 m 주행을 통째로 버리는 건 비쌉니다.
그 경우 **최소 유효 점수**가 필요합니다:

```
제안: 유효 대응점 6개 미만이면 CALIB_FAIL
```

(피팅 자체는 4점이면 되지만, 4~5점이면 LOO 가 안 돌거나 의미가 없어져
품질 지표가 사라집니다. 6점이 실질 하한입니다.)

부분 실패 시 서버는 계속 진행하면 되고, 카메라가 `CALIB_CAPTURE_OK` 대신
`CALIB_CAPTURE_FAIL {point_index, reason}` 을 보내는 형태를 제안합니다.

### 3-4. 세션 타임아웃 — 카메라 측

`CALIB_DONE` 이 영영 오지 않으면(서버 재시작, 링크 단절) 카메라 세션이 계속 열려
있고, **그 렌즈가 다른 캘리를 거부하는 상태로 남습니다.**

```
제안: 마지막 CALIB_CAPTURE 로부터 10분 무응답이면 카메라가 세션을 폐기
```

폐기 시 서버에 알릴 방법이 마땅치 않아(그 시점엔 세션이 없음) **로그와 `/status`
에만 남기려고 합니다.** 그리고 모르는 세션의 `CALIB_CAPTURE` 가 오면
`CALIB_CAPTURE_FAIL {reason:"no_session"}` 으로 명시 거부하겠습니다 — 서버가
그걸로 재시작을 판단할 수 있습니다.

### 3-5. `method` 값 — 확인만

`"checkerboard"` | `"robot_motion"` 으로 확정. 이견 없으시면 그대로 갑니다.

## 4. 참고 — 작업 사각형을 키울 여지가 있습니다

CH2 의 현재 `H` 로 화면 영역이 월드에서 얼마나 되는지 계산해봤습니다.

| 화면 영역 | 월드 범위 |
|---|---|
| 전체 | 4,542 × 2,655 mm |
| **중앙 85%** (왜곡보정 수렴역) | **3,611 × 2,172 mm** |
| 중앙 70% | 2,793 × 1,734 mm |

기본값 **900 × 600 mm 는 중앙 70% 안에도 넉넉히 들어갑니다.** `unmappable` 걱정은
현재 설치에서는 하지 않아도 될 것 같습니다.

**사각형을 키우면 원근항(`h20`, `h21`)이 훨씬 잘 잡힙니다.** 대응점이 화면 가장자리
쪽으로 퍼질수록 호모그래피의 조건수가 좋아지기 때문입니다.

**다만 트레이드오프가 있습니다** — 주행 거리가 늘면 오도메트리 누적 오차도 같이
늡니다. 폐합오차도 비례해서 커집니다. 그래서 "무조건 크게"는 아니고, **1,800 × 1,200
정도까지는 중앙 85% 안에 들어가므로 검토해볼 만하다** 는 정도로 제안드립니다.
첫 주행은 900 × 600 으로 하고, 폐합오차를 본 뒤 키울지 정하는 것도 방법입니다.

> 주의: 이 계산은 `H` 가 undistort 픽셀 기준이라 화면 가장자리 매핑은 근사입니다.
> "900×600 이 들어가는가"에 답하기엔 충분하지만, 경계에 딱 붙여 설계하실 거면
> 실측이 필요합니다.

## 5. 카메라 착수 범위 (§3 확정 후)

| # | 내용 | 비고 |
|---|---|---|
| A | `CALIB_CAPTURE` / `CALIB_DONE` 수신 파싱 | 중앙 TLS 링크 |
| B | 명령 핸들러 | `CALIB_START` 가 세션 시작점이 됨 |
| C | 정지 판정 + 캡처 | `t_capture` 필터 + 픽셀 분산 |
| D | 대응점 버퍼 + 피팅 | 기존 최소제곱·LOO 재사용 |
| E | 측정 `H_marker` 슬롯 + stale 2종 | §1-3 반영 |
| F | 번들 조립기 (`method`, `K`/`D` 게이트, `H_floor` 역산) | §1-1·§1-2 반영 |
| G | 폐합오차(mm) + 두 방식 비교 | idx 8 은 피팅 제외 → out-of-sample 검증 |
| H | 세션 가드 (중복·K 없음·좌표계) | 서버 `calibActive_` 와 양방향 |

**대시보드(`cctv.py`)는 변경 없습니다** — 결과가 기존 `HG`/`HG_FIT`/`HG_FIT_PT`
메시지로 나가므로 관리자창이 그대로 받습니다.

호모그래피 탭은 이미 `floor` / `Odometry` 서브탭으로 나눠 배포했고, 각 서브탭에
서버 송신 블록도 붙어 있습니다(조립 함수는 한 벌 공유).

## 6. 정리

**서버팀 결정 필요**: §3 의 5건. 그중 3-1(필드 의미)이 가장 중요하고, 나머지 넷은
저희 제안대로 두셔도 무방합니다.

**CCTV 진행 중**: §3 회신을 기다리는 동안 A~E·H 를 먼저 붙입니다. F·G 는 3-1·3-3 이
정해져야 확정됩니다.

**병행 요청**: §4-2 의 1 m 직진 실측(엔코더 스케일 보정계수)은 로봇팀 일정에 맞춰
언제든 좋습니다. 그 값이 있어야 두 방식 비교에서 나온 불일치를 어느 쪽 탓으로
돌릴지 결정할 수 있습니다.
