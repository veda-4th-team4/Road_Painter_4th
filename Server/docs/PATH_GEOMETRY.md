# 경로 생성 기하

> **로봇이 왜 저기로 가지?** 에 답하는 문서.
> 도면(Qt) → 로봇 op 으로 바꾸는 과정에서 서버가 하는 네 가지 계산을 다룬다.
> 관련: [PROTOCOL](PROTOCOL.md) · [TUNING](TUNING.md) · [ARCHITECTURE](ARCHITECTURE.md)

구현은 전부 [`src/ops_builder.hpp`](../src/ops_builder.hpp) 한 파일에 있다.

---

## 0. 기호

| 기호 | 뜻 | 설정 키 |
|---|---|---|
| `a` | 마커 중심 → 펜(노즐)까지 거리. **펜은 중심 뒤에 있다** | `pen_offset_m` |
| `w` | 펜이 실제로 칠하는 폭. `h = w/2` | `pen_width_m` |
| `W` | 좌우 바퀴 축간거리 | `wheel_base_m` |
| `R_paint` | 도면상 노즐이 그려야 할 호 반지름 | (도면) |
| `R_robot` | 로봇(마커 중심)이 실제로 돌 반지름 | (서버가 계산) |

🔴 **`a` 와 `w` 의 실제 수치는 여기 적지 않는다.** 현장에서 계속 미세 조정되는 값이라
문서에 박아두면 금방 어긋난다. **정본은 [`config/params.json`](../config/params.json)** 이고,
서버가 기동할 때 적용값을 로그로 남긴다. 항목 설명은 [TUNING](TUNING.md)에 있다.

## 1. 왜 서버가 이걸 다 하는가

Qt 는 **사람이 그린 그대로**를 보낸다 — 펜 오프셋도, 속도도, 회전 중심도 담지 않는다.
로봇은 **시킨 만큼만** 간다 — 스스로 보정하지 않는다.
그 사이의 모든 변환이 서버 몫이다.

```
Qt : "이 사각형을 칠해줘"       (도면 좌표, 미터, CCW 양수)
        ↓  서버
로봇 : "0.125 m 가라 → 노즐 내려라 → 0.55 m 가라 → …"   (op 배열)
```

이렇게 나눈 이유는 **보정 주체를 한 곳으로 몰기 위해서**다.
로봇이 자기도 오프셋을 보정하면 매 꼭짓점마다 이중 보정이 되고,
Qt 가 보정하면 로봇 실측값이 바뀔 때마다 관제 PC 를 전부 다시 배포해야 한다.

> 🔴 **로봇은 펜 오프셋 보정을 하면 안 된다.** 서버가 이미 넣어서 보낸다.

## 2. 펜 오프셋 — 노즐이 뒤에 달려 있다는 문제

### 2.1 불변식

이 문서 전체가 아래 두 줄에서 나온다.

> **노즐이 내려가 있다 ⟺ 마커 중심이 도면 꼭짓점보다 진행방향으로 `a` 앞서 있다.**
> **노즐이 올라가 있다 ⟺ 마커 중심이 도면 꼭짓점 위에 있다.**

보정 op 은 이 두 상태를 오갈 때만 삽입된다.

### 2.2 생성 규칙

```
Qt 의 NOZZLE op 은 전부 버린다.        // 서버가 노즐 타이밍을 다시 만든다
penDown = false                          // draw 시작: 노즐 up, 중심 = points[0]

for each qtOp in program:
    isPaint = (qtOp.op == "MOVE" or "ARC") and qtOp.paint == true

    if isPaint and not penDown:          // 도색 진입
        emit move(+(a − h),  role=offset)
        emit nozzle(down=true, role=offset)
        penDown = true

    if not isPaint and penDown:          // 도색 이탈
        emit nozzle(down=false, role=offset)
        emit move(−(a + h),  role=offset)
        penDown = false

    emit convert(qtOp, role=path)        // 소문자화 + 부호반전 + 호 반지름·위상 보정

if penDown:                              // 경로 끝
    emit nozzle(down=false, role=offset)
    emit move(−(a + h), role=offset)
```

- 도색 진입에 "노즐 올리기"가 없는 이유: `penDown == false` 이므로 이미 올라가 있다.
- 이 규칙 덕분에 노즐 op 은 **자동으로 down/up 교대**가 보장된다.
- 연속 도색 구간 사이에는 불필요한 up/down 이 끼지 않는다
  (꼭짓점 회전각이 작아 Qt 가 `TURN` 을 생략한 경우).
- **`phase="draw"` 에서만 적용한다.** 접근(`approach`) 중에는 펜 위치를 따질 이유가 없다.

## 3. 펜 두께 — 귀퉁이가 비는 문제

### 3.1 무엇이 문제였나

실주행에서 목표 사각형의 **네 귀퉁이가 칠해지지 않았다.**

펜은 폭 `w` 짜리 마커인데 시스템이 펜을 **폭 0인 점**으로 취급했기 때문이다.
경계 코너를 원점으로 두면:

```
가로 구간 : 중심경로 y=h 위를 x=h 부터 진행   → 도색 밴드 x∈[h,…], y∈[0,w]
세로 구간 : 중심경로 x=h 위를 y=h 로 도착     → 도색 밴드 x∈[0,w], y∈[h,…]

       ┌────────────  ← 목표 경계
  ╱╱╱╱ │              [0,h]×[0,h] 정사각형이
  ╱╱╱╱ │              어느 밴드에도 안 들어간다
  ─────┼─────
       │
```

**미도색 영역 = 한 변에 `h × h` 짜리 정사각형.**

### 3.2 해법 — 앞뒤로 `h` 씩 늘린다

```
전진 오프셋 =  a − h
도색 move   =  L + w        (앞 h + 뒤 h)
후진 오프셋 =  a + h
```

검산 — 꼭짓점 `V0 → V1`, 구간 길이 `L`:

| 단계 | 마커 중심 | 펜 위치 | |
|---|---|---|---|
| 시작 | `V0` | `V0 − a` | |
| 전진 `(a−h)` | `V0 + a − h` | `V0 − h` | ✅ 앞으로 `h` 연장 |
| 도색 `(L+2h)` | `V1 + a + h` | `V1 + h` | ✅ 뒤로 `h` 연장 |
| 후진 `(a+h)` | `V1` | | ✅ 꼭짓점 복귀 |

🔴 **전진과 후진이 비대칭(`a−h` vs `a+h`)인 것이 핵심이다.**
도색 구간이 `w` 만큼 길어진 것을 후진에서 되돌려야 다음 꼭짓점 기준이 밀리지 않는다.
대칭으로 만들면 꼭짓점마다 `h` 씩 누적되어 사각형 한 바퀴에 네 번 밀린다.

### 3.3 호에서는 스윕을 늘린다

직선은 거리를 늘리지만 호는 각도를 늘린다.

```
sweep' = sweep + 2 × (h / R_paint)      [rad]
```

### 3.4 🔴 목표 좌표도 같이 고쳐야 한다

두께 보정은 **의도된 과주행**이다. 그래서 거리만 고치면
`MORE` 피드백이 그것을 오차로 보고 **매번 되돌려 버린다.**

| op | 실제 목표 | 보정 전 코드가 믿던 값 | 결과 |
|---|---|---|---|
| 전진 다리 | 꼭짓점 `+ (a−h)` | 꼭짓점 `+ a` | `h` 만큼 더 전진시켜 보정 무효화 |
| 도색 move 끝 | 꼭짓점 `+ (a+h)` | 꼭짓점 `+ a` | `h` 만큼 되돌림 |
| 후진 다리 | 꼭짓점 | 꼭짓점 | 문제없음 |

목표가 op 마다 다르므로(`a−h`, `a+h`, `0`) `bool` 하나로는 표현할 수 없다.
그래서 `OpMeta` 는 목표를 **거리값**(`centerAheadM`, double)으로 들고 있다.

> **피드백을 끄는 게 아니라 목표를 고치는 것이 답이다.**
> 끄면 두께 보정은 지켜지지만 원래 잡아주던 주행 오차까지 같이 놓친다.

## 4. 호(arc) — 노즐이 바퀴보다 크게 돈다

### 4.1 반지름 치환

> 🔴 **직각의 꼭짓점은 C(바퀴 중심)다. N(노즐)이 아니다.**
> 이 하나가 공식의 부호를 가른다.

차동구동 로봇의 회전중심(ICR)은 **반드시 좌우 바퀴 축선 위에 있다.**
축선은 C 를 지나고 차체축(C→N)에 수직이다. 따라서

```
ICR→C  ⊥  C→N     →  직각의 꼭짓점 = C
빗변   =  ICR→N   =  R_paint
```

```
R_paint = √(R_robot² + a²)      ← 노즐이 바퀴 중심보다 멀리 돈다
R_robot = √(R_paint² − a²)      ← 서버가 로봇에 보낼 값
```

**검산 — 제자리 회전(`R_robot = 0`)**
바퀴 중심은 서 있고 노즐만 반지름 `a` 원을 그린다(자명).

| 공식 | `R_robot = 0` 일 때 | 판정 |
|---|---|---|
| `R_robot = √(R_paint² + a²)` | `R_paint = 0` (노즐도 제자리) | ✗ 물리와 불일치 |
| `R_robot = √(R_paint² − a²)` | `R_paint = a` | ✅ |

- 스윕 각도는 **반지름 때문에 보정하지 않는다.** N 의 편각은 C 의 편각보다
  `atan(a/R_robot)` 만큼 **일정하게** 뒤처질 뿐이라 둘이 쓸어가는 각도는 같다.
  (두께 보정으로 늘리는 것은 §3.3 의 별개 항이다.)

> ⚠️ 저장소의 `Paint_Robot/RaspberryPi/src/arc_test.cpp` 는 `√(r² + a²)` 를 쓴다.
> 그것은 단독 실행용 실험 도구이고 실제 주행 경로에는 들어가지 않는다.
> 주행에 쓰이는 값은 서버가 계산해 보낸다.

### 4.2 진입 위상 보정 — 안 하면 원이 통째로 어긋난다

> **도색 호에서는 차체가 접선을 향하면 안 된다.**
> 접선에서 `φ = atan(a / R_robot)` 만큼 호 안쪽으로 틀어져 있어야 한다.

펜을 도면 원 위에 올리는 것만으로는 부족하다. ICR 을 도면 원 중심 `O` 에 놓으려면
마커 중심 `C` 가 `O` 에서 `R_robot`, 펜 `P` 에서 `a` 떨어진 자리에 있어야 하고,
그때 차체 방위는 접선에서 정확히 `φ` 만큼 틀어진 방향이다.

**검산**: `R_paint = a`(제자리 회전)이면 `R_robot = 0` 이라 `φ = 90°`.
차체가 접선과 직각 — 마커는 원 중심에 가만히 있고 펜만 도는 자명한 사실과 맞는다.
구현은 `atan2(a, R_robot)` 이라 `R_robot = 0` 에서도 터지지 않는다.

**안 하면 무슨 일이 생기나** — 반지름은 맞는데 원이 다른 자리에 그려진다.

| `draw_test --arc 0.5` | 보정 전 | 보정 후 |
|---|---|---|
| 펜 도착점 (도면 `(0, −1.0)`) | `(0.310, −0.950)` ❌ **0.31 m 이탈** | `(−0.001, −0.999)` ✅ |
| 펜 자취 반지름 (도면 `0.500`) | `0.4996` ✅ | `0.4997` ✅ |

**생성 규칙** (`φ` 는 CCW 부호 포함, 좌회전 호 `+` / 우회전 호 `−`)

```
진입:  turn(+φ)  →  move(+(a−h))  →  nozzle(down)  →  arc
이탈:  nozzle(up)  →  move(−(a+h))  →  turn(−φ)
```

- 이탈 `turn(−φ)` 으로 **반드시 접선으로 되돌린다.** 안 하면 뒤따르는 직선 op 이
  전부 `φ` 만큼 기운 채로 이어진다.
- 도색하지 않는 호는 `φ = 0` 이다. 펜이 올라가 있어 마커 중심이 곧 도면 자취다.

### 4.3 직선↔호 접합부에서는 펜을 든다

펜이 중심 뒤에 끌려가므로 펜의 **속도 방향**은

- 직진 중: 차체 방향과 같다
- 호 중: 차체 방향에서 `atan(a / R_robot)` 만큼 어긋난다

그래서 직진 → 호 전환점에 꺾임이 남는다(`R_paint = 0.5 m` 기준 **약 18°**).
끌리는 펜의 기하학적 귀결이라 주행 중에는 없앨 수 없다.

**그래서 접합부에서는 노즐을 한 번 올렸다 내린다.**
펜을 든 채로 위상을 맞추면 꺾임이 자취에 남지 않는다.
**획이 끊기는 것이 꺾이는 것보다 낫다**는 판단이다.

### 4.4 `heading_deg` 의 의미 — 호는 "진입" 접선

🔴 `ARC` 의 `heading_deg` 는 **호에 진입할 때의 접선**이다.
`MOVE`/`TURN` 은 진입과 출구가 같아 구분할 필요가 없지만 호는 스윕만큼 다르다.

```
tangent_entry = heading_deg
tangent_exit  = normDeg(heading_deg + (left ? +sweep : −sweep))
```

호에서 서버가 정렬시켜야 할 방위가 곧 진입 접선이라(접근 단계의 마지막 회전이 이 값을 쓴다)
계약상 이쪽이 자연스럽다. 출구 접선은 서버가 스윕을 더해 만든다.

한편 `OpMeta` 에 실리는 `headingDeg`/`exitHeadingDeg` 는 접선이 아니라
**차체 방위**(= 접선 + `φ`)다. `ALIGN` 목표와 `MORE` 투영축이 전부 이 값을 쓰는데,
pose 의 `theta` 가 곧 차체 방위이기 때문이다.
접선을 넣으면 호 진입 `ALIGN` 이 매번 `φ` 만큼 어긋난 곳으로 정렬시킨다.

> ⚠️ 이 항목은 한 번 뒤집혔다가 되돌아왔다(2026-08-07 진입으로 확정).
> 부분호가 스윕만큼 틀어지면 Qt 쪽이 출구 접선을 싣고 있는지 먼저 확인할 것.
> 온전한 원(`sweep = 360°`)은 정규화로 상쇄돼 우연히 맞으므로
> **'O'/'ㅇ' 만 테스트하면 드러나지 않는다.**

### 4.5 최소 도색 반지름 — 기하 하한과 모터 하한은 다르다

**기하 하한 = `a`.** `R_paint = √(R_robot² + a²) ≥ a` 이므로
노즐이 그릴 수 있는 가장 작은 원의 반지름은 정확히 `a` 이고, 그 경우가 제자리 회전이다.
그보다 빡빡한 원은 어떤 바퀴 속도 조합으로도 그릴 수 없다.

**실사용 하한 = `min_paint_radius_m`(현재 `0.200 m`) ← 서버가 실제로 검사하는 값.**
기하가 허용해도 모터가 못 낸다. 호에서 바깥 바퀴 속도는

```
SPS_바깥 = base_sps × (R_robot + W/2) / R_robot        (base_sps = 771.65, 0.05 m/s)
```

이고 `1/R_robot` 으로 **발산**한다.

| `R_paint` | `R_robot` | 바깥 바퀴 SPS | |
|---|---|---|---|
| 0.156 | 0.0176 | 4403 | 탈조 |
| 0.170 | 0.0698 | 1689 | 위험 |
| **0.180** | 0.0915 | **1450** | 마진 하한선 |
| **0.200** | 0.1264 | **1278** | ✅ 권장 — 현재 기본값 |
| 0.300 | 0.2569 | 1021 | 여유 |

NEMA 17(3200 steps/rev) 기준 **2000 SPS 를 넘으면 토크가 떨어져 탈조 위험**
(로봇팀 회신 2026-08-07).

- 도면에 더 빡빡한 호가 있으면 서버가 도면을 거부한다 →
  `DRAW_FAIL{stage:"plan", reason:"arc_too_tight"}`
- `min_paint_radius_m` 은 `pen_offset_m` 미만으로는 내려가지 않는다(기하 하한에서 clamp).

> 🔴 **속도를 바꾸면 이 하한도 바뀐다.** 위 표는 호 주행 속도가 `0.05 m/s` 로
> 고정돼 있다는 전제다. 더 빠르게 돌면 같은 반지름에서 SPS 가 비례해 올라간다.

## 5. 도색 언더슛 — 일부러 덜 가고 실측으로 메운다

개루프로 한 번에 명령하면 지나치기 쉽다. 그래서 **도색 직선만** 일부러 덜 명령하고,
남은 만큼은 `MORE` 피드백이 CCTV 실측 기준으로 채운다.

```
도색 move 명령값 = max(min_move_m, (L + w) − paint_undershoot_m)
MORE 목표        = 그대로 (줄이지 않는다)
```

- 🔴 **목표는 줄이지 않는다.** 명령만 줄여야 그 차이가 다음 지점에서 오차로 잡힌다.
  목표까지 줄이면 메울 오차가 사라져 그냥 짧게 그은 선이 된다.
- 보정 시점에는 노즐이 아직 내려가 있어서(`nozzle(up)` 은 그다음 op) 남은 구간도 이어서 칠해진다.
- **호는 제외한다** — `MORE` 가 호 끝에 접선 직선을 덧붙이는 방식이라 덜 그으면 원이 찌그러진다.
- **오프셋 다리도 제외한다** — 펜이 올라가 있어 덜 갈 이유가 없고, 경로 맨 끝의 후진 다리는
  뒤에 `READY` 가 없어 `MORE` 로 메울 수도 없다.
- 도착 꼭짓점을 모르는 구간도 제외한다(`MORE` 자체가 안 걸린다).

⚠️ `paint_undershoot_m` 은 `more_deadband_m` 보다 커야 한다. 이하면 `MORE` 가
"보정 불필요"로 판정해 **덜 그은 채로 끝난다.** 서버가 기동할 때 `WARN` 을 남긴다.

## 6. 전체 예시

한 변 `2 m` 사각형의 첫 두 변. `role` 은 관찰용 메타데이터일 뿐 로봇 동작을 바꾸지 않는다.

```
op0  move   role=offset   +(a−h)        펜을 시작 꼭짓점보다 h 앞에 놓는다
op1  nozzle role=offset   down
op2  move   role=path     +(L+w)−undershoot    ← 도색. MORE 가 나머지를 채운다
op3  nozzle role=offset   up
op4  move   role=offset   −(a+h)        마커 중심을 꼭짓점으로 복귀
op5  turn   role=path     −90°          (서버 내부 CCW +90° → 로봇 대면 −90°)
op6  move   role=offset   +(a−h)
op7  nozzle role=offset   down
op8  move   role=path     +(L+w)−undershoot
...
```

## 7. 검증

이 문서의 계산은 오프라인 테스트로 고정돼 있다. 로봇·카메라 없이 돌아간다.

```bash
cd Server
make offset_feedback_test && ./tools/offset_feedback_test
```

생성된 op 시퀀스를 눈으로 볼 수 있게 찍어주고, 아래를 검사한다.

1. 오프셋 전진 다리가 시작 꼭짓점을 목표로 잡는가
2. 오프셋 후진 다리가 종료 꼭짓점을 목표로 잡는가
3. 도색 move 의 기존 보정이 그대로인가 (회귀 확인)
4. 오프셋 보정이 노즐이 올라가 있을 때만 실행되는가
5. 펜 두께 보정 — 펜이 실제로 `[V0−h, V1+h]` 를 지나는가
6. 도색 언더슛 — 명령만 줄고 목표는 그대로인가

호 관련 검증은 `make draw_test` 후 `./tools/draw_test --arc 0.5` 를 쓴다.
자세한 것은 [tools/README](../tools/README.md) 참고.
