## 1. Qt 경로 의미 — 서버 해석과 일치합니다

§2~§3을 코드와 대조했습니다. 어긋나는 곳이 없습니다.

| Qt가 보내는 값 | 서버 해석 |
|---|---|
| `points` = 바닥 미터, 노즐 자취 | 그대로 사용. **픽셀 재변환 없음** — 맞습니다 |
| `paint[i]` = `points[i-1]→points[i]` 도색 여부 | 동일. 길이가 `points`와 다르면 이 필드만 무시하고 전 구간 도색 |
| `paint[0]` 항상 false | 서버도 대응 구간이 없어 무시합니다 |
| `heading_deg` = 바닥 CCW 양수 절대 방위 | 동일. 로봇 송신 직전에만 부호를 뒤집습니다 |
| `v` = 출발 꼭짓점 index | **필수**. 없으면 도면 거부(`bad_program`) — MORE의 목표 좌표원입니다 |
| `TURN.angle_deg` CCW 양수 | 동일 |
| `ARC.radius_m` = 도면상 노즐 반지름 | 서버가 `R_robot = sqrt(r² - 0.155²)`로 바꿔 로봇에 보냅니다 |
| `ARC.dist_m` | **서버가 쓰지 않습니다.** v2 로봇 arc 정지 조건이 바퀴중심 기준이라 펜 기준 호 길이와 다릅니다 |
| 속도·SPS·서보 시간 미전송 | 서버도 기대하지 않습니다 |

**도색 ARC 0.200m 하한**: 서버도 같은 값으로 거부합니다(`DRAW_FAIL{arc_too_tight}`).
`params().min_paint_radius_m`에 있고 `config/params.json`으로 조정됩니다.

> ⚠️ 이 값은 **기하가 아니라 모터가 정한 값**입니다. 호에서 바깥 바퀴 SPS가
> 1/R로 발산하는데, 로봇팀 회신(2026-08-07) 기준 2000 SPS를 넘으면 탈조
> 위험입니다. 로봇 호 주행 속도가 바뀌면 이 하한도 같이 올라갑니다.
> **`LOGIN_OK`로 한계를 내려주는 방향**은 좋습니다 — 다만 지금 넣으면 Qt가
> 서버 재시작 없이는 못 받으므로, 필요해지는 시점에 맞춰 논의하시죠.

**닫힌 도형의 시작점 중복 추가, 도형 간 연결 구간 `paint=false`** — 둘 다 서버가
그대로 받습니다. 여러 도형을 한 폴리라인으로 만드시는 방식에 서버 쪽 제약은
없습니다.

## 2. 노즐 — §6-2, §6-3

### §6-2: 단일 결정 기준은 유지됩니다

`buildDrawOps()`가 `MOVE/ARC.paint` + 펜 오프셋만 보고 최종 nozzle op을 만듭니다.
**Qt의 논리 `NOZZLE`은 서버가 버립니다.** 노즐 타이밍이 펜 오프셋 보정 op과 한
몸이라(노즐 down = 차체 중심이 꼭짓점보다 0.155m 앞) 분리할 수 없습니다.

"서버 단일 소유 방식도 수용 가능, 두 의미를 혼합하지만 않으면 된다"에 동의합니다.
Qt는 종전대로 `NOZZLE`을 넣어 보내셔도 되고 빼셔도 됩니다.

### §6-3: 🔴 지적이 맞았습니다 — 통과하고 있었습니다

```cpp
manualCmd = FORWARD | BACKWARD | TURN_LEFT | TURN_RIGHT | STOP
if (manualCmd && planActive_) { 무시 }
```

`NOZZLE_DOWN`/`NOZZLE_UP`/`PAINT_ON`/`PAINT_OFF`가 목록에 없어 **도색 중에도 그대로
로봇까지 갔습니다.** 로봇은 그 넷을 실제로 처리합니다(`main.cpp:112-115`).
서보가 뒤집히면 **다음 nozzle op이 올 때까지 반대 상태로 그립니다.**

**수정**: 노즐 명령도 `planActive_` 중에는 차단합니다.

```cpp
nozzleCmd = NOZZLE_DOWN | NOZZLE_UP | PAINT_ON | PAINT_OFF
if ((manualCmd || nozzleCmd) && planActive_) { 무시 }
```

⚠️ **`manualCmd` 목록에 합치지는 않았습니다.** 그 목록은 차단 말고 한 가지를 더
합니다 — 서버를 "수동 모드"로 바꿔 ALIGN/MORE/DRIFT를 멈추는 래치입니다. 노즐은
로봇을 움직이지 않으니 자동 판정과 충돌할 일이 없고, 합쳤다면 **대기 중 노즐
점검 한 번에 다음 작업 전체가 개루프로 도는** 부작용이 생겼을 겁니다.
(그 래치 자체가 §3의 문제였습니다.)

⚠️ **관리자 창은 이 차단을 받지 않습니다.** `fromAdmin`은 판정 자체를 거치지
않고 바로 로봇으로 보냅니다 — 점검·설치용으로 의도적으로 열어둔 경로입니다.
결과적으로 **Qt는 막히고 관리자 창은 열린** 상태가 되는데, 수동 노즐 탈출구가
한 군데는 남아야 하므로 이 배치가 맞다고 봅니다. 이견 있으시면 알려주세요.

## 3. 🔴 검토 중 발견 — 수동 모드 래치가 작업 전체를 개루프로 만들었습니다

§6-3을 확인하다 나온 것으로, **노즐보다 영향이 큽니다.**

### 증상

```
BLUEPRINT 전송 → 대기 중 조이스틱으로 로봇 위치 조정 → START_DRAW
  → 그 작업 전체가 ALIGN / MORE / DRIFT 없이 개루프 주행
```

`manualMode_`는 조이스틱 명령에 켜지고 **새 `BLUEPRINT`가 와야만** 꺼졌습니다.
그래서 "도면 올리고 → 로봇 위치 잡고 → 시작"이라는 지극히 자연스러운 순서를
밟으면 피드백이 통째로 죽었습니다. 복구하려면 도면을 다시 보내야 했고요.

**조용히 도색 품질만 나빠지는 종류라 로그에도 드러나지 않았습니다.**
(v1에서 DRIFT 없이 최대 -40도까지 틀어진 실측이 있습니다.)

### 재현 및 확인

`tools/draw_test`에 `--nudge` 옵션을 추가했습니다 — `BLUEPRINT_OK` 직후
`START_DRAW` 전에 조이스틱 명령을 한 번 끼워 위 순서를 그대로 재현합니다.

같은 시나리오, 같은 도면, `robot_sim` 상대로:

| | GO 사유 "수동 모드" | ALIGN/MORE/DRIFT 판정 |
|---|---:|---:|
| 수정 전 | **26건** (전부) | **0건** |
| 수정 후 | **0건** | 정상 수행 |

### 수정

`START_DRAW`에서 래치를 풉니다. 그 시점에는 유지할 이유가 없습니다 — 서버가
접근 경로를 **지금 pose에서 새로 만들기** 때문에 "서버가 든 경로가 낡았다"는
전제 자체가 사라집니다. 해제는 이제 **새 BLUEPRINT 또는 START_DRAW** 두 곳입니다.

주행 중 수동 조작은 예전처럼 그대로 차단되므로, 경로 실행 중에 래치가 켜질 일은
없습니다.

## 4. §6-4: `DRAW_ABORTED`는 접수 ACK입니다

**물리 정지 완료 ACK가 아닙니다.** 서버가 `ABORT_DRAW`를 로봇에 중계하고 자기
경로 상태를 비운 직후 보냅니다. `was_active`는 "서버가 버릴 경로를 갖고 있었나"일
뿐, 로봇 바퀴가 섰는지와는 무관합니다.

2026-08-07 회신에도 같은 내용을 적었고, 그때 Qt팀이 정리해주신 주의사항과 동일합니다.

**호모그래피 취소는 일부러 다른 규약으로 만들었습니다.** `CALIB_CANCELLED`는
ROBOT·CCTV 양쪽의 `CALIB_STOPPED`를 받은 **뒤에만** 나갑니다. 캘리 중에는 Qt가
전체 화면 대기 상태라 조작자가 화면만 보고 있는데, 거기서 "중단됨"을 먼저 띄우면
아직 굴러가는 로봇 쪽으로 사람이 걸어갑니다.

`ABORT_DRAW`도 같은 규약으로 바꿀 수 있습니다. 다만 **로봇이 정지 완료 ACK를 새로
보내줘야** 하므로 로봇팀 작업이 선행됩니다 — 로봇팀 문서 §4.3에서 이미 물어보고
계시니 그 답을 보고 정하시죠. 서버는 어느 쪽이든 맞춥니다.

### 최종 물리 상태 판단 기준 (현재)

| 상황 | Qt가 받는 것 | 물리 상태 보장? |
|---|---|---|
| 정상 완료 | `DRAW_DONE` | 로봇 `PATH_DONE(draw)`이 트리거 — 로봇이 끝냈다고 말한 것 |
| 중단 | `DRAW_ABORTED` | ❌ 접수 ACK |
| ESTOP | (별도 응답 없음) | ❌ 로봇 `STATUS.state`로 판단 |
| 로봇 연결 단절 | `DRAW_FAIL{robot_offline}` | ❌ 서버가 끊김을 감지한 것뿐 |
| 캘리 취소 | `CALIB_CANCELLED` | ✅ 양쪽 정지 확인 후 |

**즉 지금 물리 상태를 보장하는 것은 `CALIB_CANCELLED` 하나뿐입니다.** 나머지는
로봇 `STATUS`(500ms 주기, `state`/`painting`)를 기준으로 표시하셔야 합니다.
"`STATUS.painting`을 실제 상태 표시 기준으로 사용하는 방향"이 맞습니다 — 다만
그 값이 실제 서보를 반영하는지는 로봇팀 §4 확인 결과에 달려 있습니다.

## 5. §6-5: 종단간 시험 준비 상태 — 아직 불가

호모그래피 회신 §3과 같습니다. 서버는 준비됐지만 두 가지가 막고 있습니다.

- **CCTV**: `CALIB_START`를 JSON 파싱 없이 문자열 검색으로만 처리해
  `ch`/`request_id`가 카메라 앱 경계에서 소멸합니다 (`central_tls_sender.cpp:90`)
- **로봇**: `CALIB_START` 핸들러가 없어 조용히 무시됩니다 (`main.cpp:66-115`).
  계약의 `method`가 `"robot_motion"`인데 주행 명령을 모릅니다

**서버 쪽 준비 상태**:

| 항목 | 상태 |
|---|---|
| 세션 상태기계 (`router_calib.cpp`) | ✅ 회귀 테스트 21/21 |
| `CALIB_STOPPED` 수신 처리 | ✅ 대기 중 (양쪽 미구현이라 현재는 5초 뒤 `cancel_failed`) |
| 노즐 차단 · 수동 모드 래치 | ✅ 이 회신의 수정분 |
| C++ 서버 프로세스 | ⚠️ **현재 미기동** — 새 바이너리로 띄워야 위 계약이 적용됩니다 |

## 7. Qt팀에 필요한 회신

1. **수동 노즐이 관리자 창에만 열려 있는 배치**가 괜찮은지 (§2). Qt UI도 이미
   막고 계시니 실무상 차이는 없을 것으로 봅니다.
2. **`ABORT_DRAW`를 `CALIB_CANCELLED`와 같은 "정지 확인 후" 규약으로 바꿀지** (§4).
   로봇팀 §4.3 답변을 보고 결정하시면 됩니다.
3. **`min_paint_radius_m`을 `LOGIN_OK`로 내려주는 건**, 지금 넣으면 Qt가 서버
   재시작 없이 못 받습니다. 필요해지는 시점에 다시 논의하시죠 (§1).

§1·§2-2·§4는 확인·설명이므로 회신이 필요 없습니다.
