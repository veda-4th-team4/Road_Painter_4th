# 서버 ↔ 로봇 프로토콜 v2 (server-driven)

**상태: 초안 (구현 전)**
대상 브랜치: `feature/server-driven-v2`
작성 기준일: 2026-08-05

이 문서는 **서버와 로봇 사이 구간만** 규정한다. Qt ↔ 서버, CCTV ↔ 서버 구간은
v1(`Server/server_PROTOCOL.md`, `Server/src/protocol.hpp`)에서 **바뀌지 않는다**.

---

## 0. v1 대비 무엇이 바뀌는가

| 항목 | v1 | v2 |
|---|---|---|
| 각도 부호 | 양수 = 좌회전(CCW) | **양수 = 우회전(CW)** |
| op 이름 | `MOVE` / `TURN` / `NOZZLE` / `ARC` | `move` / `turn` / `nozzle` / `arc` (소문자) |
| 펜 오프셋 보정 | **로봇**이 자기 하드웨어 상수로 자율 처리 | **서버**가 경로에 보정 op을 끼워 넣음 |
| 노즐 op 생성 | Qt가 `program`에 직접 넣음 | **서버가 전부 재생성** (Qt NOZZLE은 버림) |
| 핸드셰이크 단위 | MOVE 앞에서만 READY | **모든 op마다** READY → GO |
| 동작 식별자 | `seg` (segments 배열 index) | `op_index` (경로 전체 통일, 서버가 부여) |
| 피드백 | ALIGN / DRIFT | **ALIGN / MORE / DRIFT** (MORE 신설) |
| 이탈 재계획 | 0.3m 이탈 시 복귀 PATH 재전송 | **폐지** (피드백 3종으로만 보정) |
| POS 두절 | 대응 없음 | **HOLD** 로 즉시 정지 / 복구 시 재개 |
| 배열 필드명 | `segments` | `ops` |

**폐지되는 서버 코드**: `buildRecovery`, `advanceCursor` / `planCursor_`,
`distToActiveSegment`, `pointSegDistExt`, `kDevThresholdM`, `kReplanCooldownMs`.

**유지되는 서버 코드**: `calib.hpp` 전체, `poseFromPos`, `normDeg`,
POS 이상치 게이트(`kPoseGateBaseDeg` / `kPoseGateRateDps` / `kPoseRejectMax`),
`user_store`, `tls_server`, Qt/CCTV 핸들러 전부.

## 1. 좌표계와 부호 규약

### 1.1 서버 내부 (v1과 동일 — 바뀌지 않음)

- 월드 = 바닥 평면, 단위 미터.
- `pose.theta` = **반시계(CCW) 양수**, +x축 기준. (`poseFromPos`, `atan2`)
- Qt `heading_deg`, Qt `TURN.angle_deg` = **반시계 양수**.

### 1.2 로봇 대면 (v2에서 반전)

> 🔴 **로봇에게 나가는 모든 각도는 "양수 = 오른쪽으로 그만큼 틀어라"다.**

`turn.angle_deg`, `ALIGN.angle_deg`, `DRIFT.angle_deg` 전부 해당한다.
`arc.angle_deg`는 예외로 **항상 양수(회전량 크기)**이고 방향은 `direction`이 갖는다.

### 1.3 변환식 (서버가 송신 직전에 1회 적용)

```
angle_robot = -angle_ccw
```

| 계산 | CCW 기준 (서버 내부) | 로봇에 보낼 값 |
|---|---|---|
| Qt TURN 중계 | `qt.angle_deg` | `-qt.angle_deg` |
| ALIGN | `err = normDeg(target_heading - theta_deg)` | `-err` |
| DRIFT | `err = normDeg(target_heading - theta_deg)` | `-err` |

**검산**: 로봇 `theta`=30°, 목표 `heading`=40°.
왼쪽으로 10° 돌아야 함 → `err = +10` → 로봇에 `-10` 전송 → "왼쪽 10°". ✅

> ⚠️ v1 DRIFT 주석("값 = 좌회전으로 보정해야 할 양")은 v2에서 **정확히 부호가 반대**다.
> 로봇 실행부에서 v1 코드를 재사용할 때 이 지점이 가장 조용히 깨진다.

## 2. 메시지 카탈로그

공통 형식은 v1과 동일: `{"type":"...", "seq":n, "payload":{...}}` + `\n` (TLS 위 JSON Lines).

### 2.1 서버 → 로봇

| type | payload | 설명 |
|---|---|---|
| `PATH` | `{"phase":"approach"\|"draw", "ops":[...]}` | 경로 전체. 받는 즉시 기존 경로 폐기. |
| `GO` | `{"op_index":n}` | op n 실행 허가 |
| `ALIGN` | `{"op_index":n, "angle_deg":±d}` | 제자리 미세 회전 후 **같은 op_index로 READY 재전송** |
| `MORE` | `{"op_index":n, "dist_m":±m}` | 현재 방향으로 전/후진 후 **같은 op_index로 READY 재전송** |
| `DRIFT` | `{"op_index":n, "angle_deg":±d}` | 직진 주행 **중** 각도 보정 (READY 불필요) |
| `HOLD` | `{"hold":true\|false, "reason":"pos_lost"}` | 즉시 정지 / 재개 |
| `CMD` | `{"cmd":...}` | v1 그대로 (ESTOP/RESUME/수동조작/CALIB_START) |

### 2.2 로봇 → 서버

| type | payload | 설명 |
|---|---|---|
| `HELLO` | `{"role":"ROBOT"}` | v1 그대로 |
| `STATUS` | `{"state":..., "painting":bool}` | v1 그대로. 500ms 주기, 하트비트 겸용 |
| `READY` | `{"op_index":n}` | **op n을 실행해도 되는지** 묻는다 (아래 §3) |
| `PATH_DONE` | `{"phase":"approach"\|"draw"}` | 마지막 op까지 마쳤을 때 1회 |

`READY` / `PATH_DONE` 외에 로봇이 자발적으로 보내는 것은 `STATUS`뿐이다.

## 3. op_index 와 READY/GO 핸드셰이크

### 3.1 op_index 의미

> 🔴 `READY.op_index` = **"이제부터 실행하려는" op의 index** (완료한 op이 아니다)

- 서버가 `PATH`를 만들 때 0부터 빈틈없이 부여한다. 오프셋 보정 op도 같은 번호를 먹는다.
- `PATH` 하나 안에서만 유효하다. 새 `PATH`를 받으면 다시 0부터.
- 로봇은 자기가 기다리는 index와 다른 `GO`/`ALIGN`/`MORE`/`DRIFT`는 **조용히 버린다.**
  (지연 도착한 이전 경로의 응답이 새 경로를 움직이는 것을 막는다)

### 3.2 흐름

```
로봇                          서버
 │  PATH 수신                  │
 ├── READY{0} ────────────────>│   op 0 실행해도 되나?
 │<────────────── GO{0} ───────┤   (또는 ALIGN/MORE 먼저)
 │  op 0 실행                   │
 ├── READY{1} ────────────────>│
 │<────────────── GO{1} ───────┤
 │  op 1 실행                   │
 │        ...                   │
 │  마지막 op(N-1) 실행         │
 ├── PATH_DONE{phase} ────────>│   READY{N}은 보내지 않는다
```

- `ALIGN` / `MORE`를 받으면 로봇은 그 동작을 수행하고 **같은 op_index로 READY를 다시** 보낸다.
- `GO`를 받아야만 다음 op으로 넘어간다. 서버가 응답을 빠뜨리면 로봇은 영원히 멈춘다 —
  **서버는 모든 READY에 반드시 응답 하나를 낸다.**

## 4. op 사양 (`PATH.ops` 원소)

모든 op의 공통 필드:

| 필드 | 타입 | 설명 |
|---|---|---|
| `op` | string | `"turn"` / `"nozzle"` / `"move"` / `"arc"` |
| `op_index` | int | 0부터 연속 |
| `role` | string | `"path"` (도면 동작) / `"offset"` (서버가 끼운 보정) |

> 🔴 **`role`은 관측용 메타데이터다. 로봇은 `role`을 읽지 않으며, 값에 따라 동작을 바꾸지 않는다.**
> 로그·디버깅·서버 재현용이다. 로봇 실행부에 `role` 분기가 생기면 그 자체가 버그다.

### 4.1 `move`

```json
{"op":"move", "role":"path", "dist_m":1.2, "op_index":5}
```
- `dist_m` 음수 = 후진. 바라보는 방향은 바뀌지 않는다.

### 4.2 `turn`

```json
{"op":"turn", "role":"path", "angle_deg":-90.0, "op_index":5}
```
- 제자리 회전. **양수 = 오른쪽.**

### 4.3 `nozzle`

```json
{"op":"nozzle", "role":"offset", "down":false, "op_index":2}
```
- 노즐 상태를 바꾸는 유일한 op. `move`에는 `paint` 필드가 **없다** (v1과 다름 — §5 참고).
- 로봇은 액추에이터가 완전히 착지/상승할 때까지 **약 1.0초 정지 대기** 후 READY를 보낸다
  (로봇팀 기구학 다이어그램 2·4단계). 서버는 이 op에 즉시 `GO`를 주므로 프로토콜상
  추가 대기는 없지만, **꼭짓점 하나당 노즐 op 2개 = 약 2초**가 실행 시간에 붙는다.

### 4.4 `arc`

```json
{"op":"arc", "role":"path", "radius_m":0.476, "angle_deg":180.0,
 "direction":"right", "op_index":7, "radius_draw_m":0.5}
```

| 필드 | 설명 |
|---|---|
| `radius_m` | **로봇 마커 중심이 그려야 할** 회전 반지름 (실행값) |
| `angle_deg` | 회전량 **크기, 항상 양수** |
| `direction` | `"left"` / `"right"` |
| `radius_draw_m` | (참고용) 도면상 펜 자취 반지름. 로봇은 무시 |

#### 실행 방식 — 직선 근사가 아니다

> 🔴 **`arc` op 하나 = 좌우 바퀴 속도비를 고정한 채 완주하는 한 번의 연속 곡선 주행.**
> 짧은 직선의 조합으로 쪼개지 않는다.

```
R_L = radius_m - W/2                   (안쪽 바퀴, W = 축간거리 ≈ 0.167m)
R_R = radius_m + W/2                   (바깥쪽 바퀴)
SPS_L : SPS_R = R_L : R_R              주행 내내 고정
정지 조건: 바퀴중심 이동거리 = radius_m × θ_rad
```
(`direction="left"`면 좌측이 안쪽, `"right"`면 우측이 안쪽)

#### 펜 보정이 직선과 다르게 들어간다

| | 직진 `move` | 곡선 `arc` |
|---|---|---|
| 보정 방법 | **별도 op을 앞뒤에 삽입** (`+d` / `-d`) | **`radius_m` 값 자체에 녹임** |
| 로봇이 아는 것 | "d만큼 더 가라"는 명령 | 없음 — 시킨 반지름으로 돌 뿐 |

반지름 치환 하나로 끝나는 이유: 노즐의 회전반지름은 바퀴중심 회전반지름의 고정된
기하 함수(`sqrt(radius_m² + d²)`)이고 **쓸어가는 각도가 둘이 완전히 같다**(§5.4).
주행 내내 성립하는 관계라 중간 보정이 필요 없다.

> 📐 **실측 예시 (도면 200mm 원호 주행 시)**:
> - 도면 목표 반지름 $R_{draw} = 0.200\text{m}$ ($200\text{mm}$)
> - 노즐 오프셋 $d = 0.155\text{m}$, 차축 $W = 0.166\text{m}$
> - 서버 전달 `radius_m`: $R_{robot} = \sqrt{0.200^2 - 0.155^2} = \mathbf{0.1264 \text{ m}}$ ($126.4\text{mm}$)
> - 내측 바퀴 $R_{in} = 0.1264 - 0.083 = 0.0434\text{m} > 0$ (정방향 전진)
> - 외측 바퀴 $R_{out} = 0.1264 + 0.083 = 0.2094\text{m}$
> - 좌우 속도 비율 $SPS_L : SPS_R = R_{in} : R_{out} \approx 1 : 4.82$

#### 개루프 구간이다 — 진입 pose가 전부를 결정한다

- `arc` 주행 중에는 `DRIFT`를 보내지 않는다 (§6.3). `GO` 이후 완주까지 서버 피드백이 없다.
- 🔴 **반지름은 위 공식이 보장하지만, 그려지는 원의 "위치"는 진입 pose가 100% 결정한다.**
  ICR이 진입 시점의 중심 좌표와 heading으로 확정되기 때문이다. 진입 각도가 5도 틀어지면
  원 전체가 통째로 어긋난다. 그래서 **arc 진입 전 ALIGN은 직선 앞의 ALIGN보다 중요하다**
  (§6.1에서 arc 진입 boundary를 별도 항으로 둔 이유).

#### v1 → v2 마이그레이션 체크리스트 (ARC)

공식 부호만 뒤집는 것으로는 부족하다. **세 곳**이 바뀐다.

| # | 위치 | v1 | v2 | 안 고치면 |
|---|---|---|---|---|
| 1 | **로봇** | 자체 보정 `√(R²+d²)` 수행 | **보정 코드 삭제.** `radius_m`을 받은 그대로 사용 | **이중 보정** |
| 2 | **로봇** | 정지 조건 = Qt `dist_m` (펜 기준 호 길이) | 정지 조건 = `radius_m × θ_rad` (바퀴중심 기준) | **과회전** |
| 3 | **서버** | 없음 | `R_paint < d`면 도면 거부 (§5.5) | `√` 안이 음수 → **NaN 전파** |

**① 이중 보정이 왜 위험한가** — 서버가 이미 보정한 값에 로봇이 또 보정하면

```
R_exec = sqrt(R_robot² - d²) = sqrt(R_paint² - 2d²)
```

`R_paint = 0.5` → `0.4489` (정답 `0.4754` 대비 5.6% 작은 원).
`R_paint < d*sqrt(2) ≈ 0.219`에서는 **루트 안이 음수가 되어 그대로 터진다.**

**② 과회전이 왜 생기나** — `R_robot < R_paint`이므로 바퀴중심 호 길이는 펜 호 길이보다
짧다. 펜 기준 길이로 스텝을 세면 그 비율만큼 더 돈다.
`R_paint = 0.5`, 180° 기준 약 **9° 과회전**. v2에는 `dist_m` 필드 자체가 없으므로
자연히 걸러지지만, v1 코드를 복사해 오면 조용히 살아남는 종류의 버그다.

**바뀌지 않는 것**: `angle_deg`(스윕 각도), `direction`, SPS 속도 분배식.
스윕 각도가 보존되는 이유는 노즐 편각이 바퀴중심 편각보다 `atan(d/radius_m)`만큼
**일정하게** 뒤처지기 때문이다 — 상수 차이라 각속도에는 영향이 없다 (§5.4).

#### 작은 반지름에서 안쪽 바퀴가 역회전한다

`radius_m < W/2 ≈ 0.0835m`이면 `R_L`이 음수가 된다 — 이는 `R_paint < 0.176m`에 해당한다.
기구학적으로는 정상(제자리 회전에 가까운 선회)이다.

✅ **모터 드라이버는 좌우 반대 방향 동시 구동을 지원한다** (로봇팀 회신 2026-08-07).
따라서 역회전 자체는 하한을 결정하지 않는다. 실사용 하한 `0.200m`은 **바깥 바퀴
SPS 발산** 때문에 정해진 것이고, 그 값이 0.176보다 커서 역회전 구간은 어차피 도면
단계에서 걸러진다 (§5.5).

## 5. 펜 오프셋 보정 — 서버 생성 규칙

### 5.1 전제

- `a = 0.155 m` = 마커 중심 → 펜(노즐)까지 거리. 펜은 **중심 뒤**에 있다.
- **`phase="draw"`에서만 적용한다.** `phase="approach"`에는 보정 op을 넣지 않는다
  (접근 중엔 펜 위치를 고려할 이유가 없다).

### 5.2 불변식

> **노즐이 내려가 있다 ⟺ 마커 중심이 도면 꼭짓점보다 진행방향으로 정확히 `a` 앞서 있다.**
> **노즐이 올라가 있다 ⟺ 마커 중심이 도면 꼭짓점 위에 있다.**

보정 op은 이 두 상태를 오갈 때만 삽입된다.

### 5.3 변환 알고리즘

입력: Qt `program` (대문자 `MOVE`/`TURN`/`NOZZLE`/`ARC`, CCW 양수, `v`/`paint`/`heading_deg` 포함)
출력: 로봇 `ops`

```
Qt의 NOZZLE op은 전부 버린다.          // 서버가 노즐 타이밍을 다시 만든다
penDown = false                          // draw 시작 시점: 노즐 up, 중심 = points[0]

for each qtOp in program:
    isPaint = (qtOp.op == "MOVE" or "ARC") and qtOp.paint == true

    if isPaint and not penDown:          // 도색 진입
        emit move(+a,  role=offset)      // 노즐은 이미 up이므로 올리는 op은 불필요
        emit nozzle(down=true, role=offset)
        penDown = true

    if not isPaint and penDown:          // 도색 이탈 (turn / 비도색 이동 직전)
        emit nozzle(down=false, role=offset)
        emit move(-a, role=offset)
        penDown = false

    emit convert(qtOp, role=path)        // 소문자화 + 부호반전 + arc 반지름 보정

if penDown:                              // 경로 끝
    emit nozzle(down=false, role=offset)
    emit move(-a, role=offset)

op_index를 0부터 순서대로 부여한다.
```

**설계 노트**
- 원 요구사항은 "직진할 때 노즐 올리고 `a` 더 가서 내리고", "turn 할 때 노즐 올리고
  `a` 뒤로 가고 turn"이었다. 위 알고리즘은 그것을 불변식으로 다시 쓴 것으로,
  결과가 동일하면서 **연속 도색 move 사이에 불필요한 up/내리기가 끼지 않는다**
  (꼭짓점 회전각이 0에 가까워 Qt가 TURN을 생략한 경우).
- 도색 진입 시 "노즐 올리기"가 없는 이유: `penDown == false`이므로 노즐은 이미 up이다.
- 이 규칙 덕에 **노즐 op은 자동으로 down/up 교대**가 보장된다 (v1의 알터네이션 규약 유지).

### 5.4 `arc` 반지름 보정

> 🔴 **직각은 C(바퀴 중심)에 있다. N(노즐)이 아니다.**
> 이 한 가지가 공식의 부호를 가른다.

차동구동 로봇의 **ICR은 반드시 좌우 바퀴 축선 위에 있다.** 축선은 C를 지나고
차체축(C→N 방향)에 수직이다. 따라서

```
ICR→C  ⊥  C→N          →  직각의 꼭짓점 = C
빗변   =  ICR→N        =  R_paint
```

```
R_paint  = sqrt(R_robot² + d²)          ← 노즐이 바퀴 중심보다 "멀리" 돈다
R_robot  = sqrt(R_paint² - d²)          ← 서버가 로봇에 보낼 값
```

**검산 — 제자리 회전 (`R_robot = 0`)**

바퀴 중심은 그 자리에 서 있고 노즐만 반지름 `d = 0.155m` 원을 그린다(자명한 사실).

| 공식 | `R_robot = 0`일 때 예측 `R_paint` | 판정 |
|---|---|---|
| `R_robot = sqrt(R_paint² + d²)` | `R_paint = 0` (노즐도 제자리) | ✗ 물리와 불일치 |
| `R_robot = sqrt(R_paint² - d²)` | `R_paint = 0.155` | ✅ |

- 스윕 각도 `angle_deg`는 **보정하지 않는다.** N의 편각은 C의 편각보다 `atan(d/R_robot)`
  만큼 **일정하게** 뒤처질 뿐이라, 둘이 쓸어가는 각도는 같다.

> ⚠️ **로봇팀 기구학 다이어그램(2026-08-05)의 `R_robot = sqrt(R_paint² + d²)`는
> 직각을 N에 둔 것이다.** 그러려면 ICR이 N을 지나는 축선 위에 있어야 하고, 그건 노즐
> 위치에 바퀴가 달렸다는 뜻이 된다. 같은 다이어그램의 5단계 시퀀스(+15.5 → 노즐다운 →
> 주행 → 노즐업 → −15.5)는 §5.3 알고리즘과 정확히 일치하므로 그대로 유효하다.
> 바퀴 속도 분배(`SPS_L/R = SPS_base × R_L/R ÷ R_robot`)도 그대로 유효하되,
> 입력 `R_robot` 값이 위 식으로 바뀐다.

### 5.5 도색 가능한 최소 반지름 — 이론 `d`(0.155m), **실사용 `0.200m`**

두 개의 서로 다른 하한이 있다. 헷갈리기 쉬우니 구분해서 적는다.

#### 이론 하한 = `d` = 0.155m (기하)

`R_paint = sqrt(R_robot² + d²) ≥ d` 이므로:

> **노즐이 그릴 수 있는 가장 작은 원의 반지름은 정확히 `0.155m`이고, 그 경우가
> 제자리 회전이다.** 그보다 빡빡한 원은 어떤 바퀴 속도 조합으로도 그릴 수 없다.

#### 실사용 하한 = **0.200m** (모터) ← 서버가 실제로 검사하는 값

기하가 허용해도 모터가 못 낸다. 호에서 바깥 바퀴 속도는

```
SPS_바깥 = base_sps × (R_robot + W/2) / R_robot        (base_sps = 771.65, 0.05 m/s)
```

이고 `1/R_robot`으로 **발산**한다.

| `R_paint` | `R_robot` | 바깥 바퀴 SPS | |
|---|---|---|---|
| 0.156 | 0.0176 | 4403 | 탈조 |
| 0.170 | 0.0698 | 1689 | 위험 |
| **0.180** | 0.0915 | **1450** | 마진 하한선 |
| **0.200** | 0.1264 | **1278** | ✅ 권장 — 현재 기본값 |
| 0.300 | 0.2569 | 1021 | 여유 |

로봇팀 회신(2026-08-07): NEMA 17(3200 steps/rev) 기준 **2000 SPS를 넘으면 토크가
떨어져 탈조(스킵) 위험**. 그래서 `min_paint_radius_m` 기본값을 `0.200`으로 둔다.

- `R_draw < min_paint_radius_m`인 `ARC`가 도면에 들어오면 → 서버가 도면을 거부하고
  Qt에 `DRAW_FAIL{stage:"plan", reason:"arc_too_tight", msg:"최소 도색 반지름 0.200m"}`.
- 이 값은 `config/params.json`의 `min_paint_radius_m`으로 조정 가능하되,
  `pen_offset_m`(0.155) 미만으로는 내려가지 않는다(기하 하한에서 clamp).

> 🔴 **속도를 바꾸면 이 하한도 바뀐다.** 위 표는 로봇의 호 주행 속도가
> `base_sps = 771.65`(0.05 m/s)로 고정돼 있다는 전제다. 호를 더 빠르게 돌게 되면
> 같은 반지름에서 SPS가 비례해 올라가므로 하한을 다시 계산해야 한다.

### 5.6 직선↔호 접합부 꺾임

펜이 중심 뒤에 끌려가므로 펜의 **속도 방향**은:

- 직진 중: 차체 방향과 **같다**
- 원호 중: 차체 방향에서 `atan(d / R_robot)`만큼 어긋난다

따라서 직진 → 호 전환점에서 펜 자취에 그만큼의 꺾임이 남는다.
`R_paint = 0.5m` (→ `R_robot = 0.475m`) 기준 **약 18°**.

이것은 끌리는 펜의 기하학적 귀결이라 **주행 중에는** 없앨 수 없다. 그래서 §5.7이
접합부에서 노즐을 한 번 올렸다 내리는 쪽을 택했다 — 펜을 든 채로 위상을 맞추면
꺾임 자체가 자취에 남지 않는다. 획이 끊기는 것이 꺾이는 것보다 낫다는 판단이다.

### 5.7 호 진입 위상 보정 (2026-08-06 구현)

> **도색 호에서는 차체가 접선을 향하면 안 된다.** 접선에서
> `φ = atan(d / R_robot)`만큼 호 안쪽으로 틀어져 있어야 한다.

#### 왜 필요한가

펜 `P`를 도면 원 위에 놓는 것만으로는 부족하다. 회전 중심(ICR)은 반드시 좌우 바퀴
축선 위에 있고 그 축선은 마커 중심 `C`를 지나 진행방향에 수직인데, 도면 원의 중심
`O`에 ICR을 놓으려면 `C`가 `O`에서 `R_robot`, `P`에서 `d`만큼 떨어진 자리여야 한다.

`R_robot² + d² = R_paint²`이므로 이 직각삼각형은 항상 성립하고, 그때 차체 방위는
접선에서 정확히 `φ = atan(d / R_robot)`만큼 틀어진 방향이다.

**검산**: `R_paint = d`(= 최소 도색 반지름, 제자리 회전)이면 `R_robot = 0`이라 `φ = 90°`.
차체가 접선과 직각 — 마커 중심이 원 중심에 가만히 있고 펜만 반지름 `d`로 도는 자명한
사실과 맞는다. 구현은 `atan2(d, R_robot)`을 써서 `R_robot = 0`에서도 터지지 않는다.

#### 안 하면 무슨 일이 생기나

**반지름은 맞는데 원이 통째로 다른 자리에 그려진다.** 드라이런 실측:

| `draw_test --arc 0.5` | 보정 전 | 보정 후 |
|---|---|---|
| 펜 도착점 (도면 `(0, −1.0)`) | `(0.310, −0.950)` ❌ **0.31m 이탈** | `(−0.001, −0.999)` ✅ |
| 펜 자취 반지름 (도면 `0.500`) | `0.4996` ✅ | `0.4997` ✅ |

#### 생성 규칙

`φ`는 CCW 부호를 포함한다 (좌회전 호 `+`, 우회전 호 `−`).

```
진입:  turn(+φ)  →  move(+a)  →  nozzle(down)  →  arc
이탈:  nozzle(up)  →  move(−a)  →  turn(−φ)
```

- 진입 `turn(+φ)`은 로봇이 **진입 접선**을 보고 서 있다는 전제에서 출발한다.
  접근 경로의 마지막 회전과 Qt의 `TURN` op이 그렇게 세워준다.
- 이탈 `turn(−φ)`으로 **반드시 접선으로 되돌린다.** 안 하면 뒤따르는 직선 op이
  전부 `φ`만큼 기운 채로 이어진다.
- 위상이 바뀌는 것은 **도색 상태가 바뀌는 것과 동일하게** 취급한다. 펜을 내린 채
  제자리 회전하면 펜이 반지름 `a`의 호를 그어 버리므로, 직선↔호 접합부에서는
  노즐을 반드시 한 번 올렸다 내린다 (§5.6).
- 도색하지 않는 호는 `φ = 0`이다. 펜이 올라가 있어 마커 중심이 곧 도면 자취다
  (§5.2 불변식의 나머지 절반).

#### `headingDeg` / `exitHeadingDeg`의 의미

`arc` op의 `OpMeta`에 실리는 두 방위는 접선이 아니라 **차체 방위**(= 접선 + `φ`)다.
`ALIGN` 목표와 `MORE` 투영축이 전부 이 값을 쓰는데, pose의 `theta`가 곧 차체 방위이기
때문이다. 접선을 넣으면 호 진입 ALIGN이 매번 `φ`만큼 어긋난 곳으로 정렬시킨다.

#### Qt `heading_deg`의 정의 — ARC는 "진입할 때" (2026-08-07 확정)

🔴 `ARC`의 `heading_deg`는 **"호에 진입할 때의 접선"**이다. `MOVE`/`TURN`은 진입과
출구가 같아 구분이 필요 없지만, **호는 스윕만큼 다르다.**

```
tangent_entry = heading_deg
tangent_exit  = normDeg(heading_deg + (left ? +sweep : −sweep))
```

**호에서 서버가 정렬시켜야 할 방위가 곧 진입 접선**이므로(접근 단계의 마지막 회전이
이 값을 쓴다) 계약상 이쪽이 자연스럽다. 출구 접선은 서버가 스윕을 더해 만든다.

##### 경위 — 한 번 뒤집혔다가 되돌아온 항목

| 시각 | 일 |
|---|---|
| 7/30 | 저장소의 Qt 코드가 **출구** 접선을 실음 (`motionprogram.h` `a.heading = t1`) |
| 8/7 09:09 | 서버가 그 코드에 맞춰 **출구** 기준으로 변경 (`91ec2e2`) |
| 8/7 11:08 | Qt팀 회신 — "이미 **진입** 접선으로 수정·검증 완료" |
| 8/7 | **진입으로 확정**, 서버 되돌림 |

> ⚠️ **미해결**: Qt팀이 회신에 적은 수정이 아직 저장소에 push되지 않았다
> (`Client/src/motionprogram.h` 최신 커밋은 7/30 `b9bd938`, 전 브랜치 확인).
> 그 코드가 들어오기 전까지 저장소 Qt(출구)와 서버(진입)가 어긋나므로
> **부분호는 스윕만큼 틀어진다.** 온전한 원(`sweep = 360°`)은 `normDeg`로 상쇄돼
> 우연히 맞는다 — 'O'/'ㅇ'만 테스트하면 드러나지 않는다는 점에 주의.
> **호 도색 통합 시험은 Qt push 확인 후에 잡을 것.**

## 6. 피드백 3종

### 6.1 판정 시점 — boundary 규칙

> **각 path op의 오차는 그 op이 끝난 직후 boundary에서 교정한다.**
> `turn`의 각도 오차 → `ALIGN`, `move`/`arc`의 거리 오차 → `MORE`.

`READY{k}` 수신 시 (직전 실행 op = `k-1`):

| 조건 | 처리 | 대기 |
|---|---|---|
| `op[k-1]`이 `role=path`인 `turn` | **ALIGN 판정** (최대 6회) | 2초 |
| `k == 0` 이고 `phase == "draw"` | **ALIGN 판정** (첫 주행 op의 heading으로) | 2초 |
| `op[k]`가 `role=path`인 `arc` 이고 위에 안 걸림 | **ALIGN 판정** (진입 **차체** 방위 = 접선 + φ, §5.7) | 2초 |
| `op[k-1]`이 도착 꼭짓점을 아는 `move` 또는 `arc` | **MORE 판정** (최대 4회) | 2초 |
| 그 외 (`nozzle`, `turn`, 목표를 모르는 op) | **즉시 `GO`** | 없음 |

> 🔵 **2026-08-11 변경**: MORE 판정 조건에서 `role=path` 요구를 뺐다. 기준은 이제
> "그 op이 끝났을 때 마커 중심이 어디 있어야 하는지 서버가 아는가" 하나이고,
> **오프셋 보정 다리(`role=offset`인 `move ±a`)도 대상**이다.
>
> 예전에는 그 다리들이 조건에서 통째로 빠져, 매 꼭짓점마다 150mm를 슬립계수 하나만
> 믿고 개루프로 찍고 틀려도 아무도 고치지 않았다. 펜 오프셋 설정값이 실측과 5mm만
> 어긋나도 그 오차가 보정 없이 꼭짓점마다 그대로 나타난다(2026-08-11 삼각형 시험
> 관측: 꼭짓점 벌어짐 6~18mm). 목표는 §6.5 식 그대로다 —
> `move(+a)`는 「꼭짓점 + a·û」(곧 노즐을 내리므로), `move(-a)`는 「꼭짓점」.
>
> 두 보정 모두 **노즐이 올라가 있는 동안** 실행된다(`move(+a)` 뒤엔 아직
> `nozzle(down)` 전, `move(-a)` 앞엔 이미 `nozzle(up)`). 도료를 문지를 여지가 없다.
> 회귀 테스트: `make offset_feedback_test && ./tools/offset_feedback_test`

- 한 boundary에서 MORE 판정과 ALIGN 판정이 모두 걸릴 수 있다(도색 move 직후 곧바로 arc).
  이때는 **MORE를 먼저 소진하고, 그다음 ALIGN**을 돌린 뒤 `GO`.
- 재시도 횟수는 **boundary마다 0으로 리셋**한다.

### 6.2 2초 대기 창

- 기준 시각 = **READY 수신 시각** (ALIGN/MORE 송신 시각이 아니다).
  로봇이 회전/전진하는 동안 흘러간 시간을 대기에 포함시키면, 정작 "동작이 끝난 뒤의
  장면"을 못 보고 판정하게 된다.
- 대기 창 동안 들어온 POS를 모은다.
  - 각도: `sin`/`cos` 누적 후 `atan2` (원 위 평균 — ±180° 경계에서 깨지지 않게)
  - 위치: `x`/`y` 산술 평균
- 🔴 **창 안에 채택된 POS가 0장이면 판정하지 않고 곧바로 `GO`.**
  직전 판정과 글자 그대로 같은 pose이므로 **똑같은 보정이 한 번 더 나가는 것이 보장**된다
  (v1에서 -34.6° ALIGN이 값까지 동일하게 3번 나가 로봇이 104° 돈 사례가 있다).
  재시도 카운터는 소모하지 않는다 — 실제로 시도한 게 아니다.

### 6.3 `DRIFT` — 주행 중 각도 피드백

- **`role=path`인 `move`를 실행 중일 때만** 보낸다.
  `arc` 실행 중에는 보내지 않는다. `role=offset`인 `move`(0.155m)에도 보내지 않는다.
- 서버는 "지금 실행 중인 op" = 마지막으로 `GO{k}`를 보낸 뒤 `READY{k+1}`이 아직 안 온 상태의 `k`.
- 값 = 그 구간의 명목 heading 대비 오차. `angle_deg = -normDeg(target - theta_deg)`.
- 전송 주기 상한 `400ms`. `|angle_deg| < 1.0°`면 보내지 않는다.
- 로봇은 이 신호에 **READY로 응답하지 않는다.**
- 🔴 **거동은 "연속 조향"으로 정한다** — 멈추지 않고 좌우 바퀴 속도차로 흡수한다.
  실주행 테스트 후 "잠깐 멈추고 → 틀고 → 재출발"로 바뀔 수 있다. **서버 동작은 어느
  쪽이든 동일하다** (DRIFT는 fire-and-forget이라 로봇 거동을 서버가 알 필요가 없다).

### 6.4 `ALIGN` — 출발 각도 정렬

- 목표 heading은 서버가 알고 있다: Qt program의 각 op에 `heading_deg`(CCW 절대 방위)가 실려 있다.
  판정 대상 op에 없으면 **뒤따르는 op에서 첫 번째로 발견되는 값**을 쓴다.
- `err_ccw = normDeg(target_heading - theta_deg)`
- `|err_ccw| <= 4.0°` → `GO`
- 아니면 `ALIGN{op_index:k, angle_deg: -err_ccw}` 송신, 카운터 +1
- 6회를 다 쓰면 포기하고 `GO`

> 임계값 4.0°는 v1에서 현장 튜닝된 값이다(로봇 메인 루프 80ms × 22.58 step/deg에서
> 오는 1틱 오버슛 1.42°, + 마커 코너 픽셀 노이즈 σ≈0.7°). 로봇이 감속 접근/예측 정지를
> 넣어 오버슛을 줄이면 다시 내릴 수 있다.

### 6.5 `MORE` — 주행 거리 보정

- 서버는 목표 좌표를 **Qt가 준 데이터로만** 구한다 (추측항법 누적 없음).
  - `points` = BLUEPRINT 폴리라인 (= 펜 자취)
  - `v` = 각 Qt op의 "출발 꼭짓점" index
- 방금 끝낸 path op의 **도착 꼭짓점** = 그다음 path op의 `v`.
  다음 path op이 없으면 `points`의 마지막 점.

```
pen_target    = points[v_next]                          (도색 move/arc, 오프셋 move(-a))
              = points[v_self]                          (오프셋 move(+a) = 도색 시작 꼭짓점)
center_target = pen_target + a * û(target_heading)     if 끝난 뒤 노즐이 내려가 있어야 하면
              = pen_target                             if 아니면 (노즐 up 상태)
more_dist     = (center_target - center_actual) · û(target_heading)
```

「끝난 뒤 노즐이 내려가 있어야 하는」 op = 도색 `move`/`arc`, 그리고 **오프셋
`move(+a)`** (바로 다음이 `nozzle(down)`이므로 중심이 이미 a 앞이어야 한다).
오프셋 `move(-a)`는 이미 노즐을 올린 뒤라 목표가 꼭짓점 그대로다.

> 🔴 `+ a * û` 항이 **"오프셋 보정으로 인한 이탈은 정상"** 을 코드로 표현한 것이다.
> 이 항을 빠뜨리면 도색 구간마다 서버가 15.5cm 전진 오차를 잡고 있다고 착각해
> 매번 `MORE{-0.155}`를 쏜다.

- `|more_dist| <= 0.03m` → `GO`
- `|more_dist| > 0.5m` → 물리적으로 말이 안 되는 값이므로 판정 폐기하고 `GO` + WARN 로그
- 아니면 `MORE{op_index:k, dist_m: more_dist}` 송신, 카운터 +1 (양수 = 전진, 음수 = 후진)
- 4회를 다 쓰면 포기하고 `GO`

## 7. POS 두절 시 정지 (`HOLD`)

- 마지막으로 **채택된** POS로부터 `2000ms` 동안 새 POS가 없으면
  → `HOLD{"hold":true, "reason":"pos_lost"}`
- 로봇은 **실행 중인 op 도중이라도 즉시 정지**한다. op을 포기하지 않고 그 자리에서 멈춘다.
- POS가 다시 **연속 2장 채택**되면 → `HOLD{"hold":false}`
- 로봇은 멈춘 지점에서 **같은 op을 이어서** 수행한다 (남은 거리/각도부터).
- HOLD 중에는 서버가 `GO`/`ALIGN`/`MORE`/`DRIFT`를 **일절 보내지 않는다.**
  해제 시 유예 중이던 boundary의 2초 창을 **다시 처음부터** 센다.
- "채택"의 기준은 v1 POS 이상치 게이트를 그대로 쓴다
  (허용치 = `3.0° + 40°/s × dt`, 연속 5회 거부 시 재동기).

## 8. 단계 전이 (`phase`)

v1과 동일하다.

```
Qt: CMD{START_DRAW}
     └─> 서버: PATH{phase:"approach"}      (pose → points[0], 오프셋 보정 없음)
          └─> 로봇: PATH_DONE{"approach"}
               └─> 서버: PATH{phase:"draw"}  (Qt program + 오프셋 보정)
                    └─> 로봇: PATH_DONE{"draw"}
                         └─> 서버: Qt에 DRAW_DONE
```

- 접근 경로는 서버가 생성한다: `turn`(시작점 방향) → `move`(시작점까지) →
  `turn`(첫 도색 heading으로). 전부 `role="path"`, 노즐은 up인 채로 유지.
- 🔴 **접근 단계에도 ALIGN / MORE / DRIFT를 전부 적용한다.** 접근에서 빠지는 것은
  **오프셋 보정 op뿐**이다. 접근 도착 위치의 오차가 그대로 도색 시작점 오차가 되므로
  MORE를 켜 두는 편이 낫다 (단계당 2초를 쓰는 값은 한다).
- 접근 중에는 노즐이 up이므로 `MORE`의 목표는 `points[0]` **그대로**다
  (`+ a * û` 항 없음 — §6.5).
- `phase`는 서버가 상태로 판단한다. 로봇이 `phase`를 안 실어도, 어긋나게 실어도
  동작하되 WARN 로그를 남긴다 (v1 그대로).

## 9. 전체 예시

도면: `points = [[0,0],[2,0],[2,1.5]]`, 전 구간 도색.

Qt program (변경 없음 — 대문자, CCW 양수):
```json
[{"op":"MOVE","dist_m":2.0,"paint":true,"heading_deg":0.0,"v":0},
 {"op":"TURN","angle_deg":90.0,"heading_deg":90.0,"v":1},
 {"op":"MOVE","dist_m":1.5,"paint":true,"heading_deg":90.0,"v":1}]
```

서버가 만드는 `PATH{phase:"draw"}.ops`:

| idx | op | role | 값 | 실행 후 중심 위치 | 펜 |
|---|---|---|---|---|---|
| 0 | `move` | offset | `+0.155` | (0.155, 0) | (0,0) |
| 1 | `nozzle` | offset | `down=true` | — | (0,0) |
| 2 | `move` | **path** | `+2.0` | (2.155, 0) | (2,0) |
| 3 | `nozzle` | offset | `down=false` | — | — |
| 4 | `move` | offset | `-0.155` | (2, 0) | — |
| 5 | `turn` | **path** | `-90.0` (좌 90°) | (2, 0) | — |
| 6 | `move` | offset | `+0.155` | (2, 0.155) | (2,0) |
| 7 | `nozzle` | offset | `down=true` | — | (2,0) |
| 8 | `move` | **path** | `+1.5` | (2, 1.655) | (2,1.5) |
| 9 | `nozzle` | offset | `down=false` | — | — |
| 10 | `move` | offset | `-0.155` | (2, 1.5) | — |

boundary 처리:

| READY | 직전 op | 처리 |
|---|---|---|
| `{0}` | — (경로 시작, draw) | 2초 → **ALIGN** (목표 heading 0°) ×≤6 → `GO{0}` |
| `{1}` | 0: offset move | 즉시 `GO{1}` |
| `{2}` | 1: nozzle | 즉시 `GO{2}` |
| — | *op 2 주행 중* | **DRIFT** (≤2.5Hz, 목표 heading 0°) |
| `{3}` | 2: path move | 2초 → **MORE** (목표 중심 `(2.155, 0)`) ×≤4 → `GO{3}` |
| `{4}` | 3: nozzle | 즉시 `GO{4}` |
| `{5}` | 4: offset move | 즉시 `GO{5}` |
| `{6}` | 5: path turn | 2초 → **ALIGN** (목표 heading 90°) ×≤6 → `GO{6}` |
| `{7}` | 6: offset move | 즉시 `GO{7}` |
| `{8}` | 7: nozzle | 즉시 `GO{8}` |
| — | *op 8 주행 중* | **DRIFT** (목표 heading 90°) |
| `{9}` | 8: path move | 2초 → **MORE** (목표 중심 `(2, 1.655)`) ×≤4 → `GO{9}` |
| `{10}` | 9: nozzle | 즉시 `GO{10}` |
| — | 10 실행 후 | `PATH_DONE{"draw"}` |

**꼭짓점 (2,0) 부근 전체 순서** (요구사항의 `turn → align → go → 노즐 오프셋 보정 → move`):

```
op2 move(path)  →  op3 nozzle up  →  op4 move(-0.155)  →  op5 turn
                                                            ↓
                                              READY → 2초 → ALIGN → GO
                                                            ↓
                              op6 move(+0.155)  →  op7 nozzle down  →  op8 move(path)
```

### 남은 항목

1. **로봇팀 기구학 다이어그램 정정 공유** (§5.4). 직각 꼭짓점이 N → **C**로 바뀌고
   `R_robot` 식의 부호가 뒤집힌다. 바퀴 속도 분배식(SPS)은 그대로지만 입력값이 달라진다.
   실기로 원 하나 그려 교차 검증할 것.
2. ✅ **[해결 2026-08-06] 호 진입 자세 — 원이 통째로 어긋나던 문제** → **§5.7로 승격.**

   `turn(±φ)` 오프셋 보정을 서버가 끼워 넣도록 구현했다 (`ops_builder.hpp`
   `arcPhaseDeg` / `travelGeom`). 같은 드라이런으로 재측정:

   | 항목 | 보정 전 | 보정 후 |
   |---|---|---|
   | 서버가 보낸 `radius_m` | `0.4754` ✅ | `0.4754` ✅ |
   | 펜이 그린 호의 반지름 (도면 `0.500`) | `0.4996` ✅ | `0.4997` ✅ |
   | 펜 도착점 (도면 `(0, −1.0)`) | `(0.310, −0.950)` ❌ **0.31m** | `(−0.001, −0.999)` ✅ **1mm 이내** |

   회귀 확인: 사각형 도면(`--side 0.6`) 4꼭짓점 전부 정확히 일치. 직선 경로 영향 없음.

   ⚠️ 위 드라이런은 `heading_deg`를 **출구** 접선으로 읽던 시점(`91ec2e2`)의 결과다.
   2026-08-07에 **진입** 접선으로 확정하면서 되돌렸으므로(§5.7), 진입 규약 기준으로
   드라이런을 한 번 다시 돌려 이 표를 갱신할 것. 반지름은 규약과 무관하므로
   영향이 없지만 도착점은 재확인이 필요하다.

3. **`MORE`는 노즐이 내려간 채로 실행된다.** boundary가 `nozzle(up)` op **앞**에
   있어서, 거리 보정 주행이 그대로 도색된다. 직선에서는 이게 옳다(그리다 만 선을
   끝점까지 이어 그린다).

   ⚠️ **호 뒤의 `MORE`는 여전히 접선이 아니라 차체 방위(접선 + φ)로 직선을 덧그린다.**
   2번이 해결되어 투영축 자체는 맞게 됐지만(그래서 보정량은 옳다), 그 보정 주행이
   호가 아니라 직선이라는 사실은 그대로다. 실사용 반지름이 정해지면 호 뒤 `MORE`의
   데드밴드를 따로 키울지 정할 것.

   🟡 미해결: **`MORE`의 음수(후진)**. 과주행하면 노즐이 내려간 채로 후진해 젖은
   도료를 문지른다. 전진 전용으로 제한할지, 과주행은 그냥 감수할지 결정 필요.
4. ✅ **해결 (2026-08-07)** — `R_paint` 실사용 하한 = **0.200m**. 로봇팀 확정치이며
   `min_paint_radius_m` 기본값에 반영했다 (§5.5).
   - 안쪽 바퀴 역회전(`R_paint < 0.176m`, §4.4)은 **제약이 아니었다**. 모터 드라이버가
     좌우 반대방향 동시 구동을 지원한다는 회신을 받았다. 하한을 결정한 것은 역회전이
     아니라 **바깥 바퀴의 SPS 발산**이다.
   - 남은 것: 호 뒤 `MORE` 데드밴드를 따로 키울지(위 3번). 하한이 정해졌으니 판단 가능.
5. **수동 조작(`manualMode_`) 중 boundary 처리**. v1은 수동 CMD가 오면 자동 판정을 멈췄다.
   v2에서는 로봇이 READY로 대기 중일 수 있으므로, 수동 진입 시 대기 중인 READY를
   어떻게 회수할지 정해야 한다 (현재 안: 즉시 `GO`로 흘려보내지 말고 경로 자체를 폐기).
6. **꼭짓점당 실행 시간**. 노즐 op 2개(≈2초) + boundary 대기 2~4초 + 오프셋 이동 2회.
   꼭짓점 하나에 최소 6~8초가 든다. 도면이 크면 총 소요를 미리 견적낼 것.
