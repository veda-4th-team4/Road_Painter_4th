# 로봇 오도메트리 주행 호모그래피

- 버전: v1.0 (2026-08-12)
- 상태: 서버 구현 완료 / CCTV 구현 중 / 통합 시험 전
- 이 문서가 **정본**이다. 설계·프로토콜·구현 현황을 한 곳에 모았다.
  작성 과정의 논의 기록은 §12의 참조 문서에 있다.

---

## 1. 무엇을 하는가

로봇이 **알려진 크기의 직사각형을 개루프로 한 바퀴 돌고**, 9개 정지점마다
CCTV가 로봇 마커를 캡처한다. "물리좌표(서버가 계산) × 픽셀좌표(카메라가 관측)"
쌍 8개로 호모그래피 `H_marker`를 직접 구한다.

**기존 체커보드 방식과 비교했을 때 얻는 것:**

| | 체커보드/앵커 | 오도메트리 주행 |
|---|---|---|
| 직접 얻는 행렬 | `H_floor` (바닥 평면) | **`H_marker`** (마커 평면) |
| 시차 보정 | 바닥→마커 변환 필요 | **불필요** (마커를 직접 찍음) |
| 대응점 분포 | 보드 크기만큼 | **작업 영역 전체** |
| 물리 타깃 | 체커보드 필요 | **로봇만 있으면 됨** |

`H_marker`는 서버가 pose 계산에 실제로 쓰는 행렬이다. 이 방식은 그것을 중간
변환 없이 곧장 측정한다.

**대가는 §8에 정리했다 — 반드시 같이 읽을 것.** 오도메트리의 거리 스케일
오차는 이 방식의 자체 검증 장치로 잡히지 않는다.

> **SRS와의 관계**: `Road-Painter_기술명세서_SRS_v1.7_draft.md` §1.3 / SRN-004 /
> 부록 B "금지 사항 1"은 오도메트리 결과를 캘리브레이션 기준 좌표로 쓰는 것을
> 순환 참조를 이유로 금지하고 검증 전용으로만 쓰라고 명시한다. 이번 시도는 그
> 조항을 알고도 새로운 방식으로 진행하기로 한 결정이다(2026-08-11). §8이 그
> 조항이 우려한 위험을 정량적으로 다룬다.

## 2. 전체 흐름

```
[1] 관리자창 → Server    CALIB_START{method:"robot_motion", ch, m_cm, n_cm, start_corner}
[2] Server  → Robot+CCTV  CALIB_START 중계   ← 로봇 노즐 강제 UP(R-1) + 카메라 세션 개시
    Server  → Robot      PATH{phase:"calib", ops:[11개]}
[3] Robot   → Server      READY(k)                    ← 정지점마다
    Server  → CCTV        CALIB_CAPTURE{point_index, world_xy_mm}
    CCTV    → Server      CALIB_CAPTURE_OK{pixel_uv}  ← 카메라가 정지 판정 후
    Server  → Robot       GO(k)
                                                       ← 9회 반복
[4] Robot   → Server      PATH_DONE(calib)            ← 마지막 점은 READY 없음
    Server  → CCTV        CALIB_CAPTURE{point_index:8}  → ack
    Server  → CCTV        CALIB_DONE{m_mm, n_mm}
    ※ 서버의 세션은 여기서 끝난다
[5] CCTV                  8점으로 findHomography + LOO → H_marker
                          H_floor 역산, K/D 재활용, 번들 조립
    CCTV    → Server      H_MATRIX{ch, calib:{...}}
[6] Server                영속 저장 + Qt 즉시 중계
```

Qt는 이 세션을 **트리거하지 않는다**(v1). 관리자창 전용이다 — 캡처 완료와
호모그래피 산출 사이에 사람 입력(높이 2종)이 끼어서, 기존 `CALIB_START` 계약의
"종결 응답 하나로 닫는다"(`H_MATRIX`|`CALIB_FAIL`|`CALIB_CANCELLED`)를 세션
안에서 지킬 수 없기 때문이다. 결과 호모그래피는 [6]에서 평소 캘리 갱신과
똑같이 Qt로 중계된다.

## 3. 좌표계와 운영 제약

### 3-1. 월드 원점은 로봇의 출발 위치다

이 방식의 좌표계는 **로봇이 서 있는 자리가 정의**한다. 그래서 원점이
**세션마다 바뀐다**(수용된 결정). 번들의 `origin_mm`/`canvas_mm`은 이번 주행의
사각형 `(0,0)~(m,n)`이 된다.

### 3-2. 로봇은 작업 영역 왼쪽 변에서 시작한다

| `start_corner` | 시작점 | 1구간(m) 방향 | 회전 | 종료 |
|---|---|---|---|---|
| `bottom_left` | `(0, 0)` | +x | 왼쪽(CCW) | 시작점 복귀 |
| `top_left` | `(0, n)` | +x | 오른쪽(CW) | 시작점 복귀 |

회전 방향은 조작자가 고르는 값이 아니라 **시작 위치가 결정**한다. 같은 물리
영역을 어느 쪽 모서리에서 도느냐의 차이일 뿐이다.

코드로 강제하지 않는다 — 버튼을 누르기 전 조작자가 지켜야 하는 절차다.

### 3-3. `world_xy_mm`은 마커 중심 좌표다

> `world_xy_mm` = 그 순간 **마커 중심**의 월드 좌표. 로봇 회전 중심이 아니다.

CCTV가 짝짓는 픽셀이 마커이므로 필드 정의를 마커 기준으로 못박는다. 마커가
회전 중심에서 벗어나 있으면 정지점마다 헤딩이 달라(0°·90°·180°·270°) 어긋나는
**방향까지 달라지는데**, 이 보정은 전적으로 서버 내부에서 처리하고 CCTV는
무관하다:

```
world = center + marker_offset_mm × (cos(heading), sin(heading))
```

`marker_offset_m`(`params.json`, 기본 **0.0**)이 0이면 §4-2 좌표표가 그대로
나간다. 프로토콜이 이 물리 측정 결과를 기다리지 않는다는 것이 이 정의의
목적이다 — 값이 나중에 0이 아닌 것으로 밝혀져도 `params.json`만 고치면 되고
코드도 wire 형식도 안 바뀐다.

> 측정 방법(로봇팀): 로봇을 제자리에서 360° 회전시켜 마커가 한 점에 머무는지
> 원을 그리는지 본다. 원이 그려지면 그 반지름이 오프셋이다.

## 4. 로봇 경로

### 4-1. `CALIB_START` 중계 + 11-op, 펌웨어 변경 없음

서버는 두 가지를 보낸다:

```
1. CMD{cmd:"CALIB_START", ...} 원본을 ROBOT + CCTV 양쪽에 중계
2. 사각형 op 시퀀스를 PATH{phase:"calib"} 로 로봇에 전송
```

**`CALIB_START` 중계가 필수인 이유** — 두 가지가 여기에 달려 있다:

| 수신자 | 하는 일 |
|---|---|
| **ROBOT** | R-1 핸들러가 `auto_nozzle = 0` + `SendControlNozzle(0)`으로 **노즐을 강제로 올린다** |
| **CCTV** | `CALIB_START`가 **카메라 세션의 시작점**이다 (CCTV팀 2차 회신 §5-B) |

> 🔴 로봇 쪽이 안전 항목이다. 노즐 출력은 `nozzle_on = manual_override ?
> manual_nozzle : auto_nozzle`(`main.cpp:381`)로 결정되는데, **새 PATH를 적용할
> 때 `manual_nozzle`만 0으로 되돌리고 `auto_nozzle`은 건드리지 않는다.** 직전
> 도색이 노즐을 내린 채 비정상 종료됐다면(연결 끊김, HOLD 중 포기) `auto_nozzle`
> 이 1로 남고, 캘리 op에는 nozzle op이 하나도 없어서 **로봇이 3m 사각형을 그리며
> 바닥을 칠한다.** R-1이 정확히 이걸 막는 장치다.

로봇은 이후 `PATH`/`READY`/`GO`/`PATH_DONE` 기존 핸드셰이크를 그대로 탄다 —
캘리 전용 주행 로직은 없다.

```
ops = [ MOVE(m/2), MOVE(m/2), TURN(±90°),
        MOVE(n/2), MOVE(n/2), TURN(±90°),
        MOVE(m/2), MOVE(m/2), TURN(±90°),
        MOVE(n/2), MOVE(n/2) ]                          (11 ops)
```

- 회전 부호는 §3-2의 `start_corner`가 정한다
- 기본 `m=90cm`, `n=60cm` → 반쪽 구간 45cm/30cm (`min_move_m`=1cm 여유 충분)
- 노즐 op 없음 (도색하지 않는다 — 노즐 UP 보장은 위 R-1이 한다)
- 새 PATH 수신 시 로봇이 **2.5초 정지 대기 후 READY(0)** — 출발점의 정착 대기가
  기존 동작으로 이미 충족된다 (`main.cpp` 2500ms)
- 로봇은 새 PATH를 **현재 세그먼트가 끝난 뒤에 적용**한다(IMU yaw 보호 목적,
  커밋 `78c1005`) — 주행 중 캘리를 시작해도 중간에 경로가 갈리지 않는다

**사각형을 닫는 이유**: 3구간만 달리면 꼭짓점 4 + 중점 3 = 7점뿐이다. 4구간을
다 돌면 **8점**이 되고 로봇이 출발점으로 돌아온다(그 복귀가 폐합오차 측정이
된다, §8).

### 4-2. 정지점 9개와 좌표표

`m`/`n`은 mm(`m_cm×10`). 아래 예시는 기본값 `m=900, n=600`.

| `point_index` | 캡처 트리거 | `bottom_left` | `top_left` |
|---:|---|---|---|
| 0 | `READY(0)` | `(0, 0)` | `(0, 600)` |
| 1 | `READY(1)` | `(450, 0)` | `(450, 600)` |
| 2 | `READY(2)` | `(900, 0)` | `(900, 600)` |
| — | `READY(3)` | *(직전 op이 TURN — 스킵, 즉시 GO)* | |
| 3 | `READY(4)` | `(900, 300)` | `(900, 300)` |
| 4 | `READY(5)` | `(900, 600)` | `(900, 0)` |
| — | `READY(6)` | *(스킵)* | |
| 5 | `READY(7)` | `(450, 600)` | `(450, 0)` |
| 6 | `READY(8)` | `(0, 600)` | `(0, 0)` |
| — | `READY(9)` | *(스킵)* | |
| 7 | `READY(10)` | `(0, 300)` | `(0, 300)` |
| 8 | **`PATH_DONE`** | `(0, 0)` | `(0, 600)` |

**캡처 트리거 규칙**: `직전 op이 TURN이면 스킵`. TURN 앞뒤 READY는 같은 물리
위치라 한 번만 찍으면 된다.

**마지막 점(idx 8)은 `PATH_DONE`으로 잡는다** — 로봇(`main.cpp` R-4)은 마지막
op 완료 후 READY를 보내지 않고 곧장 `PATH_DONE`을 보낸다.

**idx 8은 `findHomography` 입력에서 제외한다.** 라벨이 idx 0과 겹쳐 같은
물리좌표에 다른 픽셀을 주면 모순된 대응점이 된다. 대신 **idx 0과 idx 8의 픽셀
차이 = 한 바퀴 누적 오도메트리 오차**로만 쓴다.

### 4-3. 피드백은 완전히 꺼진다

캘리 주행은 **온전한 개루프**여야 한다. 그 채널에 옛 캘리브레이션이 남아 있으면
pose 계산이 되면서 MORE/ALIGN이 **옛 캘리 기준으로 이번 주행을 "보정"해버려**
순수 오도메트리가 아니게 되기 때문이다.

이중으로 막는다:

1. **op 자체** — 11개 op 전부 `hasTarget=false`, `headingDeg=kNoHeading`,
   `isPath=false`로 만든다. `needsMore()`의 `hasTarget` 검사, `needsAlign()`의
   role 검사, DRIFT의 `isPath` 검사에 전부 걸려 자연히 차단된다.
2. **phase 가드** — `onReady()`가 `activePhase_=="calib"`이면 판정 로직 전체를
   건너뛰고 캡처 핸드셰이크로 위임한다.

### 4-4. IMU (로봇팀 작업 예정)

캘리 주행이 개루프인 만큼 로봇은 회전 정확도를 **IMU로 잡기로 했다**
(2026-08-12 결정). 현재 코드 상태:

| | 현재 |
|---|---|
| `UpdateTurn()` (회전) | IMU를 **안 받는다** — 엔코더 스텝 + 하드코딩 +3% 보정계수만 |
| `UpdateMove()` (직진) | `imu_yaw_deg`를 받지만 **로그에만** 쓴다 (조향은 서버 DRIFT만) |
| yaw 리셋 | `phase=="draw"`일 때만 (`main.cpp:146`) |

**요청**: yaw 리셋 조건에 `calib`을 추가할 것.

```cpp
if (phase == "draw" || phase == "calib") {
    imu_manager.ResetYaw(0.0f);
}
```

`ResetYaw()`는 적분기를 0으로 놓는 로컬 동작이라 서버·카메라 입력이 필요 없다 —
피드백이 꺼져 있어도 아무 문제 없이 동작한다. 그리고 이 방식에서는 의미가 더
정확하다: 월드 좌표계를 **로봇 출발 자세가 정의**하므로(§3-1), "PATH 시작 시점
헤딩 = 0°"가 §4-2 좌표표의 전제 그 자체다. 리셋을 걸면 IMU yaw가 좌표표의
헤딩(bottom_left면 0/90/180/270)과 **크기가 같은 값**이 된다.

> 부호는 로봇팀 확인 필요: `current_yaw += gyro_z_deg_s × dt`
> (`ImuManager.cpp:167`)가 CCW 양수인지는 센서 장착 방향에 달려 있어 코드만으로는
> 확정할 수 없다. 서버 내부 규약은 **CCW 양수**다. 반대로 나오면 좌표표 대조 시
> 부호만 뒤집으면 된다 — 제어에 쓰지 않는 진단값이라 영향 범위는 좁다.

리셋을 안 걸면 캘리 시작 시점의 yaw가 몇 시간 전 마지막 도색 세션에서 누적된
값이라, IMU 회전 제어를 켜놓고도 기준점이 틀어진 채로 잡게 된다.

> 부수 효과: 각 정지점에서 IMU yaw를 보고하면 **카메라와 무관한 회전 오차
> 진단**이 된다. 다만 §8의 진짜 사각지대(거리 스케일)는 회전 문제가 아니라
> IMU로 잡히지 않는다.

## 5. 캡처 프로토콜

### 5-1. 메시지 5종

```
Server → CCTV   CALIB_CAPTURE       {ch, request_id, point_index, world_xy_mm:[x,y]}
CCTV   → Server CALIB_CAPTURE_OK    {ch, request_id, point_index, pixel_uv:[u,v], spread_px}
CCTV   → Server CALIB_CAPTURE_FAIL  {ch, request_id, point_index, reason}
Server → CCTV   CALIB_DONE          {ch, request_id, m_mm, n_mm}
CCTV   → Server H_MATRIX            {ch, calib:{...}}          (기존 계약, §6)
```

| 필드 | 타입 | 단위 | 비고 |
|---|---|---|---|
| `ch` | int | — | **1-based** (`protocol.hpp:358` 기존 규약) |
| `request_id` | string | — | 세션 개시 때 받은 값 그대로 |
| `point_index` | int | — | 0~8 (§4-2) |
| `world_xy_mm` | [num, num] | mm | **마커 중심** (§3-3) |
| `pixel_uv` | [num, num] | px | **raw** (undistort 전, §5-3) |
| `spread_px` | number | px | 정지 판정 표준편차 — 잔차 대조용 |
| `m_mm`, `n_mm` | number | mm | `m_cm×10`, `n_cm×10` |

### 5-2. 매칭 키 = `ch` + `request_id` + `point_index`

세 개가 **전부** 일치해야 받아들인다. 하나라도 어긋나면 무시하고 WARN만 남긴다.

`request_id`만으로는 부족하다 — 세션을 재시작하면 `point_index`가 다시 0부터라,
특히 타임아웃 후 재시도는 **같은 인덱스로 되돌아가는** 경우여서 이전 세션의 늦은
ack가 새 세션의 대기를 잘못 풀 수 있다.

### 5-3. 픽셀은 raw로 주고받는다

`pixel_uv`는 **undistort 전 원본 픽셀**이다. POS가 보내는 정의와 동일하다
(`calib.hpp` 규약: "CCTV는 마커 코너를 원본 픽셀 좌표로만 보낸다"). 왜곡 보정과
`findHomography` 피팅은 **카메라 내부**에서 하고, 번들의 `coord_mode`는 그대로
`"undistort"`다.

서버가 raw 픽셀로 찍는 폐합오차는 **mm 환산이 불가능하다**(그 시점엔 새 캘리가
아직 없다). 서버 로그는 픽셀 지표로만 남기고, **mm 값은 카메라 기록이 정본**이다.

### 5-4. 정지 판정은 카메라가 한다

서버는 **고정 대기를 세지 않는다.** `READY`/`PATH_DONE`을 받으면 즉시
`CALIB_CAPTURE`를 보내고, 카메라가 프레임을 보며 로봇이 멈췄다고 판단한 시점에
캡처하고 ack한다. 서버는 ack 즉시 `GO`를 보낸다.

카메라 쪽 판정(CCTV팀 확정):

```
CALIB_CAPTURE 도착 시각 T 기록
 → t_capture 가 T 이후인 프레임만 사용 (그 전 프레임은 전부 폐기)
 → 연속 5프레임의 마커 중심 표준편차 ≤ 2px 이면 정지로 판정
 → 그 프레임들의 평균을 pixel_uv 로 채택
 → T + 10s 까지 판정 못 하면 CALIB_CAPTURE_FAIL{not_settled}
```

실패 방향이 안전하다 — 카메라 파이프라인이 지연되면 "아직 움직이는 프레임"을
보게 되므로 **더 기다리는 쪽으로만** 틀린다. 소요 시간은 채널 duty에 따라
2~20초로 변하므로 고정 대기가 애초에 맞지 않는다.

### 5-5. 실패 사유는 2층이다

| 수준 | reason | 서버 처리 |
|---|---|---|
| **지점** | `marker_not_found` / `not_settled` / `unmappable` | 그 점만 버리고 **계속 진행** |
| **세션** | `no_intrinsics` / `session_conflict` | **즉시 중단** (§7) |
| 세션 | `fit_failed` / `too_few_points` | 카메라가 `CALIB_DONE` 이후 자체 판정 |

한 점 때문에 3m 주행을 통째로 버리는 건 비싸다. 다만 유효 대응점이 **6개 미만**
이면 세션 실패다 — 4~5점이면 LOO 잔차가 의미를 잃어 품질 지표가 사라진다.

> `unmappable`: 이 렌즈는 왜곡이 커서(`k3 = -7.98`) 화면 바깥 약 15%에서 왜곡
> 보정이 발산한다. 마커가 **보이는데도 쓸 수 없는** 상태가 존재하고, 조작자가
> 할 일이 "가린 것 치우기"가 아니라 "사각형을 화면 안쪽으로 옮기기"라 구분이
> 필요하다.

### 5-6. 타임아웃 4종

| 주체 | 값 | 대상 | 만료 시 |
|---|---|---|---|
| 서버 | `calib_capture_timeout_ms` = 15000 | 캡처 ack 1건 | 세션 안전 중단 (건너뛰지 않는다) |
| 서버 | `calib_odo_timeout_ms` = 300000 | 세션 전체 | 세션 안전 중단 |
| 카메라 | 10초 | 정지 판정 1건 | `CALIB_CAPTURE_FAIL{not_settled}` |
| 카메라 | 10분 | 마지막 캡처부터 무응답 | 세션 폐기, 이후 `CALIB_CAPTURE`는 `{reason:"no_session"}`으로 거부 |

- 서버 캡처 타임아웃(15초)이 카메라 판정 한도(10초)보다 여유 있는 이유: 카메라가
  정상적으로 실패를 보고할 시간을 서버가 먼저 끊지 않기 위해서다.
- 캡처 타임아웃은 **건너뛰지 않고 중단**한다 — 카메라가 침묵하는 건 링크 문제고,
  그 상태로 3m를 계속 도는 건 의미가 없다.
- `calib_odo_timeout_ms`는 기존 `calib_timeout_ms`(180000)와 **별개 파라미터**다.
  후자는 정적 앵커 방식과 공유되고 그쪽은 지금도 Qt가 트리거하므로 "Qt가 5분에
  스스로 포기하니 서버는 그보다 짧아야 한다"는 클램프가 `params.hpp`에 걸려
  있다. 오도메트리 세션은 Qt가 트리거하지 않아 그 제약이 성립하지 않는다.

## 6. 호모그래피 산출과 전달

### 6-1. 카메라가 직접 피팅하고 보낸다

대응점은 **카메라가 보관**하고, `CALIB_DONE`을 받으면 **카메라가 직접 피팅해**
`H_MATRIX`를 서버로 보낸다. 관리자창을 거치는 중간 단계가 없다.

```
CALIB_CAPTURE → 정지 판정 → 픽셀 평균 → {point_index, world_xy_mm, pixel_uv} 내부 저장
CALIB_DONE    → 유효 8점으로 findHomography + LOO → H_marker → H_MATRIX 전송
```

관리자창 호모그래피 탭은 **`floor`(기존 체커보드) / `Odometry`(주행)** 두
서브탭으로 나뉜다. Odometry 탭은 시작 버튼 + 진행 상태 + 결과 표시(잔차,
폐합오차, 두 방식 비교) + §6-3 입력 필드를 담당한다.

> 8점이면 카메라의 LOO 기준(유효 5점 이상, 8점 미만은 advisory)을 만족해
> **advisory 없는 정식 LOO 잔차**가 나온다.

### 6-2. 이 방식이 내놓는 것은 `H_marker`다 — 시차 보정을 걸면 안 된다

체커보드 방식은 바닥 점으로 `H_floor`를 구한 뒤 카메라/마커 높이로 시차를
보정해 `H_marker`를 만든다. 오도메트리 방식은 **로봇 위 마커 자체를 찍으므로
결과가 처음부터 `H_marker`** 다. 여기에 바닥→마커 보정을 또 걸면 이중 보정이다.

카메라는 측정 `H_marker`를 **별도 슬롯**에 보관한다:

```
H_floor           앵커 실측 (floor 탭)              — 저장
H_marker (파생)    H_floor 를 K 로 분해              — 필요할 때 계산
H_marker (측정)    오도메트리 주행                    — 저장 (신설)
```

**로봇 측위에 어느 쪽을 쓸지는 조작자가 명시적으로 고른다. 기본값은
파생(체커보드) 쪽이다** — 주행 방식은 아직 스케일 오차를 검증할 수단이 없어서
(§8), 검증된 쪽을 기본으로 두고 의도적으로 전환하게 한다.

### 6-3. `H_floor`는 역산한다

두 평면은 **나디르를 중심으로 한 균일 스케일** 관계다(`h`=마커 높이,
`Zc`=카메라 높이, 관리자창의 `ratio` = `h/Zc`):

```
기존 방향 :  marker = nadir + (1 − h/Zc) · (floor  − nadir)      (축소)
이번 역산 :  floor  = nadir + (marker − nadir) / (1 − h/Zc)      (확대)
```

| 값 | 조달 |
|---|---|
| `h` 마커(로봇) 높이 | **조작자 입력** — 기존 `MARKER_HEIGHT` 필드 재활용 |
| `Zc` 카메라 높이 | **조작자 실측 입력** — 기존 `camera_z_measured_mm` 재활용 |
| 나디르(월드 좌표) | `H_marker` + `K` 분해 → 나디르 픽셀 → `H_marker`로 월드 변환 |

`Zc`는 `H_marker`+`K` 분해로도 나오지만 90×60cm 사각형 하나로 2.5m 높이를
역산하는 건 수치적으로 약하다. **실측값을 쓰고 분해값은 교차검증용으로 표시**
한다(기존 `camera_z_measured_mm` / `camera_z_used_mm` 구분과 같은 패턴).

> 규모 감각: 카메라 2.5m / 마커 160mm면 스케일이 **1.068배**다. 나디르에서
> 900mm 떨어진 점이 61mm 어긋난다. `H_floor`를 `H_marker`로 대충 채우면 서버
> pose는 `H_marker`를 쓰므로 멀쩡한데 **Qt top-view만 조용히 틀어진다**
> (서버는 `H_floor`가 없으면 `H_marker`를 복사한다 — `calib.hpp:188`).

### 6-4. `K`/`D`는 이 방식으로 나오지 않는다

번들의 `coord_mode`가 `undistort`라 캡처 픽셀을 피팅 전에 왜곡 보정해야 하고,
§6-3의 분해에도 `K`가 필요하다. 즉 **체커보드 내부 파라미터 캘리브레이션은
여전히 선행 조건**이고, 오도메트리 탭은 그 `K`/`D`를 그대로 물려받아 번들에
싣는다. 카메라는 `K`/`D`가 비면 **전송을 거부**한다.

> 서버의 왜곡 보정은 `Calib::hasKD`로만 켜진다. `K`/`D`가 빠진 번들이 오면
> 서버는 보정을 **조용히 건너뛰고** H를 raw 픽셀에 적용한다 — 에러 없이 좌표만
> 틀어진다. 실제로 겪은 사고 부류라(`cctv.py` 주석: "에러 없이 보정만 꺼졌다")
> 서버도 이 조합을 WARN으로 남긴다(거부는 하지 않는다 — 레거시 호환).
>
> 또한 측정 `H_marker`는 **피팅 당시의 `K`로 보정한 픽셀** 위에서 만들어진다.
> 나중에 `K`를 다시 잡으면 조용히 stale이 된다 — 카메라의 기존 K-변경 stale
> 표시가 이 신설 슬롯에도 걸린다(마커 높이 stale과 동일 취급).

### 6-5. 번들 필수 필드

```json
{
  "calib_id": "...", "created_at": "...",
  "image_size": [2592, 1520], "coord_mode": "undistort", "unit": "mm",
  "method": "robot_motion",
  "K": [[...]], "D": [...],
  "H_floor": [[...]], "H_marker": [[...]],
  "marker_height_mm": 160,
  "origin_mm": [0, 0], "canvas_mm": [900, 600],
  "axis": "x_right_y_up"
}
```

`method`(`"checkerboard"` | `"robot_motion"`)는 **탭이 아니라 번들에 실제로 실린
`H_marker`가 어느 슬롯에서 왔는지**로 채운다 — 조작자가 슬롯을 바꿔 쓸 수 있어
탭 기준으로 채우면 실제와 어긋난다.

서버는 번들을 저장·중계할 때 값을 바꾸지 않는다(**mm 보존** 규약,
`QT_CCTV_SERVER_CALIBRATION_FORMAT_20260811.md`). ÷1000은 서버 내부 계산용
사본(`Calib::Hf`/`Hm`)에서만 일어난다.

## 7. 안전 정지

`robot_motion` 세션의 취소·타임아웃은 **정적 앵커 방식과 같은 핸드셰이크**를 쓴다:

```
Server → Robot: CALIB_CANCEL   (ack: CALIB_STOPPED)   ─┐ 둘 다 모여야
Server → CCTV:  CALIB_CANCEL   (ack: CALIB_STOPPED)   ─┘ 세션을 닫는다 (5초 한도)
```

로봇은 R-2 핸들러(`main.cpp` `"CALIB_CANCEL"` 분기)에서 속도 0 + 노즐 UP +
경로 폐기 + 래치 클리어를 마친 뒤 **100ms 정착 후 `CALIB_STOPPED`를 회신**한다.

**`ABORT_DRAW`를 쓰지 않는 이유**: 그것도 로봇을 세우기는 하지만 **ack가 없다**
(로봇은 수신 즉시 속도 0을 내리는 동기 처리고, `DRAW_ABORTED`는 로봇의 회신이
아니라 서버가 QT에 보내는 통지다). 그러면 서버는 "명령을 보냈다"까지만 알 수
있는데, 이 규약이 지키려는 것은 **"로봇이 실제로 섰다는 확인"** 이다:

> 중계했다는 사실만으로 `CALIB_CANCELLED`를 보내면 안 된다. 그것은 "명령을
> 전달했다"는 뜻이지 "로봇이 섰다"는 뜻이 아니다 — 조작자는 이 응답을 보고
> 대기를 풀고 다시 화면 앞에 앉는데, 그 순간 로봇이 아직 굴러가고 있으면
> 사람이 다치는 쪽에 서 있게 된다. — `router_calib.cpp:190`

받을 수 있는 확인을 일부러 버릴 이유가 없다. 서버는 상태를 세우고 메시지만
보내고, 이후는 기존 상태 기계가 그대로 처리한다:

| 상황 | 처리 |
|---|---|
| 양쪽 ACK 도착 | `onCalibStopped()` → `clearCalib()` + `clearPath()` |
| 5초 안에 불발 | `checkCalibTimeout()` → `cancel_failed` (추정으로 확인하지 않는다) |

**정적 앵커 방식(`method != "robot_motion"`)의 취소·타임아웃 동작은 한 줄도
바뀌지 않는다.** 두 방식이 같은 핸드셰이크를 공유하되 `calibIsOdo_`로 갈리는
지점은 "타임아웃 파라미터 선택"과 "종료 시 `clearPath()` 여부"뿐이다.

## 8. ⚠ 검증과 한계 — 반드시 읽을 것

### 8-1. 잔차도 폐합오차도 스케일 오차를 못 잡는다

**호모그래피는 아핀 변환을 완전히 포함한다.** 오도메트리 라벨이 참값의 `s`배
(`W_label = s·W_true`)면 피팅 결과는 `H_fit = diag(s,s,1)·H_true`가 되고,
이것은 **유효한 호모그래피**다. 잔차가 **정확히 0**으로 나오면서 좌표는 틀린다.

> 이 연산은 서버 코드에 이미 있다 — `calib.hpp`의 `scaleMat3Rows01()`(mm↔m
> 변환용)이 정확히 "0·1행에 스칼라를 곱한다"이다. **스케일은 호모그래피가
> 자유롭게 흡수한다**는 사실이 코드로 드러나 있다.

| 오도메트리 오차 | 재투영 잔차 | 폐합오차 | 현실성 |
|---|---|---|---|
| **균일 스케일** (m·n 둘 다) | ❌ 완전 흡수 | ❌ 0 — 네 변이 똑같이 짧으면 정확히 복귀 | **높음** (바퀴 지름·틱 환산) |
| **m·n 스케일이 다름** | ❌ 흡수(아핀 신축) | ❌ 0 | **있음** (방향별 슬립 차이) |
| turn 88°/92° 교대 (진짜 전단) | ❌ 흡수 | ❌ 0 | 낮음 |
| turn 전부 88° (계통 편향) | ✅ 잡힘 | ✅ 잡힘 (76.7mm) | — |
| 한 지점만 슬립 | ✅ | ✅ | — |

**SRS 부록 B가 경고한 "오픈루프 오차 1~5%"가 정확히 첫 줄이다.** 900mm에서
3%면 27mm인데 두 지표 모두 0을 보고한다.

다행인 점: 이 경로는 회전이 **전부 같은 방향**이라 자이로·엔코더의 계통적 회전
편향은 "전부 88°" 쪽으로 나타나고 그건 두 장치가 다 잡는다. 교대 전단은
물리적으로 덜 그럴듯하다. 결과적으로 실질적 사각지대는 **스케일 계열 두 개**로
좁혀진다.

### 8-2. 유일한 독립 검증 — 체커보드와 비교

줄자와 엔코더는 **완전히 독립적인 길이 기준**이다. 두 방식의 결과를 비교하면
스케일 불일치가 드러난다. 행렬을 직접 비교하면 안 된다 — 월드 원점이 다르다.

```
1. 같은 평면으로 맞춘다:  A = H_marker(파생, 체커보드),  B = H_marker(측정, 주행)
2. 테스트 픽셀 N개를 두 행렬로 각각 월드로 보낸다
3. 두 점집합 사이 닮음변환을 최소제곱으로 맞춘다:  world_B ≈ s·R·world_A + t
4. 회전 R, 평행이동 t는 프레임 차이일 뿐이라 버린다
```

| 지표 | 정상 | 벗어나면 |
|---|---|---|
| **스케일 `s`** | 1.000 | **길이 기준 불일치** — 다른 어떤 장치로도 못 잡던 값 |
| 정렬 후 RMS 잔차 | ~0 mm | 형상 자체가 다름 (전단·원근·왜곡 미보정) |

로봇이 900mm 갔다고 보고했는데 실제 873mm였다면 `s = 1.031`로 나온다.
이 비교는 카메라가 계산해 Odometry 탭에 표시한다.

### 8-3. 비교로도 "어느 쪽이 틀렸는지"는 모른다 — 1m 실측이 필요하다

`s = 1.031`이 나와도 오도메트리가 3% 짧게 잰 것인지 줄자가 3% 어긋난 것인지는
구분되지 않는다. **불일치의 크기**만 나온다.

확정하려면 제3의 기준이 필요하다: **로봇을 정확히 1m 직진시키고 실제 이동거리를
줄자로 재는 것 한 번**이면 충분하다(엔코더 스케일 보정계수). 세션마다가 아니라
**로봇 물리 상수 1회 확인**이다.

이 실측 뒤에도 §1의 이점 세 가지는 그대로 남는다.

### 8-4. 사각형 크기 — 첫 주행은 900×600 유지

CH2 현재 `H` 기준 화면 영역:

| 화면 영역 | 월드 범위 |
|---|---|
| 전체 | 4,542 × 2,655 mm |
| **중앙 85%** (왜곡보정 수렴역) | **3,611 × 2,172 mm** |
| 중앙 70% | 2,793 × 1,734 mm |

기본값 900×600은 중앙 70% 안에도 넉넉히 들어가 `unmappable` 걱정은 현재
설치에서 하지 않아도 된다.

**키우면 원근항(`h20`, `h21`)이 잘 잡히지만**(대응점이 가장자리로 퍼져 조건수
개선) **오도메트리 누적 오차도 같이 는다.** 1,800×1,200까지는 중앙 85% 안에
들어가므로 검토 여지가 있다. 다만 §8-1의 스케일 사각지대는 키워도 나아지지
않고 드리프트만 커지므로, **첫 주행은 900×600으로 하고 폐합오차를 본 뒤**
결정하는 순서가 맞다.
