## 0. 요약

§1(HG_QUERY), §2(필드 배정) 둘 다 **코드 확인 결과 정상**입니다. 의심하신
두 경로 모두 문제가 없어서, 그렇다면 실제 원인이 아직 안 밝혀진 상태입니다.
저희 쪽에 남은 유력한 후보(§3)와, 원인 좁히기용 역질문(§4)을 같이 보냅니다.

| # | 확인 요청 | 결과 |
|---|---|---|
| 1 | `HG_QUERY`가 floor H 없는 렌즈에서 뭘 돌려주나 | **`available:false`만 돌려줌** — 측정 H 유출 경로 없음 |
| 2 | `SendCalibBundle()` 측정/역산 필드 배정 | **정상 (A)** — `H_marker`=측정, `H_floor`=역산 |
| 3 | `cmp_scale: 0.0` 원인 | **말씀하신 그대로** — floor H 없어 비교 대상 부재 |

## 1. 확인 요청 1 — `HG_QUERY`는 floor H 없으면 `available:false`만 돌려줍니다

```cpp
bool HomographyMapper::Get(int ch, double h[9]) const {
  if (!Available(ch) || h == NULL) return false;   // floor 슬롯(H_[ch])만 봄
  ...
}
```

`HG_QUERY` 핸들러(`ReportHomography()`)는 오직 floor 슬롯 `H_[ch]`만 읽고,
오도메트리 측정 슬롯(`hmm_[ch]`)은 아예 참조하지 않습니다. CH2처럼 floor H가
없으면 응답은 정확히:

```json
{"type":"HG","ch":2,"available":false,...}
```

**측정 H(마커 평면)가 `HG` 응답으로 새어나올 코드 경로가 카메라 쪽엔 없습니다.**

말씀하신 관리자 창 브리지(`calib_cache_h(H, ch)` → `push_calib_to_server()`)도
같이 확인했습니다 — 현재 `cctv.py`의 `HG` 핸들러는:

```python
if mtype == "HG":
    ch = msg.get("ch")
    if msg.get("available"):          # ← available 게이트, 이미 존재
        H = msg.get("H")
        calib_cache_h(H, ch)
    else:
        broadcast(f"[calib] ch={ch} 호모그래피 아직 계산 안 됨")
```

`available:false`일 때는 `calib_cache_h()` 자체가 호출되지 않습니다. 즉
**카메라·관리자창 양쪽 다 CH2의 측정 H가 `H_floor`로 둔갑할 경로가 없습니다.**
(참고로 이 게이트는 저희가 처음 확인한 게 아니라, 그쪽 코드 주석에 "ch 없이는
잘못 캐싱될 뻔한 버그였다"고 이미 남겨두신 부분이라, 최근에 한 번 손보신
자리로 보입니다.)

## 2. 확인 요청 2 — 필드 배정은 (A), 뒤바뀌지 않았습니다

```cpp
double Hm[9];
homography_.GetMeasuredMarkerPlane(ch, Hm);   // hmm_[ch] — FinishOdom()이 채움 (측정)
...
// s = 1 + h_mm/zc_m 로 나디르 기준 확대 → Hf
...
"H_marker":[[...Hm...]], "H_floor":[[...Hf...]]
```

`H_marker` 키엔 측정값(`Hm`), `H_floor` 키엔 역산값(`Hf`)이 그대로 들어갑니다.
JSON 조립 코드에 필드를 바꿔치기할 경로가 없습니다.

**물리적으로도 (A) 방향이 맞습니다**: 마커는 바닥보다 카메라에 더 가까우므로
같은 화각이 마커 평면에서는 더 좁은 실세계 범위를 덮습니다 — 바닥 평면(더 먼
거리)이 더 큰 스케일을 가져야 합니다. 검산하신 `s=1.103`(`H_floor`가
`H_marker`보다 큼)이 정확히 이 방향과 일치합니다. (B)라면 거꾸로(더 가까운
마커 평면 쪽이 더 큰 값)여야 하는데 그렇지 않습니다.

### 참고 — `cmp_scale: 0.0`

```cpp
if (!hmm_have_[ch]) { ...; return false; }
if (!GetMarkerPlane(ch, hd)) {   // floor H를 마커 높이로 역산한 비교 대상. floor H 없으면 실패
  *reason = "파생 H_marker 가 없습니다 (체커보드 캘리와 마커 높이가 필요)";
  return false;
}
```

말씀하신 그대로입니다 — CH2는 floor H 자체가 없어 비교 대상을 못 만들고,
`cmp_ok=false` → `cmp_scale=0.0` 폴백입니다. **제안하신 `cmp_scale: null` +
`cmp_scale_reason` 분리, 반영하겠습니다.** (다음 빌드에 포함)

## 3. 그럼 실제 원인은? — 저희 쪽 후보 하나, 확신은 아님

§1, §2 둘 다 코드상 정상이라 두 가설로는 관측된 증상이 설명이 안 됩니다.
번들(`calib_id: odom-1786610340124`)의 시각을 환산하면 **8/13 17:39** 인데,
이 시점은 저희가 그날 오후에 배포한 것 중:

- ✅ 16:19 설치(§1/§2 관련 로직 포함, 세션 사유 세분화 등) — **적용된 상태**
- ❌ 18:23 설치(Odometry 탭 수동 전송 버튼을 `ODOM_RESEND` 명령으로 교체) — **아직 미적용 상태**

였던 시점입니다. 18:23 이전 Odometry 탭의 수동 "서버로 전송" 버튼은 **저희가
그 이후 자체적으로 버그로 판단해서 교체한 것**입니다 — 카메라에 다시
요청하는 대신, 브라우저 쪽에서 캐시된 값으로 번들을 직접 구성해서 보내는
방식이었고, 그 캐시가 실제 오도메트리 측정 결과와 안 맞을 수 있는 구조였습니다.

**질문**: 17:39 시험에서 이 H를 보낸 경로가 (a) 주행 완료 직후 자동 전송이었나요,
아니면 (b) Odometry 탭에서 수동으로 버튼을 눌러 보내신 건가요?

- (a) 자동 전송이었다면 — 이 후보는 배제됩니다. 자동 전송은 처음부터
  `SendCalibBundle()` 하나만 타므로 §2에서 정상 확인된 경로와 동일합니다.
- (b) 수동 버튼이었다면 — 그 구버전 버튼이 원인일 가능성이 있고, 이미
  18:23 설치로 교체됐으니 **재시험하면 재현이 안 될 것으로 예상**합니다.

## 4. 역질문 — CH2 복원 시점

1차 회신 §7에서 "8/13 15:14 회귀 테스트가 운영 서버의 CH2 캘리 슬롯을
테스트 데이터로 덮었고, 복원 예정"이라 하셨습니다.

**질문**: 그 복원이 17:39 시험 **전**에 끝나 있었나요? 만약 시험 시점에
CH2 슬롯이 아직 오염된 상태였다면, Qt가 본 게 이번에 문의하신 정상 오도메트리
경로가 아니라 그 잔여 테스트 데이터였을 가능성도 있습니다.
